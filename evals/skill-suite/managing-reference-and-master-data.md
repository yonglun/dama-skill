# `managing-reference-and-master-data` 独立 GREEN／边界评估

## 结论与评估口径

**GREEN：正向场景能形成可执行的共享客户身份与参考代码治理方案；负向场景正确让位于单系统数据质量整改。未发现 P0、P1 或 P2 缺口。**

已完整读取 `skills/managing-reference-and-master-data/SKILL.md`、`skills/managing-reference-and-master-data/references/playbook.md`、`evals/skill-suite/baseline-master-data.md` 和 `evals/skill-suite/scenarios.md`。以下是按技能实际生成的场景决策及可验收输出，不把正文中出现关键词本身当作行为通过证据。比较对象是独立代理在未读取该技能时给出的基线回答；基线已经有较强的治理、质量、项目计划和验收设计，因此只把新增的主数据能力计为实质改进。

判级：P0 为错误主责或不可逆的错误身份发布；P1 为缺少关键裁决、回滚或消费者控制，以致方案不可安全实施；P2 为可实施但仍需项目自行发明的重要判定或证据结构。

## 测试 A：十周 CRM、计费、客服客户主数据整改

### 路由与业务边界

本案存在跨三个系统的客户身份、黄金表示、客户状态与国家代码的共享权威，且六个月前的一次清洗已经复发，因此由 `managing-reference-and-master-data` 主导身份、属性生存、参考代码和共享发布。`improving-data-quality` 主导地址有效性、输入规则、基线和根因闭环；`modeling-data` 裁决“自然人／组织／客户／计费账户／客服联系人”的粒度及关系；`integrating-data` 实现增量传输、重送和技术对账；治理、安全、元数据、架构分别承接决策权、用途与访问、目录血缘、系统责任。不得仅凭同名或共享地址把家庭成员、同集团法人或一个公司的多个计费账户合成一个客户。

十周目标沿用基线提出的初始目标作为待批准草案：第 1 周锁定分母后确认重复率下降至少 60%、人工抽检误合并率低于 2%、地址有效率至少 95%、三系统国家码合规率至少 99.5%、状态映射覆盖 100%、源头关键规则一次通过至少 98%。新增的验收维度是身份交叉引用覆盖、经批准的属性权威覆盖、自动匹配分群精确率／召回率、拆分恢复、参考代码版本兼容、消费者业务对账和管家队列 SLA。目标数值及自动化阈值须由客户数据 owner 根据损害和标注样本批准，不能由平台默认值决定。

### 身份、权威与黄金记录的代表性决策

先保留三套系统的 `source_system + source_customer_id`，再分配稳定的 `global_party_id`；计费账户与客服联系人保留独立对象和关系，不自动变成同一客户实体。交叉引用保存连接状态、首次／最后确认时点、证据、规则版本和裁决人。身份判断独立于地址、状态和国家码生存规则：即使两个来源被确认是同一实体，也可能因用途、时效或质量而选择不同的属性值。

| 决策项 | 十周方案中的可执行规则草案 | 批准与证据 |
|---|---|---|
| 身份 | 稳定且已核验的强标识、名称、联系方式及关系构成正证据；不同已核验强标识、法人边界或互斥事实构成负证据；只同名或同地址进入人工区 | 数据 owner 批准实体边界与禁止自动合并条件；标注样本和误合并分析存档 |
| 法定名称 | 以适用法人、时间和已核验登记事实选择；CRM 展示名可保留为别名 | 属性级权威矩阵列出来源、验证、时间、冲突与回退；源 owner 确认 |
| 地址 | 区分账单、联系、服务和历史地址；按用途选有效、最近确认且合法使用的值，无法核验则标记待确认 | 业务 owner 批准用途；质量团队给出验证结果和修复队列 |
| 客户状态 | 先定义三系统状态语义和映射；计费状态不覆盖 CRM 营销状态，互斥组合进入争议队列 | 状态定义、适用流程、规则版本、例外和批准记录 |
| 国家代码 | 采用经批准的两位标准代码集和本地映射；保存参考版本与生效期，旧交易仍可按当时版本解释 | 参考数据 owner 批准外部标准版本、本地映射、替换与消费者迁移 |

这张表是待第 1–2 周剖析和业务裁决的规则草案，不能被当作三个系统现状的既定事实。黄金记录的每个关键字段必须可回溯源值、获胜条件、有效期、人工覆盖、冲突、置信度和规则版本；缺证据时维持并列来源或待裁决状态，不发布猜测值。

### 匹配、合并、拆分与十周阶段门

| 周次／阶段门 | 具体动作 | 阻断验收证据 |
|---|---|---|
| 第 1–2 周：域与基线 | 批准客户与账户边界、源／消费者清单、字段权威矩阵、国家与状态参考集；按系统和群体标注正、负、边界样本，冻结质量分母与风险上限 | owner 签署模型、权威、样本抽取法、隐私用途、候选阈值与消费者影响；未签署不做批量合并 |
| 第 3–5 周：影子构建 | 建全局 ID／crosswalk、候选生成、三个裁决区、属性生存、案件队列；在隔离环境回放同名异人、家庭／集团、源 ID 复用、历史地址、边界证据和已发布错合并用例 | 按来源／地区／实体类型报告精确率、召回率、误合并率、漏合并率和人工比例；误合并超过 owner 上限或无法拆分则 No-Go |
| 第 6–7 周：试点 | 先只读发布黄金参考视图，验证一至两个消费者；高影响合并由管家与 owner 复核；分批开放低风险动作与源头国家码／地址／查重控制 | 每批保留前像、源 ID、关系、批准和撤销令牌；试点重复率下降及输入通过率达到已批准阶段目标；业务对账通过 |
| 第 8–9 周：扩展 | 分批接入其余业务单元和消费者，发布版本化状态／国家代码映射，回收拒绝项，通知代码弃用与过渡期 | 各消费者回执、版本和代码映射一致；异常有 owner、SLA、重送与暂停路径 |
| 第 10 周：移交 | 演练错误合并拆分、参考版本回退、消费者重对账；交接管家容量、每日监控、月度规则复测和源头反馈 | 指标达到批准阈值；未达标项有责任人、期限与风险接受；运行 owner 签收 |

三个裁决区须根据标注集确定：高置信且无禁止项的候选才可考虑自动连接；中间区由管家复核；低置信或强负证据不合并。合并单保存两边原始 ID、前像、特征／正负证据、规则版本、业务决定、每个属性的获胜理由、受影响交易／关系／消费者及批次。发现错合并时，恢复两个身份及其属性、关系和 crosswalk，发布 `split/correction` 事件，通知消费者并按其业务对象重新对账；不能把“恢复数据库备份”当作唯一拆分方案。

### 参考数据、管家与消费者验收

国家代码及客户状态须分别形成受控数据集，含稳定代码、定义、语言、层级或映射、来源、owner、版本、生效／失效、替换、历史解释和消费者。变更链为提议、语义审查、影响分析、owner 批准、沙箱测试、未来生效发布、回执与对账。代码含义改变时建立新版本／新稳定 ID；不得直接覆写旧含义或把 CRM 的本地状态码静默当成企业标准。紧急变更仍记录授权、通知和补做影响分析。

管家队列至少记录案件 ID、来源、候选与负证据、风险、受影响客户／账户、规则版本、责任人、SLA、决定、批准、执行批次、回滚和关闭证据。常规案件由管家处理；高价值客户、跨法人、阈值例外、批量合并与参考语义争议升级给 owner。提出批量动作的人不能独自批准并执行。

发布契约明确 `global_party_id`、源键映射、操作类型（新增／更正／合并／拆分／失效）、属性来源、参考版本与生效期、水位、质量状态和弃用窗口。每批至少对账：发布对象数与哈希；全局 ID—源 ID 的边；关键属性／代码／层级版本；消费者回执、导入／拒绝数、本地映射；抽样客户、账单与客服案件是否仍指向正确身份。任何关键消费者对账失败、旧码失去历史含义、无法拆分或无人处理队列都阻断扩展发布。

### 与 RED 基线的实质比较

| 检查点 | RED 基线已有内容 | 加载技能后的新增／更严格结果 |
|---|---|---|
| 项目结构和质量目标 | 十周计划、阶段门、RACI、重复率／地址／代码／状态指标和源头预防都较完整 | 保留这些优点，不把其原有能力误算为技能收益；为身份、版本、消费者对账增加专门验收 |
| 身份 vs 属性 | 提到黄金客户标识、交叉引用、字段映射 | 单独裁决“同一实体”与“哪个地址／状态／名称胜出”；账号、联系人和客户粒度先经业务批准 |
| 权威和黄金记录 | “黄金标识／交叉引用”有追踪，但未给出属性级、用途／时效条件的生存决策结构 | 逐属性权威矩阵和生存规则记录条件、有效期、人工覆盖、来源、置信度及回退；未决不伪造单一真相 |
| 匹配质量 | 合并建议抽检准确率、误判目标与人工高风险审核 | 已标注正／负／边界集、负证据和禁止项；分群精确率／召回率、漏合并率及人工区，防止为提高召回而放宽误合并风险 |
| 合并可逆 | 基线要求可回滚批次、源记录和审核痕迹 | 将错合并拆分细化到身份、属性、关系、crosswalk、交易和已发布消费者；保留前像与撤销令牌 |
| 参考数据 | 统一 ISO 两位国家码、状态映射、规则版本监控 | owner 审批、稳定代码、版本与生效期、替换／弃用、旧交易历史解释、消费者迁移与紧急变更 |
| 管家运营 | 例外队列、SLA、升级和所有者已有 | 案件的正负证据、规则版本、合并影响、批准／执行职责分离、关闭及拆分证据成为必填 |
| 发布及对账 | 基线要求下游影响图、接口报表确认和发布回滚 | 分清发布成功、消费者接收与业务正确；按身份边、内容版本、拒绝／隔离、客户／账单／客服业务对象逐层对账 |

## 测试 B：单系统一次性客户表修补

请求仅对一个系统的客户表做一次性去重和字段修补；无跨系统共享身份、无参考代码权威变更、无黄金记录或持续对外发布。**本技能不应主导。** 由 `improving-data-quality` 主导问题定义、剖析、规则、修复与复测；若需要决定客户表结构或键，由 `modeling-data` 协同；数据库实施由对应系统 owner 承担。只有后续出现跨系统身份解析、共享代码控制、持续匹配／合并／拆分或权威发布时，才触发本技能。技能正文的“适用边界”明确给出这一负向判定，故边界测试通过。

## 缺口判定

| 级别 | 数量 | 依据 |
|---|---:|---|
| P0 | 0 | 未发现错误主责；明确禁止把未决候选发布成权威事实，并设置误合并、可逆性与消费者 No-Go |
| P1 | 0 | 身份、属性权威、匹配、拆分、参考版本、管家和分发对账均有可操作的决策结构 |
| P2 | 0 | 十周场景所需的补充数值和源事实须在项目中由 owner 批准，技能已给出字段、测试、阶段门与证据结构；这属于正常项目裁剪，不是技能缺口 |

**评估限制：** 这是基于静态技能材料的独立情境应用评测，未接入真实 CRM、计费或客服样本，也未实测匹配算法。上述来源优先级和阈值是可审批方案，不声称已反映该企业事实。GREEN 证明技能能引导正确的项目决策和验收设计，不等于真实数据已达标。
