# 客户/订单域可实施数据模型：四周 RED 基线方案

## 1. 目标、成功条件与边界

四周的目标不是“一次性统一全公司所有数据”，而是为一组已确认的高价值用例，交付一套能够进入开发、测试和治理流程的客户/订单域模型。它必须回答：核心术语是什么意思，数据以什么粒度记录，CRM、订单系统和计费系统各自对什么事实负责，冲突客户标识如何关联，源字段如何映射到目标字段，以及模型变化后由谁批准。

优先用例建议限定为：客户 360、订单履约分析、订单到开票/回款对账，以及按客户统计收入或订单金额。启动会上由业务赞助人最终排序。若某个用例没有明确的决策动作、用户、刷新频率和质量要求，不纳入首期承诺。

四周完成的定义包括：概念模型和术语表已由业务签署；逻辑模型覆盖优先用例；首期物理模型能在指定平台落地；三套源系统至目标模型的字段级映射、转换规则和血缘可执行；客户身份匹配规则有置信度、人工例外和不可匹配处置；代表性数据通过质量、对账、性能和安全验收；未决事项、假设与后续范围透明登记。

首期通常不承诺：替换 CRM/订单/计费系统；建设完整企业级 MDM；清洗全部历史数据；统一所有财务会计口径；覆盖退货、订阅、渠道、跨法人等全部例外；直接修改源系统标识；以分析模型反向承担交易系统职责。它们若是优先用例的硬依赖，应进入风险与后续路线图，而非默认为已经解决。

## 2. 首周需求澄清：从一句口号变成可验证需求

### 2.1 需要参加的人

访谈和工作坊至少覆盖：业务赞助人，销售运营/CRM 产品负责人，订单运营负责人，计费/财务负责人，客户主数据或数据治理负责人，数据架构师/建模师，三套源系统的数据所有者和技术 SME，数据工程、分析/报表、安全隐私、测试与运维代表。客户、订单、收入定义发生跨部门冲突时，不能由建模师自行裁决，必须有具名的业务决策人。

### 2.2 将模糊需求拆成问题清单

围绕实际决策而非“想看什么字段”提问：

- 谁会使用统一模型做什么决定？错误、延迟或重复分别会造成什么后果？
- “客户”指潜在客户、签约主体、付款方、收货方、使用方、集团母公司还是其某种组合？一个法人可否有多个账户，一个账户可否关联多个法人？
- B2B 层级如何表达：全球集团、法人、业务单元、站点、联系人、合同账户分别是什么关系？层级是否需要按时间保存？
- “活跃客户”“新客户”“流失客户”的事件和时间窗口是什么？以 CRM 状态、有效合同、订单还是发票为准？
- “订单”是在提交、接受、履约、开票还是付款时成立？草稿、报价、取消、部分履约、改单、拆单、合单、退货和贷项如何处理？
- 分析粒度是订单头、订单行、履约行、计费行还是事件？数量、金额、税、折扣、运费和币种分别在哪个粒度可相加？
- 订单系统与计费系统是一对一、一对多还是多对多？预付款、分期开票、汇总开票和贷项怎样关联原订单行？
- 哪个系统对客户名称、法律主体、销售归属、订单状态、履约事实、发票金额分别是权威来源？当权威来源缺失或迟到时采用何种临时值？
- 各系统客户 ID 是否稳定、可复用或会合并/拆分？是否存在税号、注册号、D-U-N-S、合同号、邮箱或地址等辅助匹配属性，其合法使用范围是什么？
- 历史追溯到何时，日更还是近实时，允许多大延迟；更正历史时是覆盖还是保留版本？

每项需求用统一模板记录：需求 ID、业务问题、使用者、对象与粒度、业务定义、维度/指标、过滤条件、事件时间、期望时效、历史深度、质量阈值、安全分类、负责人、优先级、验收方法和状态。将口头冲突转成带截止日期的决策项，而不是在模型中偷偷选择一种解释。

### 2.3 最小业务定义样例

在建模前至少就下列概念形成“术语卡”：客户、客户账户、法人、客户层级、订单、订单行、订单版本、履约、发票、发票行、取消、退货、净订单金额、开票金额、交易币种、记账币种。每张卡包含业务定义、包含/排除项、例子与反例、计算或识别规则、权威负责人、来源、有效日期和版本。尤其要明确“订单金额”是下单时快照、当前有效金额还是履约/开票金额；三者不得共用一个含糊字段。

## 3. 分层建模策略

三层都需要，但深度不同：先用概念层完成业务裁决，再用逻辑层固定语义与粒度，最后只对首期范围做可部署的物理层。直接从源表拼一个“统一大宽表”会固化三套系统的冲突，也无法处理多对多和历史变化。

### 3.1 概念模型：对齐业务语言和责任

建议的核心概念包括：Party/法人或组织、Customer Account/客户账户、Party Relationship/组织关系、Source Customer Identity/源客户身份、Customer Identifier/业务标识、Contact、Address、Order、Order Version、Order Line、Product/Offer、Fulfillment、Invoice、Invoice Line、Payment（若首期用例需要）、Currency，以及 Order-to-Invoice Allocation/订单行与计费行分摊关系。

概念模型只展示稳定的业务实体、关键关系、基数和责任边界，不塞入所有源字段。需要特别标示：一个 Party 可在多个系统拥有多个 Source Identity；客户账户与 Party 不一定一一对应；订单头包含订单行；订单行与发票行可能通过分摊桥表形成多对多；层级关系和账户归属可能具有有效期。

### 3.2 逻辑模型：固定粒度、键、历史和业务规则

每个实体都必须写明一句粒度声明，例如“每条记录代表某业务订单在一次已接受修订下的一条订单行”。同时定义自然键候选、企业代理键、唯一性、必填性、关系基数、状态枚举、金额/数量的可加性、币种和时间语义。

客户统一不等于删除源 ID。保留 `enterprise_customer_id`（或 party/account 的企业键）以及 `(source_system, source_customer_id)` 交叉引用。身份解析规则按可靠性分层：经治理的外部/法定标识精确匹配优先；受控主数据映射次之；名称、地址等模糊匹配只生成带置信度的候选。记录规则版本、证据、置信度、生效时间和人工裁决者。低置信度不自动合并；错误合并必须可拆分；一个源身份到企业客户的归属需要时间有效性和完整历史。

订单模型区分业务订单号、源记录键、订单版本和订单行键。状态使用规范状态加源状态映射，并保留状态事件或至少保留有效期，避免用当前状态改写历史。`created_at`、`submitted_at`、`accepted_at`、`fulfilled_at`、`invoiced_at`、`updated_at` 分开；事件时间、源提交时间、平台摄取时间也不混用。金额包含数值、币种、汇率类型/日期和税前税后语义。发票与订单通过明确分摊关系连接，不能因号码相似就假设一一对应。

逻辑模型还应包含：软删除和撤销语义；迟到与更正数据；生效/失效时间；源记录版本；审计字段；敏感字段分类；参考数据及代码映射；未知、不适用、尚未提供等不同空值语义。客户属性若需要“当时视角”和“当前视角”，明确采用双时态、有效期维度或事件历史中的哪一种。

### 3.3 物理模型：首期可执行，不越过平台事实

第 3 周在已知目标平台、查询方式、数据量和刷新要求后才冻结物理设计。物理产出包括表/视图、列和数据类型，主外键或等效约束，唯一性与空值规则，分区/聚簇或索引，增量装载键，CDC/删除处理，历史策略，命名规范，访问控制，敏感列处理，数据保留，以及面向消费的稳定视图。

建议把源保真层、标准化核心层和消费语义层分开：源保真层保留原始标识与摄取元数据；核心层实现企业键、规范关系和历史；消费层按用例提供易用视图及明确指标。环境、引擎和工作负载未知时，不应凭空指定某种分区、索引或范式；先记录物理假设，并用代表性数据基准测试后定型。

## 5. 可追溯性与模型制品

建立一张双向追溯矩阵，使任何字段都能向上解释业务需要、向下定位实现和测试。最小链路为：

`业务目标 → 用例 → 需求 ID → 术语/规则 → 概念实体 → 逻辑实体.属性 → 物理表.列/视图 → 源系统.表.字段 → 转换/匹配规则 → 质量规则 → 测试用例与结果 → 审批/版本`

追溯矩阵还记录数据所有者、敏感级别、权威来源和生效版本。对于派生字段，要保存公式、过滤条件、时间窗口、币种转换和空值规则；对于同一目标字段来自多个系统的情况，要记录优先级、冲突检测及回退规则。自动血缘可作为证据，但不能替代业务定义和人工系统间映射。

模型包统一版本化，包含：图形模型与机器可读定义、数据字典、术语表、源到目标映射、代码集、身份解析规则、质量规则、测试数据与结果、ADR/决策日志、评审纪要、开放问题和发布说明。图、字典、DDL 与映射必须由同一版本号关联，防止“图已更新而实现未更新”。

## 6. 评审机制与决策权

安排四类评审，避免一次大会议承担所有目的：

1. 业务语义评审：业务负责人确认定义、粒度、状态、包含/排除项和层级关系。
2. 数据/模型评审：建模师、治理与系统 SME 检查规范化、键、基数、历史、身份解析、参考数据和可追溯性。
3. 工程与运行评审：工程、平台、测试和运维检查可装载性、增量/重跑、容量、性能、可观测性、恢复和成本。
4. 安全与合规评审：确认分类、用途、最小化、权限、脱敏、留存、跨境和审计要求；法律结论由法务/隐私负责人作出。

每次评审使用场景化走查而非只看框线：客户合并后又拆分；一个集团多个法人；订单多次改单；部分取消和部分履约；一行订单拆成多张发票；多行订单汇总开票；贷项晚到；客户属性回溯更正；源系统删除后重放。意见分为阻断、应修复和建议，均有责任人、截止时间、处置结论。跨域争议升级给数据治理委员会或赞助人，架构师负责提出选项与影响，不拥有业务口径的最终决定权。

## 7. 变更、版本与发布控制

基线签署后，任何模型变更提交变更请求，至少说明：触发需求、受影响术语/实体/字段/接口/报表、兼容性、历史回填、隐私与质量影响、迁移和回退方案、测试及发布日期。使用语义版本或等效规则：新增可选属性通常为向后兼容的小版本；改粒度、键、含义、单位、状态语义或删除字段属于破坏性大版本。

对破坏性变更提供并行版本和弃用期，通知已登记消费者，收集迁移确认后再下线旧版本。源系统 schema 漂移由自动检测告警，但只有经过影响分析和批准才能改变规范模型。紧急修复仍需事后补录决策、血缘和测试证据。模型、代码、映射、质量规则与文档应在同一发布流程中保持一致。

## 8. 验收标准与证据

验收阈值要在第 1 周根据风险和数据剖析确定，下面是建议结构而非未经验证的承诺：

- 覆盖性：首期 P0/P1 需求 100% 有追溯链；核心实体/属性 100% 有定义、粒度、所有者和来源；未实现需求均有批准的延期决定。
- 客户身份：精确规则的查准率、查全率或覆盖率达到约定阈值；自动模糊合并的误并率低于风险阈值；低置信度进入待裁决队列；所有合并/拆分可审计、可重算。
- 数据质量：关键字段完整性、唯一性、引用完整性、代码合法性及时效满足分级阈值；质量规则同时给出分母、容忍值、告警和处置责任人。
- 财务/订单对账：按日、客户、订单/行和币种核对订单、履约、发票与贷项；数量和金额差异在约定容差内，差异可分类并追到源记录。金额不能只用总和相等来掩盖错配。
- 历史与增量：新增、更新、删除、迟到、更正、重跑和幂等测试通过；指定时点能够重建当时的客户归属和订单状态。
- 性能与运行：以代表性数据量验证刷新窗口、典型查询响应、并发、成本或资源上限；失败可重试，运行有监控、血缘和责任人。
- 安全：敏感字段分类完整，角色访问与拒绝用例通过，非生产数据受控，访问和身份匹配决策留有审计记录，留存/删除规则可执行。
- 可用性：业务用户使用发布视图复现约定样例报表，数据工程团队可依据模型包独立建表和装载；业务、数据、工程、安全分别签署其责任范围。

验收证据包括测试数据版本、查询或校验脚本、结果快照、差异解释、缺陷关闭记录、性能报告、权限测试、评审纪要和签署记录。不得仅以“ER 图已完成”或“样例看起来正确”验收。

## 9. 角色与责任

| 角色 | 主要责任 | 关键决策 |
| --- | --- | --- |
| 业务赞助人 | 确认价值、范围、优先级和资源；解决跨部门阻塞 | 接受范围变化和残余风险 |
| 客户/订单/计费业务数据所有者 | 定义术语、规则、质量与权威来源 | 对本域语义和验收签字 |
| 数据治理委员会/数据负责人 | 管理共享术语、企业键、标准、例外与跨域争议 | 裁决跨域口径和长期所有权 |
| 数据架构师/建模师 | 主持澄清；设计三层模型、粒度、键、历史和追溯 | 提出设计选项并维护模型基线，不代替业务裁决 |
| 源系统 SME/所有者 | 解释源语义、变更、质量和抽取限制 | 确认源到目标映射与权威事实 |
| 数据工程/平台 | 验证物理可行性，实现装载、血缘、监控与性能 | 确认实现、运行和成本约束 |
| 数据质量/测试 | 设计规则、金样本、回归和对账 | 给出独立测试结论 |
| 安全、隐私、法务 | 分类、用途、访问、保留与法规评估 | 对控制与合规要求签署 |
| 数据消费者/分析负责人 | 验证可理解性和用例结果 | 确认消费视图满足使用场景 |

每个关键实体、术语、规则和质量问题只能有一个明确 accountable owner；“数据团队共同负责”不构成可执行责任。

## 10. 交付与运行指标

项目推进指标：已澄清并签署的 P0/P1 需求比例；已裁决核心术语比例；有完整追溯链的模型元素比例；评审阻断项数量和平均关闭时长；映射完成率；按计划通过质量关口的制品比例；未经批准的范围变更数量。

模型质量指标：存在粒度声明、主键/唯一性和所有者的实体比例；有业务定义和来源的关键属性比例；孤立关系、重复术语、无消费者字段及破坏性变更数量；DDL、字典、映射版本一致率；测试覆盖率。

数据结果指标：客户匹配覆盖率、准确率、误并/漏并率、待人工裁决量及老化时间；重复客户率；订单头—行、订单—履约、订单行—发票行引用完整率；未映射状态/代码率；订单与计费金额/数量对账差异率；迟到数据率；刷新 SLO 达成率；关键质量问题恢复时间。

价值指标需与首期用例绑定，例如客户 360 人工拼接时间、订单到开票对账耗时、争议订单数量、报表间口径差异或结账调整量的变化。四周项目先建立基线和测量方法；没有当前基线时，不虚构改善百分比。

## 11. 关键边界与设计原则

- 规范模型不是源系统的逐表并集，也不是专供一个报表的宽表；源语义保真、规范核心和消费语义各司其职。
- 企业客户 ID 是受治理的关联层，不抹去源标识，也不自动证明两个客户就是同一法律主体。
- 订单、履约、发票、回款是不同业务事实；任何“订单收入”指标必须明确采用哪一事实和时点。
- 客户身份解析的技术模型不能替代业务/法务对法人、账户和集团关系的定义。
- 分析模型不写回交易系统，除非另有独立、获批的主数据运营流程。
- 四周内优先交付一个端到端可验证薄切片；广而浅但无法装载、对账和演进的模型不算可实施。

## 12. 容易遗漏的要点

1. 客户“同一性”与客户“集团层级”是两个问题：两个账户可属于同一集团，却不应被合并为一个客户记录。
2. 客户合并、拆分和层级调整需要时态、血缘与可逆性；只保存当前交叉引用会污染历史订单归属。
3. 联系人通常是个人数据，不能直接当作 B2B 客户主键；模糊匹配还涉及用途限制、误合并和人工复核权限。
4. 订单号可能只在法人、渠道、年份或源系统内唯一；显示编号不能未经验证直接作为企业主键。
5. 订单修改可能覆盖原记录，也可能生成版本；不识别源系统行为就无法重建“下单时”和“当前”的差异。
6. 取消、退货、退款、贷项、补开发票是不同事件；负金额不能自动代表同一种业务含义。
7. 一订单多发票、多订单一发票、部分履约和分摊舍入会破坏简单一对一连接，必须有桥接与分摊规则。
8. 多币种模型必须保存原币、金额口径、汇率类型/日期和舍入规则；仅存换算后金额无法审计。
9. “客户名称”“销售区域”“行业”等属性会随时间变化；报表究竟看当前属性还是交易发生时属性要显式选择。
10. 时区、夏令时、业务日截止时间、事件时间与摄取时间常导致日级对账假差异。
11. 空值要区分未知、不适用、未采集、被遮蔽和源系统错误，不能用一个默认值吞并。
12. 测试数据若只取“干净样本”会掩盖真正冲突；应分层抽取正常、边界、异常和高价值客户，并记录抽样偏差。
13. 指标总额相等不代表记录正确，错误匹配可能相互抵消；必须同时做记录级、分组级与总量级对账。
14. 源系统下游存在未登记消费者和手工 Excel 导出；变更通知、弃用期与消费者登记容易被遗漏。
15. 参考数据、状态码和产品/币种映射也需要版本与所有者，否则统一实体后仍会出现口径冲突。
16. 历史回填、重算、模型重版本和算法升级时如何保持可重复结果，常晚于首发才被发现。
17. 权威来源可能按属性和生命周期阶段不同，不能简单宣布“CRM 是客户真源、订单系统是订单真源”。
18. 数据许可、合同限制、保留删除、跨境位置和非生产复制要在模型设计阶段落实，而不是上线前补审批。
