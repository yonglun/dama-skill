# organizing-data-management：RED 基线

## 测试条件

- 执行者没有读取或调用未来的 `organizing-data-management` 技能；以下先按通用数据管理经验直接回答场景，再做 DMBOK 第 16 章复盘。
- 正向场景：集团三个事业部、多个地区，数据团队分散。集团要统一关键数据标准和跨域决策；产品团队担心中央组织拖慢交付。10 周内提出可实施运行模式，人员不能大幅增加。
- 负向场景：组织结构已确定，只缺一项数据定义的决策及争议规则。

## 未使用专属技能时的实际交付

建议采用**联邦式数据管理**：集团保留少量跨域规则和仲裁能力，事业部及地区保留产品交付与日常数据责任。中央团队尽量由现有架构、质量、平台和治理人员兼职组建；不把所有项目审批集中到集团。集团只处理跨域定义、共享主数据、重大质量风险与例外；单一产品范围内的设计由产品团队决定。

组织设置如下：

| 层次 | 主要职责 | 会议节奏 |
| --- | --- | --- |
| 集团数据委员会 | 确认优先级、关键标准、跨域争议与投资 | 每月一次；紧急争议异步表决 |
| 业务数据 owner | 对客户、产品等领域定义和质量目标负责；批准重大例外 | 每两周跨域碰头 |
| 数据管家 | 整理术语、规则、质量问题和变更请求，推动业务确认 | 随产品迭代工作 |
| 集团架构、质量、平台小组 | 提供公共模型、质量检查方式、目录和共享平台能力 | 每周办公时间与按需咨询 |
| 事业部和地区产品团队 | 实施本域规则，提交跨域影响，记录例外和证据 | 纳入现有迭代节奏 |

决策流程：提出议题后由管家说明影响和选项；本域事项由业务 owner 决定，跨域事项提交集团数据委员会。委员会应在五个工作日内给出决定或指定临时规则，避免阻塞产品发布。未达成一致时由委员会主席裁决，并将决定写入术语与决策记录。重大监管或客户影响由法务、合规或安全职能介入。

**10 周实施安排：**第 1–2 周访谈三个事业部和地区负责人，盘点现有角色及高频争议；第 3–4 周起草组织章程、关键角色说明、议题分级和审批时限；第 5–6 周选客户、产品两个跨域主题试运行；第 7–8 周把决策记录、数据标准和质量工单接入现有工具；第 9–10 周复盘处理时长、争议关闭率与产品反馈，调整会议范围及职责，并形成下季度推广计划。交付物包括组织图、章程、角色清单、决策流程、首批标准、试点台账和指标看板。

人员及经费：先由各事业部各指定一名兼职业务 owner 和一名管家，集团现有架构、质量与平台骨干组成虚拟共享服务；预算由集团负担共性目录和培训，由事业部负担本地实施。第一阶段不增加编制；若试点积压超出兼职人员承受能力，再在季度预算中申请专职协调岗。用标准采用率、争议解决时长、重要质量问题数量和产品团队满意度衡量运行效果。

**负向场景判断：**既有组织结构已确定，仅一项数据定义缺少决策与争议规则，应由 `establishing-data-governance` 主导，明确业务 owner、决策权、升级时限与记录方式。无需启动完整组织模式重设计。

## 对照 DMBOK 第 16 章后的自评

核对范围：附件 PDF 第 525–543 页（书内第 521–539 页），第 16 章“Data Management Organization and Role Expectations”。下表评价的是上面的原始回答，不把复盘建议倒填到回答中。

| 检查点 | 原回答 | 具体缺口与后果 |
| --- | --- | --- |
| 现状与参与者图（§2、§5.1，PDF 525–526、535） | 部分 | 只计划访谈与盘点角色，没有可交付的现状图：谁实际创建/维护/使用关键数据、谁作决定、已有委员会和汇报线、各地区的自治程度、现有技能和文化阻力均未落图。直接指定新委员会和兼职角色，可能覆盖已经有效的关系。 |
| 利益相关者分析（§4.6、§5.2–5.4，PDF 534、536–537） | 遗漏 | 提到了产品团队担忧，却没有按影响力、受影响程度、目标、支持度和阻力分析事业部/地区负责人、IT、法务、财务、HR、客户等，也没有确定谁能提供赞助和关键资源、如何争取其参与。 |
| 五种模式的选择准则和比较（§3.1–3.7，PDF 527–532） | 遗漏 | 直接选联邦模式，没有逐项比较集中、分散、网络、混合、联邦，也未用现有决策方式、组织/数据域复杂度、成熟度、地区独立性、扩展性和可用编制给选择打分。第 16 章明确联邦模型层级多、协调复杂；在不能明显增员的条件下，可能应先验证网络化责任制或轻量混合模式。 |
| 正式授权与委员会章程（§3、§4.1、§5.2，PDF 527、532–533、536） | 部分 | 列出了委员会职责、节奏和时限，但没有执行赞助人、委员席位和代理、授权来源、法定人数/决策规则、保留事项、会议输入输出及章程审批。所谓“主席裁决”缺乏已授权的主席和约束范围。 |
| RACI 与角色边界（§3.2、§6–7，PDF 528、537–543） | 部分 | 列出 owner、管家、架构、质量、平台和产品团队，却没有对标准制定、例外批准、质量问题关闭、共享服务请求、地区差异审批、预算等活动明确唯一 A、R/C/I，尤其集团委员会与业务 owner 的边界可能冲突。 |
| 交互与升级（§3、§6，PDF 527、537–540） | 部分 | 提出五日决定或临时规则，但没有议题入口、跨域影响判断、工作组与委员会的分工、架构评审会与质量团队的接口、超时和不同意裁决的二次升级、决定向地区和产品团队传播/执行的验证。 |
| 技能与容量（§2、§5.1、§7，PDF 526、535、541–543） | 部分 | 提议兼职复用现有人，但未估算每周议题量、各角色可用工时、主持会议和维护标准的容量、备份人和岗位能力差距；未设计按角色培训。若试点积压才申请人，可能已经造成交付延误。 |
| 资金、绩效与采用（§4.7–4.8、§5.1，PDF 534–535） | 部分 | 粗分集团与事业部预算，列出四个指标，却没有共享服务的费用分摊依据、预算拥有者/审批规则、兼职工作在绩效目标中的权重、指标基线与目标值，以及用实际采用和业务结果决定扩展的证据。 |
| 分阶段转换（§3.7、§4.10，PDF 531–532、535） | 部分 | 给了 10 周活动表和下季度推广意向，但没有从现状到网络/混合/联邦的过渡状态、试点退出/扩面门槛、模式重选触发条件或回退方式。第 16 章强调组织应随成熟度渐进演化。 |
| 负向场景路由 | 满足 | 对单项数据定义争议，将工作交给数据治理，避免组织模式重设计，符合问题边界。 |

**RED 结论：**原回答可作讨论草案，但“联邦式”选择没有基于现状证据和五模型比较；人数和预算也没有容量验证。它无法直接作为 10 周可实施、可授权和可考核的组织运行方案。后续技能的 GREEN 测试应要求出现现状/参与者图、明确的模式比较及选择理由、授权章程与活动级 RACI、交互升级、容量/资金、分阶段转换条件，并保持负向场景路由正确。
