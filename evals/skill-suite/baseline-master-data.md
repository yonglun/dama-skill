# Scenario B：客户主数据质量整改（十周项目方案）

## 1. 目标、范围与假设

**业务目标。** 在十周内把 CRM、计费、客服三个系统中可识别为同一客户的重复记录显著下降，并把地址、客户状态、国家代码的质量问题从“一次性清洗”转为可预防、可监控、可追责的日常机制。项目成功不只以删除记录数衡量，而以关键指标改善、源头录入控制启用、问题可以闭环为准。

**量化目标（第 1 周锁定基线后确认分母）。**

- 活跃客户的疑似重复率从基线降低至少 60%，且人工抽检的合并误判率低于 2%。
- 地址有效率达到至少 95%；无法自动验证的地址进入待补全队列，不能被静默改写。
- 国家代码采用唯一的 ISO 两位代码参考表，CRM、计费、客服三个系统合规率均达到 99.5% 以上。
- 三系统客户状态映射覆盖率 100%；映射后“状态冲突”（同一客户在适用系统具有互斥状态）低于 1%，其余必须有例外原因和责任人。
- 新增或修改客户记录在源头规则启用后，关键字段规则一次通过率至少 98%，未通过记录在一个工作日内进入可处理队列。

**范围。** 本期覆盖客户主记录及其姓名/组织名称、联系方式、地址、国家代码、状态、外部系统标识和合并关系；覆盖三套系统的存量治理、增量接口和前台录入。高风险的客户合并由业务人工确认，不在脚本中自动物理删除。项目建立“黄金客户标识”和跨系统交叉引用表；在十周内不强制替换三个既有系统。

**关键假设。** 三个系统可导出/调用客户变更数据并可配置校验或接入前置校验；业务能在两个工作日内裁决歧义合并；有合法的地址验证服务或受控参考地址库；客户记录的唯一性以约定的匹配规则和业务裁决为准，而非仅靠姓名相同。

## 2. 工作流、依赖与阶段门

| 阶段与周次 | 工作内容与依赖 | 阶段门（批准人） |
|---|---|---|
| 0. 启动（第 1 周） | 任命客户数据所有者、数据管理员和系统负责人；冻结指标口径、字段范围、优先级和例外升级路径。依赖业务负责人可投入裁决。 | 《项目章程、RACI、指标口径》获客户数据所有者批准；未批准不得批量处理数据。 |
| 1. 画像与设计（第 1–2 周） | 对三系统做数据剖析，测量重复、地址、国家代码、状态的基线；编制字段词汇表、系统/字段映射、现有接口和下游报表影响清单；定义匹配阈值、状态映射、国家代码参考表、保留与合并规则。依赖只读数据访问。 | 数据质量基线、匹配规则、状态映射和影响分析由数据所有者、隐私/安全代表、各系统负责人联合签署。 |
| 2. 构建与试运行（第 3–5 周） | 建立黄金客户标识和交叉引用表；实现标准化、候选重复评分、地址/国家码校验、状态冲突检测、例外工作队列和审计日志；在隔离环境使用抽样数据回放。依赖阶段 1 已批准的规则。 | 回放结果达到：规则覆盖约定字段 100%、合并建议抽检准确率至少 98%、无未授权字段暴露；变更评审批准后才可试点。 |
| 3. 试点整改与源头防控（第 6–7 周） | 选择一个客户业务单元试点；业务审核候选合并，按可回滚批次写回或建立交叉引用；在 CRM、计费、客服的新增/修改流程中启用国家码、地址、状态和查重控制。依赖可回滚备份和业务审核容量。 | 试点指标达到阶段性目标（重复率下降至少 40%、新增规则通过率至少 98%），且无 P1 业务中断，方可扩展。 |
| 4. 全量推广与交接（第 8–9 周） | 分批处理其余业务单元；发布数据目录、运行手册、例外处理和月度质量报表；培训一线录入人员、客服主管和数据管理员。依赖试点复盘关闭关键缺陷。 | 三系统负责人确认控制已上线；数据所有者确认剩余例外有责任人、完成日期和风险接受记录。 |
| 5. 稳定与验收（第 10 周） | 连续两周监控增量质量、抽检合并结果、演练异常回滚和队列升级；召开治理评审决定转入常态运营。 | 量化目标、验收证据、运行责任、未决风险均获签署；未达标项转为带日期的整改事项而非宣称完成。 |

## 3. 角色、责任与决策权

| 角色 | 责任 | 决策权 |
|---|---|---|
| 客户数据所有者（业务高管） | 对客户定义、质量目标、合并原则和风险取舍负责；主持周度治理会。 | 批准规则、阈值、例外风险接受、阶段门和范围变更；对跨部门争议作最终裁决。 |
| 客户数据管理员（业务运营） | 维护术语、状态映射、国家码参考表；审核低/中置信度候选，分配和关闭问题单。 | 可批准常规人工合并/拆分；超过阈值或政策例外升级给数据所有者。 |
| CRM、计费、客服系统负责人 | 提供字段和接口说明，实施本系统输入控制、发布和回滚。 | 对本系统技术变更、发布窗口和恢复方案签字；不能单方面改变跨系统标准。 |
| 数据工程/主数据团队 | 建立交叉引用、规则执行、监控、审计日志和报表；维护数据血缘。 | 提出技术方案并停止不满足质量/安全门的发布。 |
| 隐私与安全代表 | 审核访问、最小化、保留、地址验证供应商及审计要求。 | 对不符合访问或允许用途的处理拥有否决权。 |
| 一线业务与客服主管 | 试点、培训、反馈录入摩擦，确认业务例外。 | 对客户实际状态和疑似重复的业务事实提供裁决证据。 |

冲突处理：数据管理员在一个工作日内处理常规问题；跨系统冲突在两个工作日内提交客户数据所有者；涉及隐私/安全的事项立即暂停相关批次并由隐私与安全代表裁定。任何自动合并阈值、状态定义或访问范围的变更须经过变更评审并记录版本、理由、影响和批准人。

| 数据词汇表、字段目录、状态映射、国家码参考表 | 覆盖三系统范围字段 100%；每个字段包含定义、格式、所有者、来源系统、允许值和更新时间；三方系统负责人确认。 |
| 数据流与影响分析 | 图示从三源到交叉引用、质量规则、下游消费的字段级流向；列出受合并/状态变更影响的接口和报表，并由其负责人确认。 |
| 基线报告与质量规则库 | 每项指标有查询逻辑、分母、阈值、负责人、刷新频率；保存第 1 周基线和每周趋势；规则库含版本和测试结果。 |
| 黄金标识/交叉引用、匹配与合并工作流 | 每个合并建议可追溯至源记录、匹配依据、审核人、时间和撤销操作；抽样 200 个建议显示准确率至少 98%，且可完成回滚演练。 |

| 运行手册、仪表板、培训材料 | 仪表板按日显示四项核心指标及未处理例外；演练告警、恢复和升级；相关录入人员完成培训且测验通过率至少 90%。 |

## 5. 指标、风险、控制与升级

每日计算并在周度治理会上审阅：活跃客户疑似重复率、确认重复率、地址有效率、国家码合规率、状态冲突率、规则一次通过率、例外队列数量和平均处理时长、合并误判率。仪表板保留按系统和业务单元的切片，避免总体平均掩盖单一系统退化。

控制措施包括：

- **预防：** 前台格式/参考表校验、查重提示、状态转换规则、最小权限访问、变更评审；高风险合并必须双人复核。
- **侦测：** 每日增量质量扫描、每周抽检、规则失败告警、审计日志及对参考表修改的版本监控。
- **纠正：** 不合格记录进入带系统负责人和业务责任人的队列；可撤销的合并批次、处理步骤和复发原因分析。

升级阈值：国家码合规率低于 99.5%、状态冲突率高于 1%、新增规则通过率低于 98%、任何未经授权的客户数据访问、或合并误判率达到 2%，即在四小时内通知项目负责人和相应系统负责人；涉及隐私/安全时立即停止该数据流；连续两个工作日未恢复则由客户数据所有者在治理会上决定回滚、暂停发布或投入额外人力。

主要风险与缓解：姓名相近导致错合并，使用保守阈值、人工审核和回滚；历史地址无法验证，标记待确认而非伪造“有效”；状态语义不同，先批准映射和例外码再改数据；源系统改动影响业务，采用试点、发布窗口、备份和分批推广；人员绕过控制，培训并按队列和复发率向主管反馈。

运行承诺：质量扫描和告警每日运行；P1（数据泄露、错误批量合并、关键录入中断）4 小时内响应并在 1 个工作日内给出处置计划；P2（单系统阈值失守）1 个工作日内响应、5 个工作日内修复或获得风险接受。保留合并和参考表变更审计记录至少 24 个月；批量变更前保留可恢复快照，并在第 10 周完成恢复演练。

## 6. 变更与采纳

第 1 周召开三系统负责人、客户运营、客服、销售、隐私与安全的启动会，确认痛点和裁决代表；每周发布按系统的质量趋势、未决例外和即将变更；试点前向一线说明何时会被拦截、如何请求例外、谁处理队列。第 7–9 周对录入和客服人员开展角色化培训，提供一页操作指引和办公时间；上线后四周由数据管理员审查绕过率、培训完成率、队列 SLA 和用户反馈，将高频问题纳入规则或培训修订。治理会在项目结束后改为月度例会，持续拥有规则版本和指标审阅责任。

## 7. 明确不纳入本期

- **不替换 CRM、计费或客服平台，也不建设全企业主数据平台。** 十周窗口优先解决客户域的质量和源头控制；当客户域在连续三个月达到指标、且其他域有已批准业务案例时，再单独立项评估平台化。
- **不清洗客户以外的产品、供应商、员工等主数据。** 它们需要不同定义和所有者；本期仅交付可复用的治理模式和模板。
- **不自动合并所有重复客户，也不物理删除原始记录。** 误合并会影响账单、服务和合规证据；只有达到保守置信度且依规定完成审核的记录才处理，其余留在队列。
- **不追溯重写所有历史交易或重算全部经营报表。** 本期输出交叉引用和影响清单，保证未来消费可解析黄金标识；若财务或监管提出追溯要求，须另行确定会计、审计和回算范围。
- **不以地址质量为由擅自补全或改变客户联系信息。** 无法验证的记录进入待确认流程；取得客户确认或合法权威来源后才更新。
