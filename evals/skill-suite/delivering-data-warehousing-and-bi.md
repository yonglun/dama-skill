# `delivering-data-warehousing-and-bi` 独立 GREEN／边界评估

## 测试结论

**GREEN：无 P0、P1、P2 缺口。** 对高管销售仪表板，技能能产生从决策到已批准指标、原子事实、历史、装载、BI 发布和运行反馈的可验收链条。对单个 Kafka CDC 管道，能正确将主责交给 `integrating-data`。

本评估完整读取了 `skills/delivering-data-warehousing-and-bi/SKILL.md`、`references/playbook.md` 和无技能的 RED 基线 `evals/skill-suite/delivering-data-warehousing-and-bi-baseline.md`。下列内容是以测试场景执行技能后形成的代表性项目判定，不把手册中出现关键词本身当作通过证据。场景没有给出源字段、实际金额或已授权的业务裁决，因此字段映射、目标阈值和批准状态必须保持待核实，不能伪造为已签署。

## 测试 A：八周高管销售仪表板

**场景输入：** CEO 需要跨 CRM、订单、ERP、退货系统的销售仪表板；销售额、净收入、订单数、客户数和地区归属在财务、销售、运营之间冲突；源按小时或日刷新；历史退款、迟到更正、汇率和区域重组影响同比；需要钻取、导出、地区授权及财务月结对账。

### 1. 实际项目判定：从决策追到来源

首版应先确认 CEO 要用每个视图作什么决定。以下表是发现会使用的工作底稿，不代表指标已获批准；`源字段`需在第一、二周的来源画像中填入真实名称、版本和质量结果。

| 决策与行动 | 问题／候选指标 | 必须裁决的语义与粒度 | 候选来源→转换→语义→视图 | 验收人／证据 |
|---|---|---|---|---|
| 调整销售投入和目标 | 哪些地区的销售趋势偏离目标？销售额 | 订单／订单行粒度；支付、取消、折扣、税、退款、币种、事件日期；总额或净额 | 订单交易＋退货事件→原币原子事实和冲销→获批销售额版本→地区趋势／订单钻取 | 销售指标 owner；样本逐笔回溯、分组控制总额、计算式签署 |
| 判断已结业绩并对外解释差异 | 本月财务认可的收入是多少？净收入 | ERP 入账／凭证粒度；已结与未结、税、退款、冲销、汇率和财务期间 | ERP 入账与退货→财务期间和锁账版本→获批净收入→已结／未结分列 | 财务 owner；月结报表对账、已批准例外、锁账签署 |
| 识别转化和订单异常 | 订单量变化来自新增还是取消？订单数 | 下单、完成或已入账；取消、拆单、重复和状态回退；订单主键 | 订单状态历史→去重和状态规则→获批订单数→状态／渠道钻取 | 运营 owner 与销售协签；重复、撤销、状态边界测试 |
| 判断客户覆盖与留存动作 | 哪些客户群扩大或萎缩？客户数 | 下单客户、活跃客户或 CRM 客户；匿名／合并身份；观测窗口 | CRM 身份映射＋订单客户键→受控客户身份及时间窗→获批客户数→客户群趋势 | 客户／主数据 owner 与销售协签；跨源重复、合并拆分样本 |
| 分配区域预算与问责 | 业绩按哪个地区归属？地区归属规则 | 交易发生时地区、当前地区或双视图；客户／门店／销售员归属；组织变更生效时间 | CRM／组织地区层级＋订单／客户映射→版本化地区桥接／维度→当时／当前口径→地区同比 | 销售／财务共同授权的裁决机构；重组前后重算差异及批准版本 |

每个指标契约要存 ID、定义与排除项、来源权威、公式、粒度、时间与币种、允许过滤、历史政策、质量阈值、owner、版本、生效时间和批准记录。若销售额与财务净收入有不同业务用途，保留明确命名的两个口径；开发团队不能用同一“收入”字段替代两者。五项中的地区归属是共享归因规则而非简单数值指标，但同样需要批准，并与受影响指标和报表版本关联。

**首个阶段门：** 第一、二周内取得上述五项的业务裁决或明确未决范围。未批准的指标不得以“认证／集团统一”身份进入高管正式报表；可仅在标明限制的原型中讨论。每次规则变更生成新版本，并列出受影响历史、数据集、视图、导出和再批准人。

### 2. 历史、原子事实与一致维度

建议以订单行事件、退货／退款事件及 ERP 入账行作为可核对的原子事实，保留源键、业务事件时间、源更新时间、加载时间、原币金额、币种、汇率及规则版本。是否把拆单、退款、总账冲销合成某个分析事实，须按获批业务过程和可加性建模；不能先把所有金额汇总成月度地区表。客户、地区、日期、币种和产品使用一致维度或明确桥接；地区层级与客户归属保留生效区间，以便“当时地区”和“当前地区重述”作为不同版本查询。

财务已结和经营中的未结数要分开。财务锁账版本记录期间、锁账时点、批准人、控制总额和报表版本；锁账后的迟到退款／更正先进入待裁决差异队列。财务决定是本期冲销、追溯调整还是发布独立重述版本；获授权前不覆盖已发布已结数。汇率来源、日期、精度和是否重算也由财务批准。这样既能解释同比变化，也保留历史报表复现能力。

架构可采用不可变原始／暂存层、保留历史和源键的集成层、获批事实维度及销售集市、认证语义层、高管仪表板。小时级订单与每日 ERP 分别标实际水位、最近合格版本和已知缺口，避免把运营近实时数标成财务已结数。最终仓库／集市／ODS 组合需根据源时限、历史需求、权限、性能和现有资产评审，而非在未知平台条件下先锁定工具。

### 3. 装载、拒收与多周期业务验收

| 验收层 | 代表性证据 | 失败处理与责任 |
|---|---|---|
| 源→暂存 | 每源批次／CDC 水位、文件清单、行数、金额控制总额、schema 版本、到达时间 | 缺批、重复、关键字段或 schema 不兼容隔离；源 owner 与集成 owner 处理 |
| 暂存→历史 | 源键唯一、订单状态历史、退款关联、币种与地区代码、生效时间、拒收清单 | 拒收保留原始值、规则、批次、责任人和补载状态；不得静默丢弃 |
| 历史→事实／维度／语义 | 订单／退款／入账按日期、地区、币种、财务期间的数量与金额；维度覆盖；指标重算差异 | 对照**来源业务控制清单**，而非只对相邻层；超获批容差阻断发布 |
| 语义→仪表板／导出 | 指标版本、过滤／钻取、行列级权限、导出权限、刷新标签、p95 响应 | 未授权地区访问、缓存／导出绕过权限、数值不一致即阻断 |

八周验收路线可为：第 1—2 周决策／语义裁决和来源画像；第 3—4 周原子事实、一致维度及历史／锁账设计；第 5—6 周装载、分层对账、认证语义和仪表板；第 7 周初装及至少多个小时和每日刷新周期的业务 UAT，并用历史已结月份的回放覆盖锁账／退款／汇率；第 8 周发布、培训和服务接管。实际刷新和月结日期若不落在窗口内，应使用已结历史回放并标明与真实月结运行的剩余风险，不能声称已经观察到未来月结。

UAT 抽取正常与风险样本，逐笔从视图反查语义版本、事实、转换和原始源；覆盖已结／未结、迟到退款、重跑、汇率、区域重组、地区权限、导出和恢复。每轮保留批次、源控制数、差异单、修复／批准、业务签收和最近合格发布版本。关键口径未批、财务对账失败且无获批例外、源缺口未知、权限负测失败或无恢复路径，均为 No-Go。

### 4. BI 发布、自助与运营

首版高管视图只取获批指标与必要钻取。语义数据集需有认证状态、指标版本、血缘、质量、权限、owner 和新鲜度；报表发布单记录 UAT、受影响消费者、权限测试、培训、回滚和支持联系人。个人沙箱可做标记为未认证的探索；团队共享仅可在允许的认证字段及派生规则内进行；新口径、跨域连接和正式报表需走业务／安全评审，不能从沙箱直接提升为集团口径。地区限制对图表、钻取、订阅、缓存和导出一致生效。

服务单应为订单小时刷新与 ERP 每日刷新分别填来源到达、合格发布、数据新鲜度、失败升级；另填仓库／报表可用性、p95 查询、故障响应／恢复、服务时段和支持队列。目标数值先测基线并由产品／运行 owner 批准。运营看板按测量点、窗口、分母和 owner 追踪刷新达标、对账差异、拒收老化、权限事件、活跃高管／分析师、实际查询／订阅、目标决策任务完成率、用户满意度和业务行动。上线后定期复盘低使用视图、反馈与需求队列，而非只计报表上线数。

### 测试 A 的可验收性判断

上述四段可以直接转成需求追溯表、五份指标／归因契约、事实与维度评审、历史／锁账决议、分层对账与拒收记录、UAT 签收、发布单和运行服务单。技能给出了这些交付槽位、决策权、异常路径和 No-Go 条件，因此不是只在正文里提醒“注意口径／质量”。**通过。**

## 测试 B：单个 Kafka CDC 管道

请求仅为可靠捕获订单变更并送至下游，不含分析数据产品、共享指标或报表。正确主责是 `integrating-data`：定义生产／消费契约、事件顺序与幂等、schema 演进、水位／延迟、重放、死信和交付 SLO。此时不应额外建设事实维度、认证语义、仪表板或 BI 发布流程。`delivering-data-warehousing-and-bi` 正文明确该分流条件，并在手册依赖段把接入、重放和技术对账交给集成技能。只有下游再提出历史分析集市、指标或报表，才并行启动 DW/BI 交付。**负向路由通过。**

## 与 RED 基线的逐项差异

| 检查点 | RED 实际输出 | GREEN 实际执行证据 | 结果 |
|---|---|---|---|
| 决策→指标→源追溯 | 有五项指标，却没有 CEO 的决策／行动链 | 上表逐项连接行动、问题、语义粒度、候选源、变换、视图、验收人；真实字段留待画像 | 改进并通过 |
| 五项争议业务批准 | 财务只确认月结净收入，其余口径未有正式签署 | 五项分别设裁决与批准人、版本、生效期、适用范围；未决不得认证发布 | 改进并通过 |
| 锁账与历史重述 | 知道保留地区历史、汇率和重算版本，但财务锁账路径粗 | 已结版本冻结；迟到更正进入差异队列，由财务选择冲销、追溯或新重述版，保留当时／当前地区视图 | 改进并通过 |
| 原子事实和一致维度 | 提了订单明细及客户／地区维，但缺粒度、可加性和源键约束 | 订单行、退款和入账原子事实保留源键／时间／原币；一致维度、有效期、桥接、可加性纳入模型评审 | 改进并通过 |
| 分层装载／拒收／多周期验收 | 加载校验和并行月结，缺源控制数及多层证据 | 四层源基准对账、隔离／补载责任、多个小时／日周期 UAT、历史月结回放与业务签收 | 改进并通过 |
| 认证语义／自助发布 | 有 UAT、权限与导出，缺认证和自助边界 | 认证状态与发布门；沙箱、团队共享和正式报表分别限定派生、连接、导出和审批 | 改进并通过 |
| SLA／支持／采用／满意度 | 日常故障检查和联系人，缺衡量与反馈机制 | 分源新鲜度、p95、故障响应／恢复、支持时段、使用／任务完成／满意度与定期复盘 | 改进并通过 |
| 单 CDC 负向触发 | 已正确分流 | 继续由 `integrating-data` 主导，DW/BI 无额外建设要求 | 保持通过 |

## 缺口分级

| 级别 | 发现 | 判断 |
|---|---|---|
| P0 | 无 | 财务锁账、权限、来源缺口和关键指标未批准都有发布硬门。 |
| P1 | 无 | 决策到数据、模型、装载、业务签收、发布与运行均有可交付槽位。 |
| P2 | 无 | 场景缺真实字段、平台和阈值；保持待画像／待批准是正确行为，不属于技能缺口。 |

最终判定：**GREEN，无阻断项。**
