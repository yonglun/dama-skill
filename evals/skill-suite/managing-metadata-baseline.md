# RED 基线：跨系统报表口径与血缘

## 测试条件

- 在 `managing-metadata` 技能创建前独立作答；未读取或使用该技能，也未修改任何技能。
- 场景：三份关键经营报表的“净收入”和“活跃客户”不一致；链路涉及 CRM、ERP、订单、退款、批任务、SQL、BI 语义层；目录仅有表名，脚本和运行版本与设计文档不一致。六周内建立最小可用目录与字段级血缘，以支持变更影响分析和审计追溯。
- 以下“实际回答”先于后面的自评形成；自评没有补写到实际回答。

## 实际回答（未使用专属技能）

我会把范围锁定在三份报表及两个争议指标，先解决口径与责任，再沿实际计算链路做最小目录和血缘。第六周的验收不是“目录里有多少表”，而是审计人员能从报表指标追到来源、负责人和计算逻辑；改动一处字段或规则时，团队能列出受影响的报表并让业务负责人确认。

第一周与财务、销售、运营、报表开发者一起核对三份报表。记录每份报表的用途、发布时间、使用者、负责人与两个指标的现有公式和差异实例。将“净收入”拆出订单、折扣、退款、税费等处理口径，将“活跃客户”写清身份合并规则、活动事件与时间窗口。对冲突口径建立决策单，由业务负责人批准一个适用范围明确的标准定义；不把历史报表的旧口径静默改写。

第二周盘点 CRM、ERP、订单、退款到批任务和 BI 的相关表、字段、作业与语义层指标。每个目录条目至少记录名称、说明、来源系统、负责团队、更新时间、敏感级别、关联指标和上游/下游。先筛出支撑两项指标的字段，避免六周项目扩展为全公司的资产普查。

第三至四周由数据工程师读取生产作业配置、SQL、调度依赖和 BI 指标定义，绘制字段到字段的映射。对脚本无法自动解析的转换，由开发者标注连接键、过滤条件、聚合与退款抵扣规则；把人工确认的部分标成“待核实”或“已确认”。逐一用订单和退款样本复算两项指标，与三份报表的结果对账，记录差异、修复负责人和处理期限。

第五周建立变更流程：报表或上游字段变更申请必须附上受影响链路、两项指标的对账结果、业务负责人确认、发布日期及回退办法。选择一项真实的上游字段或计算规则变更做演练，从目录检索下游报表并形成影响清单。

第六周向审计和业务展示交付物：指标定义与审批记录、相关资产目录、两项指标的字段映射图、三份报表的差异与复算记录、变更影响演练、未解决问题清单。抽样选一个“净收入”和一个“活跃客户”报表数值，让非开发人员按证据链追到源字段和 SQL。验收时要求两项指标都有明确业务负责人，三份报表的差异要么消除，要么有已批准的适用口径及解释。

## 回答后自评：DMBOK 第 12 章维度遗漏

| 维度 | 实际回答覆盖 | 具体缺口 |
| --- | --- | --- |
| 业务、技术、运行元数据 | 部分 | 写了指标定义、表字段、作业和更新时间；没有为业务、技术、运行元数据分别定义必备属性、关系和责任人，也没覆盖运行状态、作业实例、失败记录、实际执行版本。 |
| 来源与消费需求 | 部分 | 提到系统盘点与三份报表使用者，但没有正式的生产者/消费者需求收集、查询用例、优先级和服务水平。 |
| 仓库/联邦架构 | 遗漏 | 只说“目录”，没有选择集中仓库、联邦检索或混合架构，没有说明跨平台标识、同步和查询边界。 |
| 采集与人工策展 | 部分 | 提到读配置/SQL及人工确认，未设计连接器、采集频率、人工策展队列、冲突解决和审批规则。 |
| as-designed 与 as-implemented | 部分 | 识别设计文档与运行版本不一致，但没有定义两种视图、差异检测、事实优先级及持续对齐机制。 |
| 字段级血缘证据 | 部分 | 有字段映射图与复算样本，却未指定每条边要绑定 SQL/作业版本、执行时间、解析方法、证据位置、验证人及可信度。 |
| 影响分析 | 部分 | 有变更演练，但没有明确图遍历规则、未解析边的处理、影响范围可信度与变更前批准门槛。 |
| 元数据质量与新鲜度 | 部分 | 提到更新时间和待核实状态，但无完整性、准确性、有效性、新鲜度的阈值、检测频率和责任闭环。 |
| 安全权限 | 部分 | 目录字段有敏感级别，但未规定谁能看字段、SQL 和血缘，未处理敏感元数据脱敏、访问审批和审计日志。 |
| 采纳 | 部分 | 有第六周展示与业务验收，但无目录使用率、影响分析使用率、贡献者参与、培训和持续运营机制。 |

基线的主要失败模式：把目录和血缘视为六周制图与验收交付，未把元数据本身设计成持续运行的受控产品。场景中最危险的空缺是未明确“实际运行版本”如何成为可审计的血缘证据，以及未在目录中保留设计态与运行态的差异。

## 负向场景

仅为单个数据模型中的两个字段命名，且没有跨系统目录、共享口径、血缘或影响分析需求，不应触发 `managing-metadata`。此时直接在该模型的命名约定和数据字典中解决即可。
