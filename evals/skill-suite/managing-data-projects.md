# Scenario A：十二周湖仓平台 — 项目方案

## 1. 最小项目画像

| 项目要素 | 已知事实 / 本方案假设 |
|---|---|
| 业务结果与价值假设 | 为经营分析提供每日更新的销售与客户指标；假设门店、客户和电商运营者据此缩短日常经营决策的数据等待时间。价值以每日按时刷新、可用指标覆盖和目标用户实际使用验证。 |
| 类型与阶段 | 首个云湖仓建设项目，当前处于对齐与评估起点；十二周是硬交付窗口。 |
| 数据范围与消费者 | 输入为 CRM、POS、电商订单；首期消费者为经营分析人员及其管理层。首期输出限定为已批准的销售和客户指标数据产品/报表。 |
| 排除范围 | 不建设全企业目录、完整正式治理组织、全域质量规则、实时流处理、预测模型、主数据平台或历史系统替换。 |
| 约束 | 云厂商已定；未给出地区、个人信息分类、历史回溯期、预算、团队容量及现有接口质量。任何适用法律/行业要求、跨境传输与保留期限均为未决，不能假定合规。 |
| 当前能力与责任 | 无正式治理组织、企业数据目录或统一质量规则；需在项目内建立首期可运行的最小责任和控制，而非等待企业级能力完备。赞助人、数据所有者、技术负责人和风险否决者尚未命名。 |
| 决策期限 | 第 1 周确认章程、所有者和首期指标；第 2 周确认数据可得性、合规边界与质量基线；第 4 周批准可构建设计；第 10 周完成验证；第 12 周仅凭证据决定投产。 |

## 2. 知识域选择与理由

| 层级 | 技能 / 工作域 | 理由与边界 |
|---|---|---|
| 主 | `delivering-data-warehousing-and-bi` | 直接交付每日销售和客户指标及分析消费能力。范围是决策需求、语义、数据产品、验收和采纳；不代替系统间数据移动或企业架构决策。 |
| 基础/监督 | `establishing-data-governance` | 当前没有正式治理；首期必须指定指标定义、数据所有权、例外批准和问题升级的决策权。仅设项目/产品级最低制度，不声称建成企业治理委员会。 |
| 基础/监督 | `improving-data-quality` | 三源汇总会直接影响每日指标可信度；需定义关键数据元素、质量规则、基线、阈值、对账和异常闭环。 |
| 基础/监督 | `managing-metadata` | 无企业目录仍需最小业务术语、字段/指标定义、来源—转换—输出血缘和变更影响记录。 |
| 基础/监督 | `securing-data` | CRM 与订单可能含个人信息；需先分类用途和访问角色，再实施最小权限、审计、加密/密钥责任与发布前复核。 |
| 基础/监督 | `handling-data-ethically` | 客户数据用于经营分析须核对用途是否超出原始预期、是否会造成不公平或不当画像；本期形成用途限制和复核触发，而不开展模型公平性项目。 |
| 支持 | `integrating-data` | CRM、POS、电商订单的抽取、映射、增量加载、失败重跑和源/目标对账是 BI 数据供应的前置能力。 |
| 支持 | `designing-data-architecture` | 确定已选云厂商内的最小分层、环境边界、数据流、可观测性与过渡架构；不重新进行厂商选型。 |
| 支持 | `organizing-data-management` | 将最低可运行职责嵌入现有业务/技术团队：数据所有者、数据产品负责人、工程负责人、控制负责人、运营值班。 |
| 支持 | `leading-data-change` | 首个平台的价值取决于分析人员采用；须进行目标用户试用、指标解释、培训、反馈和上线后的使用追踪。 |

该组合回答了最小完备检查：数据及关键决策由命名的数据所有者承担；质量由关键指标规则和阈值定义；含义/来源/转换由最小元数据和血缘追溯；安全与用途合宜性由安全、隐私和伦理复核把关；运营负责人运行监控、异常和变更；业务代表确认采纳并设定停用/退役条件。

## 3. 调用顺序、依赖与十二周路线图

| 阶段 / 周次 | 目标状态与工作包 | 前置依赖 | 负责人 | 可验证出口与回退/停止条件 |
|---|---|---|---|---|
| 对齐（第 1 周） | 主域定义首期经营决策、消费者、指标优先级和范围；治理/组织指定决策权；安全与伦理登记数据用途及未知合规项。 | 业务赞助人可用。 | 业务赞助人（A），数据产品负责人（R）。 | 已批准章程、单一数据所有者、风险否决者、指标清单。无所有者或用途不被允许则 Hold，不进入开发。 |
| 评估（第 1–2 周） | 集成盘点三源接口、粒度、历史和刷新；质量建立基线；元数据登记术语与来源；架构/安全评估现有云账户、网络、身份和日志控制。 | 对齐结论。 | 工程负责人（R），数据所有者（A）。 | 可追溯的数据/系统清单、质量基线、控制差距和未知项。关键源不可访问、关键质量无法支持或合规未决则缩小首期范围或 Hold。 |
| 规划与设计（第 3–4 周） | 架构设计最小湖仓分层与环境；集成定义数据契约、映射和增量；BI 定义语义模型/数据产品；治理定指标和例外决策；质量、元数据、安全、伦理形成控制矩阵；变更确定试用与培训。 | 评估证据与范围。 | 技术负责人（A），各工作包负责人（R）。 | 经业务、数据、技术、控制负责人批准的设计、RACI、契约、测试/上线计划。未满足控制或运行责任缺失则 Rework。 |
| 开发与验证（第 5–10 周） | 构建受控抽取/加载、分层存储、语义层和每日指标；实施质量检查、血缘、访问审计与监控；以代表性数据进行功能、对账、质量、安全、恢复和用户验收。 | 批准的设计与可用环境。 | 工程负责人（R），技术负责人（A）。 | 可运行增量、测试证据、缺陷台账、元数据/血缘、恢复演练、试用反馈。高风险缺陷未关闭且未被有权人限时接受则不放行。 |
| 部署与转交（第 11–12 周） | 灰度发布，完成源/目标对账、权限复核、培训、值班/升级、服务目标和运营接管。 | 验证门通过。 | 运营负责人（R），业务赞助人（A）。 | 发布记录、对账报告、四方签字、回滚演练和培训记录。任一关键签字、回滚或支持容量缺失则 Conditional Go/Hold。 |
| 运营与改进（上线后） | 每日监控新鲜度、质量、成本、访问与使用；根因和变更闭环；每季度复核用途、权限、元数据、价值与退役。 | 正式接管。 | 数据产品负责人（A），运营负责人（R）。 | 趋势记分卡与问题/变更记录。连续两周未达服务目标、用途越界或无业务使用则升级、缩小或退役。 |

依赖链为：业务结果与用途边界 → 所有权/数据盘点与质量基线 → 架构、契约、语义和控制设计 → 集成与湖仓构建 → 对账/质量/安全/恢复/UAT 验证 → 灰度转交 → 运行改进。治理、质量、元数据、安全和伦理从对齐开始持续监督，不是开发末尾补件。

## 5. 交付物与验收证据

| 交付物 | 责任工作域 | 最小验收证据 |
|---|---|---|
| 项目章程、范围、价值假设、决策日志 | 主域 + 治理 | 业务赞助人签字；指标、消费者、排除范围与用途限制可区分。 |
| 数据清单、三源数据契约、字段/指标术语和血缘 | 集成 + 元数据 + BI | 每个首期指标可追溯至来源、转换和负责人；变更影响可查询。 |
| 目标/过渡架构、环境与运行设计 | 架构 + 集成 | 技术负责人批准；开发、测试、生产边界和失败重跑/回滚路径明确。 |
| 质量基线、规则、阈值、对账和问题台账 | 质量 + 治理 | 代表性数据的规则运行记录；源/目标销售金额、订单数和客户计数对账；异常有所有者和时限。 |
| 访问控制、分类、审计与用途限制记录 | 安全 + 伦理 | 最小权限测试、审计日志样例、访问复核签字、用途审查结论；未决法务项有负责人/日期。 |
| 语义层/每日指标数据产品和 UAT 记录 | BI | 目标用户用批准口径完成代表性经营分析；指标与批准定义一致。 |
| 测试、恢复、培训、值班和接管包 | 技术/变更/组织 | 功能、质量、安全、恢复测试通过；培训/试用记录；服务目标、升级表和接管签字齐全。 |

## 6. 指标、风险、控制与升级

| 风险事件 | 预防 / 侦测控制 | 指标阈值 | 所有者 | 失败动作与升级 |
|---|---|---|---|---|
| 每日数据未及时刷新 | 定时编排、依赖检查、失败重跑；每日新鲜度监控 | 截止时间前未完成刷新 | 运营负责人 | 停止发布当日指标或标记陈旧；当日升级技术负责人和业务代表。 |
| 三源口径或重复记录使销售/客户指标失真 | 批准的契约/口径、去重和完整性规则；源目标对账 | 任一关键对账差异超经数据所有者批准的容差 | 数据所有者 | 隔离批次、创建问题单、修复后重跑；超过一个工作日升级赞助人。 |
| CRM/订单个人信息被越权访问或用途外使用 | 分类、最小权限、审计、用途限制和定期复核 | 未授权访问、审计缺失或用途无法关联批准记录 | 风险/控制负责人 | 立即撤销访问并按适用事件流程处置；控制负责人可阻止上线。 |
| 无所有者或例外被项目进度默认接受 | RACI、阶段门签字、例外登记（风险/批准人/到期/补救） | 任一关键工件没有单一 A；例外到期未关闭 | 业务赞助人 | Hold/Conditional Go；升级至赞助人，禁止以日期压力自动放行。 |
| 用户不采用或误解指标 | 试用、培训、指标说明、反馈收集和使用监控 | 上线后连续两周目标用户未使用，或 UAT 出现未解决理解偏差 | 数据产品负责人 | 补充培训/改进语义；无价值证据则缩小或退役。 |

所有控制须在控制矩阵中记录执行频率、证据位置、失败动作和责任人；本方案中的数值容差和刷新截止时间在第 2–4 周由业务与数据所有者确定，不能凭空设定。

## 7. 本期裁剪与重新纳入触发条件

| 裁剪项 | 理由与残余风险所有者 | 重新纳入触发条件 |
|---|---|---|
| 企业级正式治理组织与全企业政策 | 十二周首期只需项目级决策权；残余风险：业务赞助人。 | 新数据域/部门加入、跨域所有权冲突反复发生，或控制例外无法在项目级闭环。 |
| 全企业数据目录和全量历史血缘 | 首期只登记三源、关键字段、转换和指标；残余风险：数据产品负责人。 | 扩大到新来源/数据产品、影响分析无法在一个工作日完成，或审计要求全量可追溯。 |
| 全域统一质量规则与完整历史修复 | 先控制影响每日指标的关键元素；残余风险：各源域数据所有者。 | 关键质量阈值连续不达标、对账差异导致业务决策受影响，或新增用途需要更高准确度。 |
| 实时/流式数据、复杂预测与个性化 | 业务目标是每日经营分析，不是实时运营或模型决策；残余风险：业务赞助人。 | 经批准的新场景要求近实时决策、预测/评分或面向客户的自动决策；届时重新纳入数据科学、伦理和更严格控制。 |
| 主数据平台、全面客户身份统一与遗留系统替换 | 首期可在批准的匹配规则内使用最小客户关联；残余风险：客户数据所有者。 | 客户重复/身份冲突持续破坏关键指标，或多系统需要权威客户黄金记录。 |
| 完整企业成熟度评估 | 目标是交付，不是给组织打分；残余风险：业务赞助人。 | 首期投产后需确定跨域投资优先级、路线图或能力预算。 |

## 8. 下一阶段门及证据

**下一阶段门：第 1 周末“对齐（Align）Go/Hold”。** 决策者为业务赞助人；风险/控制负责人对用途、安全或隐私风险拥有否决权。必须提供：已确认的业务结果、首期消费者和指标优先级；三源与排除范围；单一数据所有者、技术负责人、运营负责人和控制负责人；用途/受影响方初步评估；未决合规项的所有者和日期；以及超出范围的裁剪项、风险所有者和触发条件。

未满足上述任一关键项，决定为 Hold 或缩小为已知可控的数据源/指标；不因十二周期限自动进入构建。

## 9. 完成审计与遵循评估

- [x] 业务结果以每日更新的销售和客户指标及使用验证定义。
- [x] 知识域按主、基础/监督、支持分层，并说明边界、裁剪和触发条件。
- [x] 活动按 Align/Assess/Plan & Design/Develop & Validate/Deploy & Transition/Operate & Improve 排序，且每门以证据决策。
- [x] 每项关键决定具有单一 Accountable、执行者、否决/升级路径。
- [x] 交付物具有查询、测试、签字、演练或运行记录等验收证据。
- [x] 已检查治理责任、质量、元数据/血缘、安全/隐私、伦理用途、采纳、运行与退役。
- [x] 风险登记包含预防、侦测、阈值、所有者和失败动作；未知阈值明确留待有权人确定。

**入口技能遵循结论：遵循。** 本方案从业务结果和风险出发，使用路由表选择最少且完整的跨域能力，读取建设项目生命周期并将工作映射到阶段门，采用交付模板的章程、工作包、路线图、RACI、风险控制、裁剪与阶段门结构；没有把 DAMA 知识域当成全量瀑布清单，也没有将已选云厂商当成需求依据。

**发现的缺口：** 场景未提供适用地区/法规、个人信息类别与保留规则、历史数据范围、源接口/数据剖析证据、云环境控制、预算/人员容量、指标口径及可接受质量容差，也未命名任何责任人。这些缺口均已作为第 1–2 周的决策或证据要求；在确认前，不能声称可合规上线或给出无证据成熟度结论。
