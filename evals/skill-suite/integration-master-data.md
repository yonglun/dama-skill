# 端到端 GREEN 场景 2：十周客户主数据质量整改

## 评测输入、加载路径与路由

原始请求见 `evals/skill-suite/scenarios.md` 的 Scenario B：六个月前只用脚本集中清洗客户数据，如今 CRM、计费、客服再次出现重复客户、无效地址、冲突状态及不一致国家代码；要求十周降低重复并防复发。比较对象为 `evals/skill-suite/baseline-master-data.md` 的无技能回答。该基线本来就有完整十周计划和九个 `present`，本评测不把其已有的治理、质量或培训能力算成新技能收益。

按要求先只读取 `skills/managing-data-projects/SKILL.md`，然后读取其 `references/routing-table.md`、`project-lifecycle.md` 和 `deliverable-templates.md`，据路由再加载以下子技能的 `SKILL.md` 与各自 `references/playbook.md`：

| 选择 | 路由理由与责任边界 |
|---|---|
| `managing-reference-and-master-data`（主） | 三系统需要共享客户身份、黄金表示、交叉引用、状态/国家代码权威和持续分发；负责实体与参考数据裁决。 |
| `improving-data-quality`（基础） | 重复、地址无效与冲突已经复发；负责用途适用性、基线、根因、源头预防和持续质量记分卡。 |
| `establishing-data-governance`（基础） | 跨系统规则、权威源、例外和争议需要业务批准及监督。 |
| `managing-metadata`（基础） | 状态含义、属性来源、规则版本、消费者与字段级血缘必须可查，并支持变更影响分析。 |
| `securing-data`、`handling-data-ethically`（基础检查） | 客户身份连接、地址验证及跨系统共享有访问、用途、误连接伤害与申诉风险；分别落实保护控制和用途/受影响方判断。 |

## 完整项目回答

### 1. 业务结果、范围、假设与约束

十周内先降低经业务确认的活跃客户重复，再使新增错误能够在录入或接入时被阻止、隔离或交给有责任人的队列。经营结果另量化账单错投、客服识别返工与客户投诉，不能只统计合并了多少行。范围是三个系统的客户身份及关键属性、源标识、账单/联系/服务地址、客户状态、国家代码、增量接口和至少一个实际消费者。保留源记录和现有应用；只对获批准的共享身份/代码发布权威视图。

第 1 周剖析后由客户数据 owner 批准目标、分母与容忍度。可把基线中的“确认重复率下降至少 60%、误合并低于 2%、地址有效率至少 95%、国家代码合规率至少 99.5%、状态映射覆盖 100%、新增规则一次通过至少 98%”作为讨论草案，不能当已获批事实。分别按系统、地域、实体类型和存量/新增报告；“疑似重复”与“已确认重复”分开。任何客户自动连接阈值都要由标注正例、反例和边界例以及损害评估确定，关键账单身份的误合并上限可以严于总体指标。

未决事实及责任：三源是否有稳定、不复用的客户 ID（系统 owner，第 1 周）；“客户”与计费账户、客服联系人、法人/自然人的关系（客户 owner，第 2 周）；当前地址验证依据与允许用途（隐私代表和业务 owner，第 2 周）；状态码是否具有相同生效时间与业务语义（业务管家，第 2 周）；增量接口和消费者回写能力（集成 owner，第 2 周）。若这些事实不成立，调整架构、自动化和十周承诺，不凭猜测填补。

### 2. 工作包、依赖与十周阶段门

| 周次 / 生命周期 | 活动与依赖 | 可验证出口 / 不通过动作 |
|---|---|---|
| 1：对齐、评估 | sponsor 签业务结果；任命客户域 owner、参考数据 owner、管家及三系统/消费者 owner。只读画像存量与增量；冻结重复、地址、状态、代码指标的分母、窗口和切片；盘点现有清洗脚本及复发位置。 | 章程、权责矩阵、用途/访问初审、基线查询和样本由业务与控制负责人签字。数据无合法可用范围或 owner 未定则 Hold。 |
| 2：规划与设计 | 先裁决客户、账户、联系人粒度；定义源/消费者清单、字段级权威矩阵、全局 `party_id` 与交叉引用；批准状态/国家代码含义、版本、生效期；完成根因、影响图、匹配标注抽样和试点选择。 | 业务 owner 签实体/属性/代码/用途规则；系统和消费者确认字段映射与影响；未定权威或禁止合并条件时不批量处理。 |
| 3–5：开发与验证 | 在隔离环境影子生成候选和只读黄金视图，保留三源 ID；建立高置信、人工、拒绝三段裁决与案件队列。开发源头查重/地址/代码/状态规则、版本化接口、审计、回执、对账、拆分工具；用标注集和故障注入验证。 | 按系统/地域/实体类型提交匹配精确率、召回率、误合并及人工区比例；回放同名异人、同址家庭、集团法人、ID 复用、历史地址、错合并拆分、迟到/重放和旧代码。未达批准误合并上限、无法拆分或消费者对账失败则 No-Go。 |
| 6–7：试点、转交准备 | 选一业务单元和 1–2 个真实消费者先读后写；管家复核高风险合并，低风险动作分批启用；在三个源的新增/修改入口拦截或隔离无效值，记录用户摩擦。 | 每批有前像、批准、撤销令牌、发布清单及业务对账；试点重复率和增量一次通过率达到已批准阶段目标，关键账单/客服业务对象无错误连接；否则停止扩面、修规则或回退批次。 |
| 8–9：分批扩展 | 增加来源、业务单元和消费者；参考码按版本/生效期迁移，逐批接收回执和拒绝清单；培训一线、管家及值班人员。 | 三系统入口控制测试、消费者签收、队列容量与 SLA、培训实操结果均通过；单源退化或旧版本消费者未就绪则仅保持试点范围。 |
| 10：验收与运营 | 连续两周监测新增质量与队列；演练错合并拆分、参考版本回退、集成重放、消费者重对账和中断恢复；交接规则复审、月度治理和投诉更正流程。 | 业务结果、质量趋势、合同/账单/客服抽样、控制、运行与采纳证据分别签字。未达标项有 owner、期限、补偿控制和风险批准；不以项目日期自动放行。 |

Plan 确定用途、域、目标、权威和路线；Control 批准语义、阈值、访问、例外与发布门；Develop 建立交叉引用、规则、接口并实测；Operate 持续管家裁决、质量监控、发布对账、变更与复测。这四类活动在试点后仍循环运行。

### 3. 关键设计与责任

身份和属性分开裁决。`global_party_id ↔ source_system/source_customer_id` 保留源标识、连接状态、正负证据、置信度、首次/最近确认时间和规则/人工裁决版本。客户与计费账户、联系人、同住家庭成员、集团关联公司保持可表达的关系，不能因同名或同址直接合并。各关键属性逐一写权威条件：法定名称、联系/账单/服务地址、CRM 营销状态、计费状态、客服状态、国家码可能由不同来源和时间支配。冲突或缺少验证时保留来源值与待裁决状态，不伪造黄金值。

合并测试使用独立标注的正例、反例、边界例，并记录标注人和抽样方法。高置信且没有强负证据才可进入经批准的自动区；中间区由管家查证；强标识冲突、跨法人、同址异人或 ID 复用进入隔离。合并执行单记录源/全局 ID、前像、关系、属性生存结果、批准者、执行者、批次及受影响消费者。发现错合并时拆分身份、属性、关系和 crosswalk，发 `split/correction` 通知并重对账；数据库备份只是灾难恢复补充。提出、批准与生产执行批量合并不能是同一人。

国家与状态参考集分别有 owner、稳定代码、业务定义、映射、外部来源版本、有效期、替换/弃用、历史解释和消费者清单。提议 → 语义/影响审查 → owner 批准 → 沙箱兼容测试 → 定时发布 → 回执/对账 → 关闭；紧急变更仍留授权和审计。源系统可输入本地值，但未经批准不能将本地覆盖反向提升为企业权威。

| 决定或执行 | 唯一最终负责者 | 执行与制衡 |
|---|---|---|
| 业务结果、范围及项目阶段门 | 业务 sponsor | 项目负责人汇总证据；数据、技术、安全/隐私负责人分别出具意见。 |
| 客户定义、身份/属性权威、合并上限及高风险例外 | 客户数据 owner | 管家调查，MDM 工程实现；系统/消费者 owner 提供事实；安全/隐私有独立用途和访问阻止权。 |
| 国家/状态参考含义与版本 | 指定参考数据 owner | 管家维护、三系统 owner 测兼容、消费者 owner 确认历史解释。 |
| 源头规则与发布窗口 | 对应源系统 owner | 质量团队批准业务规则和测量；集成团队实现传输；无跨系统语义单方修改权。 |
| 消费者导入和业务对账 | 对应消费者 owner | 集成/MDM 团队提供清单、回执及差异；账单/客服业务代表抽样确认。 |

常规案件由管家按一个工作日分配、两个工作日裁决或升级的草案 SLA 处理；跨系统身份争议由客户 owner 最终裁决，参考代码含义由参考数据 owner 决定；隐私、未授权使用或严重误合并立即停相关批次并通知有权控制负责人。SLA 和风险容忍度由第 1 周批准。

### 5. 本期裁剪与重新纳入条件

- 不替换 CRM、计费、客服或建设全企业事务型 MDM hub；十周先用最小 registry/参考视图验证身份和持续控制。若源权威无法维持、写回冲突持续、多个域有获批案例，再评估更强 hub 与企业架构。
- 不自动合并全部疑似客户，也不物理删除源记录；误合并和历史账单解释成本高。标注集、风险上限和拆分演练达到批准门后，才逐步扩大自动区。
- 不把产品、供应商、员工等域或全部历史交易重算纳入；若明确业务损失、财务/合规要求或消费者无法使用交叉引用，再单独立项和评估。
- 不擅自补全无法核验的地址，不把三系统同名状态码直接视为同义；获得合法验证来源和业务裁决后再修复/映射。
- 不进行客户画像、营销二次使用或自动化待遇决定；任何新用途须独立经过用途、隐私与伦理复审。以上裁剪项在章程中记录风险 owner、触发条件和复审日期。

## 缺口报告与评估限制

**P0：0；P1：0；P2：0。** 没有发现路由错位、不可逆合并、缺失关键权威或运行证据等技能级缺口。十周阈值、匹配样本、源权威和真实接口能力仍需项目第 1–2 周采证及业务批准；这是场景缺少企业事实，不属于技能缺陷。此次是文本场景下的独立行为评测，未连接真实 CRM/计费/客服、未运行匹配算法，也不证明企业数据已经改善。
