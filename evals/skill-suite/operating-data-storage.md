# `operating-data-storage` 独立 GREEN／边界评估

## 总结

**GREEN：无阻断缺口。**

测试 A 应由 `operating-data-storage` 主导。
技能正文和手册共同覆盖六周投产所缺的容量、环境、变更、可用性、RTO/RPO、备份恢复、保留处置、性能、监控、值班和移交。
其关键优势不是列出控制项，而是要求用代表性负载、故障、隔离恢复、告警注入和未来值班人员独立演练形成证据。
测试 B 不应由本技能主导，应路由至 `integrating-data`。

## 评估口径

本评估以四个问题判断是否 GREEN：

1. 输出契约是否覆盖从服务定义到常态运行的完整交付物；
2. 阶段门是否会在证据缺失时真实阻止上线，而不是只登记风险；
3. 恢复是否验证端到端业务服务，而不是只验证备份作业或数据库启动；
4. 运行团队是否能脱离项目团队独立值守、变更、恢复和升级。

严重级别定义：

- P0：会导致错误主责、无证据上线或不可恢复，阻断 GREEN；
- P1：高概率导致错误批准或无法执行，需要上线前补齐；
- P2：模板化、裁剪或一致性增强，不阻断当前方法成立。

## 测试 A：新分析数据库六周生产就绪

### 起点判定与范围控制

现有逻辑模型只说明业务语义，平台选型只说明候选承载能力，两者都不构成生产就绪。
首发目标应限定为经批准的数据域、消费者、查询和装载窗口，而不是六周内承诺全部历史、全部用户或无限并发。
第 1 周必须把未知负载、增长和服务目标登记为有 owner、有验证日期、有超限动作的假设。
若六周内无法完成某项高成本能力，应缩小数据、消费者、地域或服务等级，不得免除恢复、回退、告警和值班硬门。

### 代表性六周执行骨架

| 周次／门 | 关键动作 | 最低交付物 | 出口证据／决定 |
|---|---|---|---|
| W1／G0 范围与业务影响 | 冻结首发数据、消费者、服务窗口、关键批次、依赖、增长和合规约束；任命业务、数据、平台、运行 owner | 服务任务书、依赖／故障模型、RACI、假设与风险台账、初版容量模型 | 业务负责人批准范围和重要性；未知项均有验证期限；否则不进入详细设计 |
| W1／G1 服务目标 | 以业务影响定义 SLI/SLO、RTO/RPO、最低服务、降级、事件级别和成本边界 | 服务目标、故障场景、恢复顺序、容量／成本方案、生命周期矩阵 | 业务负责人批准 RTO/RPO 和降级；运行负责人确认目标可运营；目标未批则 Hold |
| W2／G2 环境与发布通道 | 用 IaC／受控脚本建立开发、测试、预生产、生产和恢复环境；配置身份、网络、密钥、审计、监控骨架 | 环境拓扑、配置基线、差异清单、版本库、流水线、漂移检查 | 从空环境重建成功；环境差异有批准；生产不存在无记录手工配置 |
| W3／G3 物理运行与变更 | 将批准模型实现为类型、约束、分区／索引／分布、统计和维护策略；建立扩展—迁移—收缩、前滚／回退 | PDM／DDL、变更记录、兼容矩阵、回填方案、备份点、回退阈值 | 预生产同版本发布与回退通过；破坏性变更可被门禁阻止；否则无候选版 |
| W3／G3 容量与生命周期 | 估算数据、索引、日志、暂存、副本、时间旅行、备份和恢复副本；实现归档、保全和处置 | 可复算容量模型、观察／计划／执行／硬限阈值、保留矩阵 | 阈值能触发工单；扩容提前量大于供应提前期；全副本范围可追踪 |
| W4／G4 非功能验证 | 用代表性数据和并发执行基线、峰值、耐久、维护竞争、成本和故障测试 | p50/p95/p99、吞吐、队列、批窗口、资源曲线、查询计划和缺陷复测 | 核心查询、装载窗口、容量和成本达到批准目标；否则优化、扩容或缩范围 |
| W4／G4 恢复验证 | 从非当前备份在隔离环境执行完整恢复和适用的 PITR；演练副本／故障域切换与回切 | 计时恢复记录、实际 RPO、校验和、权限、控制总额、消费者验证 | 端到端 RTO/RPO 达标且数据完整；仅备份成功或实例启动均判失败 |
| W5／G5 运行接管 | 注入容量、备份、复制、装载延迟和查询退化告警；未来值班人员按 runbook 独立处置 | 告警到工单链路、值班表、升级树、runbook、培训／演练记录 | 正确队列按目标时间确认；非项目值班人员独立完成演练并签署接管 |
| W6／G6 发布与稳定 | 按窗口分阶段开放消费者；执行烟雾、数据对账和加强监控；冻结非必要变更 | 发布日志、业务对账、仪表盘、事件记录、资产登记、运行日历 | 稳定期达到批准 SLO，无未受控高风险项；服务 owner 接受剩余风险后退出项目 |

### 输出契约验证

| 输出契约项 | 手册要求的可执行证据 | 判定 |
|---|---|---|
| 服务范围和依赖 | 消费者、窗口、上下游、身份／网络／密钥／调度／目录依赖及降级方式 | 完整 |
| 环境／配置基线 | 拓扑、隔离、版本、参数、配额、漂移，以及从空环境重建 | 完整 |
| 技术适配与物理运行 | 事务／一致性、工作负载、类型、约束、分区／索引／统计和维护 | 完整 |
| 容量／成本 | 主数据外包含日志、暂存、副本、备份、峰值和增长；阈值触发动作 | 完整 |
| SLO、RTO/RPO | 目标、测量点、窗口、数据源、owner、降级和业务批准 | 完整 |
| 备份恢复与生命周期 | 隔离恢复、PITR、密钥／凭据、结构／权限／业务对账、全副本处置 | 完整 |
| 变更发布 | 版本、审批、低环境验证、兼容、前滚／回退、触发阈值和实际结果 | 完整 |
| 监控告警与事件 | 指标、阈值、通知、事件级别、工单、runbook、复盘和升级 | 完整 |
| runbook、值班和移交 | 主责／替补／队列／权限／升级链，未来值班人员独立演练并签署 | 完整 |
| 测试、风险和运行日历 | 负载／故障／恢复证据、Go/No-Go、稳定期及周期复核 | 完整 |

输出契约没有停在文档清单。
每项关键交付物均能落到测试结果、时间戳、日志、配置版本、工单、审批或数据校验结果。
因此可以追问“证据在哪里、谁批准、何时复测”，不会以架构图或截图代替验收。

### 硬门验证

以下条件按技能要求必须判为 No-Go，而不是登记为上线后行动：

- 没有一次从非当前备份到隔离环境的成功恢复；
- 实测 RTO/RPO 未达到业务批准目标，或最低服务与降级方式未获批准；
- 核心查询、峰值并发、装载或维护竞争未在代表性规模通过；
- 配置／模式／数据变更不能重放，或破坏性发布没有经测试的前滚／回退；
- 关键告警不能到达正确值班队列，或 P1 告警未在目标时间确认；
- 未来值班团队不能脱离项目人员完成代表性处置并签署接管；
- 受监管数据的保留、法律保全或全副本处置要求未获有权人确认；
- 身份、密钥、网络、调度或消费者等关键依赖无法恢复，却声称端到端目标达标。

`Conditional Go` 只能承载非阻断风险。
每项例外必须有业务影响、补偿控制、owner、批准人、到期日和复测日期。
日期压力、厂商 SLA、备份绿色状态或“上线后补文档”均不能覆盖硬门。

### 恢复证据的充分性

一次合格恢复记录至少应包含：

- 业务服务、重要性、允许降级、故障场景和批准人；
- RTO 起止事件、逐步时间线、目标值和实测值；
- RPO 的业务定义、选择的恢复点和实测数据损失；
- 使用的非当前备份／快照、校验状态、隔离位置及恢复版本；
- 恢复账号、密钥、网络、DNS、调度、连接和依赖服务的可用性；
- 模式、约束、权限、行数、校验和、控制总额和关键业务对账；
- 应用重连、首个成功装载、认证查询和至少一个真实消费者验证；
- 切换、回切、沟通、工单、实际问题、owner、整改和复测日期。

这套证据能识别“副本正常但逻辑损坏已复制”“备份存在但旧密钥不可用”“数据库起来但消费者仍断开”等假通过。
它也明确 HA、备份和 DR 是三个不同控制，任何一个不能替代另外两个。

### 可操作性验证

手册对可操作性的要求足够具体：

- 每个关键操作有主责、替补、值班队列、权限和升级链，而不接受“平台团队负责”；
- runbook 以触发／告警、业务影响、诊断证据、安全动作、升级通知、恢复验证和证据保留组织；
- 告警通过注入验证从测量点到通知、值班确认和工单，而不是只有仪表盘；
- 未来值班人员在项目团队不直接操作时完成恢复、容量或故障处置，并正式签署接管；
- 稳定期后按周查看服务、按月复核 SLO／容量／成本／变更／事件，按风险频率演练恢复、访问和生命周期；
- 补丁、升级、证书／密钥、容量、保留和供应商支持进入具名运行日历。

代表性 runbook 演练应至少覆盖备份失败、空间逼近硬限、复制滞后、长查询／锁、装载延迟、权限异常和审计失效。
每次演练保存触发时间、确认时间、诊断、动作、恢复时间、业务验证、升级和改进项。
因此“文档已移交”不会被误判为“运行团队已接管”。

### 测试 A 结论

技能能够把逻辑模型和平台选型之后的所有关键生产缺口转化为六周关键路径、证据和停止条件。
输出契约完整，硬门明确，恢复证据为端到端且可审计，运行移交可通过独立演练验证。
测试 A 判定为 **GREEN**。

## 测试 B：CRM→湖仓跨系统集成

**判定：`operating-data-storage` 不应主导；应路由至 `integrating-data`。**

用户只要求跨系统字段映射、批／流／API 选择、失败重放和跨系统对账。
这些交付物直接对应接口契约、编排、错误处理、幂等／重放和源目标一致性，属于 `integrating-data` 的主责边界。

建议的主责输出是：

- CRM 源字段到湖仓目标字段的映射、转换、默认／空值、代码集和 schema 演进规则；
- 按延迟、数据量、顺序、一致性、成本和源能力比较批、流、API／CDC，并记录决定；
- 批次／事件标识、幂等键、断点、隔离区、死信、重试上限、重放顺序和重复抑制；
- 记录级、分组级和总量级对账，含行数、控制总额、差异分类、容差、阻断和修复后重跑；
- 端到端血缘、SLA／新鲜度、失败通知、owner 和验收测试。

本技能只在请求扩展到湖仓存储运行时协同，例如实例容量、表物理运行、备份恢复、RTO/RPO、数据库监控、发布窗口和值班接管。
若字段含义、粒度或键冲突，由 `modeling-data` 协同；若要求跨系统目标／过渡蓝图和权威源布局，由 `designing-data-architecture` 协同。
不能因为目标端是“湖仓”就让存储运行技能吞并集成主责。

## 缺口及严重级别

| 级别 | 缺口 | 影响／建议 |
|---|---|---|
| P0 | 无 | 主责、硬门、恢复与移交闭环均成立。 |
| P1 | 无 | 未发现高概率导致错误上线或错误路由的内容缺失。 |
| P2 | 缺少可直接套用的六周快速路径模板 | 手册给出生命周期阶段门但没有周次裁剪；可增加六周最小路径，避免项目自行重排关键依赖。 |
| P2 | 容量模型缺少统一可填写公式／情景模板 | 已列成本与容量构成、阈值和提前量，但可补充基线、峰值、增长、维护、恢复、单价和敏感性字段。 |
| P2 | 缺少统一证据索引／签署页模板 | 验收证据定义充分；可增加证据 ID、位置、版本、生成时间、owner、批准、有效期和复测日期，提升审计一致性。 |
| P2 | 恢复演练频率只按风险表述 | 可按服务等级给出建议频率和触发型复测条件，如重大版本、密钥轮换、拓扑变化或恢复缺陷修复后。 |

这些 P2 都是交付加速和一致性增强，不影响当前技能生成可执行方案，也不会削弱 No-Go 判断。

## 最终判定

**GREEN（无 P0／P1，边界正确）。**

测试 A 由 `operating-data-storage` 主导，可形成范围、设计、环境、发布、容量、性能、恢复、生命周期、监控、值班和移交的完整证据链。
测试 B 明确拒绝主导并路由 `integrating-data`；本技能仅在持久化平台的生产运行问题出现时作为协同能力。

## 复核：四项 P2 是否关闭

| 原 P2 | 新增差异证据 | 复核结论 |
|---|---|---|
| 缺少六周快速路径 | 新增 W1–W6 最小路径，顺序覆盖目标、环境、物理运行、容量、恢复、接管、发布和稳定期，并禁止把恢复、回退、告警或接管推迟到上线后 | **已关闭** |
| 容量模型缺少公式／情景模板 | 新增基线、峰值、12／36 月增长、灾备／恢复并行情景；公式覆盖主数据、索引、日志、暂存、副本、时间旅行、备份、恢复空间和裕度，并要求增长率、压缩率、保留期、单价敏感性 | **已关闭** |
| 缺少证据索引／签署页 | 新增证据 ID、阶段门／控制、不可变引用、配置／数据版本、生成时间／环境、Owner、审核／批准、有效期／复测字段 | **已关闭** |
| 恢复演练频率仅按风险表述 | 新增关键服务季度关键路径／年度端到端、其他服务至少年度验证，并以版本、拓扑、地域、密钥／身份、备份策略、实际事件、缺陷修复及连续失败触发即时复测 | **已关闭** |

**复核结论：四项 P2 全部关闭；未发现由这些增补引入的新 P0、P1 或 P2。最终状态保持 GREEN。**
