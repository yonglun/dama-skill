# CRM 与计费数据八周集成方案（RED 基线）

## 1. 目标、成功标准与边界

八周内把 CRM 的客户、联系人，以及计费系统的账户、发票数据接入湖仓，形成可追溯、可重跑、可对账的认证数据产品。每日批次须在 07:00 前可用；关键客户的 CRM 变更提供近实时更新。由于计费源只支持夜批，近实时承诺只能覆盖 CRM 属性和关系，不能把昨日计费快照包装成实时数据。消费端必须同时看到 `crm_freshness_ts`、`billing_as_of_date` 和整体认证状态。

上线成功至少满足：业务键冲突有确定的匹配和例外流程；接口与语义契约由源负责人签署；连续 5 个业务日于 07:00 前发布；关键客户 CRM 更新达到约定延迟；记录级、分组级和总量级对账通过；故障可幂等重跑且不会重复开票金额或联系人；删除、迟到、模式变更、隔离和重放均经演练；血缘、监控、值班及数据共享协议可执行。

### 首期范围

- CRM 客户、联系人、客户—联系人关系及其新增、变更、删除事件。
- 计费账户、发票头、必要的发票汇总字段及夜批控制文件；明细行仅在首批用例确需时纳入。
- 源落地区、标准化层、身份映射层、认证客户/账户/发票视图及关键客户低延迟服务表。
- 端到端契约、字段与代码映射、质量、对账、血缘、调度、异常处置、访问和运行移交。

### 八周内不承诺

- 不改造计费系统为流式或将计费数据承诺为近实时；如业务必须实时看余额/发票，须单独立项增加计费接口或事件能力。
- 不建立全企业主数据平台，不自动合并所有疑似重复客户；首期只维护本范围的受治理交叉引用表。
- 不覆盖全部 CRM 对象、发票明细、历史无期限回填、外部数据共享或任意自助写回。
- 不用数据虚拟化替代可审计的持久集成，也不在冲突语义未获批准时自行选择一个源为真值。

## 2. 第 1 周确认的需求与决策输入

需求工作坊必须确认：消费者和决策用途；关键客户名单的权威来源和变更频率；“近实时”的量化目标；07:00 所属时区、工作日/节假日和月末窗口；源文件最晚到达时间；初始历史年限、日增量、峰值和更正频率；联系人敏感字段、同意状态、留存及删除义务；CRM 与计费各字段的业务定义；客户、法人、地点、账户、联系人之间的粒度；空值、默认值、负金额、贷项和作废语义；下游查询和刷新依赖。

所有未确认项进入假设/问题/决策/风险台账，具名负责人和截止日。建议初始工程目标（须由业务批准后才成为承诺）：每日认证快照 06:30 完成、07:00 截止；关键客户 CRM 事件端到端 p95 不超过 5 分钟、p99 不超过 15 分钟；日批失败在 30 分钟内告警；阻断性对账差异为零，非阻断差异有阈值和批准人。

## 3. 集成方式选择

| 对象/链路 | 选择 | 理由 | 明确限制与回退 |
| --- | --- | --- | --- |
| CRM 初始全量与补数 | 分页 API 批量抽取 | API 可控、适合基线和按 ID 修复；保留源响应与水位 | 受速率限制、分页漂移影响；采用稳定排序、快照时间和指数退避 |
| CRM 常态增量 | CDC/事件流 | 满足关键客户近实时并捕获更新、删除；所有客户事件统一进入流，关键标记决定消费优先级 | 不假定事件严格有序或恰好一次；事件缺口时从最后确认水位用 API 回补 |
| CRM 每日校准 | API 增量/抽样或全量校验 | 发现 CDC 丢失、长期断连和源端静默更正 | 不替代实时链路；校准差异产生修复批次和审计记录 |
| 计费账户与发票 | 夜间批文件/批表 | 这是源唯一受支持方式，适合控制总额和可重复装载 | 要求 04:30 前到达（最终时间与源方确认），迟到则保留上一认证版本并标记过期 |
| 湖仓内部处理 | 微批流处理 CRM；批处理计费与跨源整合 | 分开满足低延迟和 07:00 认证发布，避免用流处理强行模拟批源实时性 | 流式表只表示 CRM 新鲜度；每日认证快照在完整对账后原子发布 |
| 虚拟化 | 仅限短期只读验证/源差异排查，不作生产主路径 | 可加速验数，但运行时依赖源可用性、语义和性能，难以支持历史、重放与稳定 SLA | 禁止在认证产品中无快照地跨源联查；不得绕过脱敏、访问及审计 |

整体采用“双速”架构：CRM CDC 进入原始事件表，经标准化后增量更新客户/联系人；计费夜批按不可变批次落地。身份解析层维护 `enterprise_customer_id` 与两源 ID 的交叉引用；认证层每日将两路数据按批准语义组合，关键客户服务层则把最新 CRM 属性叠加在最近一次已认证计费快照上，并显式暴露两个时间戳。

## 4. 语义、键和映射设计

### 身份与粒度

- 保留原始 `crm_customer_id`、`billing_account_id`、`invoice_id`，不得用邮箱、名称或电话直接覆盖源键。
- 生成稳定且不可复用的 `enterprise_customer_id`；交叉引用表记录源系统、源键、企业键、匹配方法、置信度、规则版本、生效/失效时间、审核状态和审核人。
- 确认客户（主体）与计费账户是一对多还是多对多；联系人只通过有时效的关系表关联客户，不能把联系人等同客户。
- 先用确定性规则（已批准的合同号/税号/外部引用）自动匹配；名称、地址、电话等模糊匹配只产生候选。低置信度或多候选进入人工队列，不静默合并。
- 合并/拆分采用有版本的映射事件；保留历史企业键关联及下游影响，不回收旧键。

### 字段与代码映射登记表示例

| 目标字段 | CRM 来源 | 计费来源 | 转换/优先级 | 质量与冲突处理 |
| --- | --- | --- | --- | --- |
| `enterprise_customer_id` | `customer.id` | `account.customer_ref` | 交叉引用生成，不由任一业务字段直接派生 | 未匹配进隔离区；映射版本可追溯 |
| `customer_name` | `customer.legal_name` | `account.bill_to_name` | 法定名称以经批准权威源为准，展示名称可来自 CRM | 非空；差异只告警，不自动覆盖法定名称 |
| `customer_status` | CRM 状态码 | 账户状态码 | 分别保存原码，再映射到共同枚举 `active/suspended/closed/unknown` | 未知码阻断发布或映射为 `unknown`，由数据所有者决定 |
| `country_code` | 国家文本/码 | ISO/本地码 | 映射到 ISO 3166-1 alpha-2，保留原值 | 非法码隔离；映射表含版本和生效日 |
| `contact_email` | 联系人邮箱 | 无 | 规范化仅用于展示/质量，不作为唯一身份键 | 分类为个人数据；格式检查、访问受控 |
| `invoice_amount` | 无 | 发票金额 | 保留原币金额与币种；派生本位币须指定汇率源、日期和舍入 | 金额、税额、贷项符号和小数精度按计费契约 |
| `billing_as_of_date` | 无 | 文件业务日期 | 取控制记录，不用文件落地时间替代 | 缺失或重复业务日期阻断认证发布 |

完整映射登记表须逐字段包含：业务定义、源对象/字段、源和目标类型、长度/精度、必填性、单位/时区、枚举、转换表达式、默认/空值规则、权威源、敏感级别、质量规则、示例、负责人、映射版本及生效日。映射变更须通过数据所有者和下游影响评审。

## 5. 接口与数据契约

每个 API、CDC 主题和批文件建立版本化契约，至少包括：接口所有者与支持时间；对象粒度；主键和业务键；事件 ID、操作类型、源提交时间、序列/游标；字段 schema、枚举、时区、编码、精度及空值语义；全量/增量/删除表示；排序和交付保证；分页/速率限制；文件名、压缩、分隔符、头尾控制记录、校验和及加密；允许到达窗口；重送规则；兼容期；数据分类；验收样例和故障联系人。

CDC 信封统一为 `event_id, source_object, source_key, operation, source_commit_ts, source_sequence, schema_version, payload, ingestion_ts`。批次清单统一为 `batch_id, source_system, business_date, extract_start_ts, extract_end_ts, file_name, row_count, amount_total, checksum, schema_version`。消费数据产品契约还须声明刷新规律、字段语义、已知限制、质量状态、版本、弃用窗口、访问目的和支持渠道。

契约存入版本库与目录；生产入口执行 schema、文件清单、校验和及允许值校验。破坏性变更未过兼容门禁时只进隔离区，不能让消费者看到半兼容版本。

## 6. 分层、血缘与发布

- **原始层**：按源到达内容不可变保存 API 响应、CDC 事件、批文件、清单、校验和与接入元数据；限制访问并按保留策略处理。
- **标准化层**：类型、时区、代码、删除标记和重复事件规范化；保留原值、规则版本、`batch_id/event_id`。
- **身份解析层**：交叉引用、匹配候选、人工裁决及历史版本，独立于事实转换。
- **认证层**：客户、联系人、账户、发票及关系的当前/历史表；只有通过质量和对账门的批次才以原子指针/分区切换发布。
- **服务层**：每日认证快照和关键客户 CRM 低延迟视图；字段级标注来源与新鲜度，禁止把两个不同水位压成一个“更新时间”。

目录记录系统、对象、字段级血缘：源接口/文件与版本 → 原始对象 → 转换作业和代码版本 → 映射规则/交叉引用版本 → 认证表/字段 → 服务视图和消费者。每条记录携带可反查的 `run_id`、`batch_id` 或 `event_id`。血缘须能回答某张发票来自哪个文件、某客户名称由哪个源和规则决定、一次重放影响了哪些下游分区。

## 7. 编排、状态和幂等

每日关键路径建议：03:30 等待计费清单与文件 → 落地/校验 → 账户与发票标准化 → CRM CDC 水位封口并执行每日校准 → 身份映射 → 跨源整合 → 三层对账/质量门 → 06:30 原子发布 → 通知消费者。最终时刻应依据真实数据量倒排，至少预留一次可完成的重跑窗口。

编排器维护有状态运行表：`run_id, logical_date, source_watermark, input_manifest, code/schema/mapping_version, status, attempt, started_at, ended_at, published_version`。依赖以数据就绪和质量状态触发，不以固定等待代替；同一业务日期并发运行加锁，发布步骤与处理步骤分离。

幂等策略：原始文件以源、业务日期、文件标识和校验和唯一；CDC 以源分区加事件 ID/序列去重；标准化和认证写入使用确定性主键及 `MERGE`/分区替换；副作用通知带幂等键；检查点仅在持久写入成功后推进。重跑创建新 `run_id`，但复用同一逻辑业务日期；若输入和版本未变，结果应一致。禁止以“作业成功退出”代表发布成功。

## 8. 失败、隔离与可控重放

- 瞬时网络、限流和服务不可用：限定次数的指数退避加抖动，尊重 `Retry-After`，总重试时长不得吞掉 07:00 重跑窗口。
- 确定性数据/契约错误：不盲目重试；记录错误码、原始引用、规则版本和处置状态，送隔离区或死信队列。
- 死信队列用于无法处理的 CDC 事件；隔离区用于坏记录、坏文件、未知代码和低置信匹配。敏感负载应加密/脱敏，访问与保留受控。
- 批文件校验和不符、控制总额错误、缺失文件或不兼容 schema：整批隔离，保留上一认证版本，不发布部分计费数据。
- 重放工具按事件范围、源分区/序列、批次、业务日期或目标分区选择，先在影子表验证对账，再原子替换；记录发起人、原因、版本、影响范围和前后校验。
- 已发布错误数据的修复采用新版本与更正通知，不直接无审计地覆写；必要时回滚认证指针到最近一次合格版本。

## 9. 迟到、乱序、更正与删除

CRM 事件按源提交时间和源序列处理，接入时间只用于运营监控；对每个键保留最后适用版本，重复或旧事件不得覆盖较新状态。定义允许乱序窗口，例如 24 小时，并允许更晚事件进入回补流程而非永久丢弃。计费迟到文件按业务日期落分区；收到更正文件必须有新清单、版本和替换/差量语义，触发受影响日期的重算及下游通知。

删除需区分业务停用、源硬删除、隐私删除和错误合并撤销。CDC tombstone 转为有时效的删除标记；分析历史是否保留取决于批准的业务和法规规则。隐私删除应沿认证层、服务层、缓存、导出和到期备份传播，并保留不含个人数据的处置证据。联系人从客户解除关系不等于删除联系人；账户关闭不等于删除发票历史。

关键客户标记的迟到和撤销同样版本化。刚升为关键的客户要通过 API 回补当前 CRM 状态；降级后停止低延迟服务但不删除应保留的认证历史。

## 10. 三层对账与质量门

| 层级 | 最低检查 | 发布规则 |
| --- | --- | --- |
| 记录级 | 主键唯一、必填、类型/长度、枚举、引用存在；源目标关键字段哈希/抽样逐条比对；每个坏记录可追至原始输入 | 金额、主键、删除等关键错误阻断；允许的非关键坏记录按阈值隔离并获批 |
| 分组级 | 按业务日期、状态、国家、币种、账户类型和关键客户标记比较记录数、金额/税额/贷项；检查孤儿账户、联系人关系和匹配率 | 差异须在批准容差内；所有差异有原因码、工单和负责人 |
| 总量级 | 清单行数、文件数、金额控制总额、唯一账户/发票数；API/CDC 起止水位、事件数、缺口和重复数 | 财务控制总额及事件序列缺口默认零容差；未通过不得推进认证指针 |

另设语义质量指标：客户自动匹配率、疑似重复率、人工队列年龄、未知代码率、空值率、CDC 延迟、批次新鲜度和更正率。对账以源方签署的控制清单为基准，不能只比较管道相邻两层，因为同一错误可能被两层共同复制。

## 11. Schema 与契约演进

schema 登记表按接口和数据产品保存版本。新增可空字段通常向后兼容，但仍需消费者测试；字段删除/重命名、类型收窄、精度变化、枚举语义变化和键定义变化属于破坏性变更。采用扩展—迁移—收缩：先增加新字段/版本并双写，回填和并行验证，迁移消费者，过完弃用窗口再移除旧字段。

入口对未知字段、缺失必填字段和版本执行策略化校验。兼容新增可保留并告警；破坏性或未知版本隔离。枚举新增不能静默映射为既有值，先落原码并由数据所有者批准映射。契约变更需源负责人提前通知、提供样例、影响分析和生效日；紧急变更也要补齐审计、回放和消费者通知。

## 12. SLA、SLI、监控与降级

| 目标 | 测量方式 | 告警与处置 |
| --- | --- | --- |
| 每日 07:00 前可用 | 从源业务截止到认证版本可查询；记录最近成功业务日和发布时间 | 预计无法在 06:30 发布即告警；07:00 未达为 SLA 事件，展示上一合格版本及过期标识 |
| 关键客户 CRM 近实时 | `service_visible_ts - source_commit_ts` 的 p50/p95/p99、积压年龄及事件缺口 | 连续窗口超阈值或序列缺口告警；切换 API 回补/受控微批并标记降级 |
| 完整性与正确性 | 三层对账通过率、金额差异、坏记录率、未知码和身份匹配例外 | 阻断项不发布；非阻断项按阈值建工单并由数据所有者接受 |
| 平台可靠性 | API 成功率/限流、CDC 连接与 lag、文件到达、作业成功率/时长、重试、死信、发布年龄 | 按源、管道和消费层分别路由，避免“湖仓正常”掩盖源延迟 |

仪表盘还需展示各源水位、批次关键路径、阶段耗时、数据量突变、空值/分布漂移、隔离区与人工匹配积压、schema 版本、成本和消费者失败。每个告警都有阈值依据、严重度、负责人、runbook、升级树及抑制规则。合成查询验证认证视图真正可用；日志关联 `run_id/batch_id/event_id`。上线前注入源迟到、CDC 断流、坏 schema、对账差异和发布失败，验证告警能在目标时间抵达当班人员。

## 13. 数据共享协议

源方、数据产品方和消费者签署的数据共享协议至少规定：允许用途与禁止二次用途；对象、字段、粒度和语义；系统记录权威及冲突裁决人；刷新与截止时间、近实时范围、新鲜度标签；质量阈值和例外披露；分类、最小权限、行列级控制、加密及审计；驻留、留存、隐私请求、法律保全和删除；允许消费者及再共享限制；导出与缓存规则；schema/语义变更通知期和弃用窗口；事件、差错更正、下游通知和责任边界；服务目标、支持时段、升级联系人、暂停共享和终止后的数据处置。

协议明确 CRM 负责源事件和客户字段语义，计费负责批文件及财务控制总额，集成团队负责传输和转换可重复性，数据所有者负责共同语义和匹配规则，消费者负责按声明用途使用并响应变更。协议不把源数据真实性责任转嫁给管道，也不把消费端副本的删除责任留空。

| 数据架构师 | 审查粒度、键、双速架构、历史与共享边界；防止临时映射固化为错误主数据 |
| 数据工程负责人 | 管道、编排、幂等、重试、重放、对账、schema 兼容、性能和技术签署 |

## 15. 八周计划与阶段门

| 阶段门 | 周次与工作 | 必须证据与通过条件 |
| --- | --- | --- |
| G0 范围与服务目标 | 第 1 周：确认用例、关键客户、粒度、历史、07:00 和近实时定义、数据分类、源能力 | 范围/RACI/风险台账、SLA 草案和依赖图签署；计费实时边界获业务接受 |
| G1 契约与语义 | 第 2 周：源剖析、键冲突分析、字段/代码映射、数据共享协议、身份规则 | 契约样例、映射登记、匹配基准集、控制总额定义；未决关键语义为零 |
| G2 接入骨架 | 第 3 周：CRM API 基线、CDC 原始链路、计费文件落地、schema/清单校验、血缘骨架 | 可重复接入样例数据；原始数据、校验和、水位和 lineage 可查；权限负向测试通过 |
| G3 标准化与身份 | 第 4 周：标准化、代码映射、交叉引用、人工例外、删除与迟到逻辑 | 代表性数据质量报告；合并/拆分、乱序、未知码和 tombstone 测试通过 |
| G4 认证与控制 | 第 5 周：认证模型、三层对账、原子发布、接口产品契约 | 全量和增量结果与源控制一致；失败时旧版本仍可用；字段级血缘可追溯 |
| G5 韧性与性能 | 第 6 周：故障注入、幂等重跑、死信/隔离/重放、峰值/补数、schema 演进 | 同批重跑无重复；断流/坏文件/破坏变更被正确处置；能在截止前恢复 |
| G6 端到端试运行 | 第 7 周：连续日批、关键客户实时链路、UAT、告警和值班演练 | 至少连续 5 个业务日达标；近实时 p95/p99 和 07:00 SLI 有实测；运行团队独立处置演练 |

## 16. 容易遗漏的事项

1. **“关键客户”本身也需要权威源、变更事件和生效时间**，不能在代码中维护静态名单。
2. **计费只夜批意味着整合视图有两个新鲜度**；必须分别标识，避免消费者误认为余额近实时。
3. **源提交时间、接入时间、业务日期和发布时间不同**，时区、夏令时和节假日规则须统一。
4. **API 分页期间的数据变动会造成漏取/重复**，需要稳定游标、快照边界和每日 CDC 校准。
5. **CDC 保留期可能短于故障时间**，须监控最老未消费事件并具备 API 回补路径。
6. **邮件、名称和电话不是稳定客户键**；共享联系人、账户转移、企业并购会破坏简单一对一匹配。
7. **贷项、作废、重开、税额、币种和舍入**常使行数相等但财务总额错误。
8. **空值、空串、零、未知和“不适用”不同**；默认值会掩盖源语义和质量问题。
9. **联系人解绑、客户关闭、源硬删除和隐私删除不同**，保留及下游动作不能共用一个布尔字段。
10. **死信/隔离区也含个人和财务数据**，同样需要权限、保留、审计和删除控制。
11. **重放可能再次触发通知或消费副作用**，所有下游写入及消息须有幂等键。
12. **交叉引用规则变化会重写历史关联**，必须版本化、影响分析并通知下游，不能静默全表回填。
13. **源控制文件也可能错误**，需源方签署口径，并以多日趋势和独立业务核验发现共同错误。
14. **认证发布要原子化**，不能让消费者同时读到新客户和旧发票分区。
15. **虚拟化查询会把源停机、限流和权限变化传导给消费者**，只适合作受控验证而非核心 SLA 路径。
16. **导出、缓存和沙箱会脱离湖仓治理**，共享协议必须覆盖再共享、删除传播和终止处置。
17. **运行账号、密钥、证书和供应商支持权限**需在夜间值班场景实际验证。
18. **成功上线后的所有权**必须延续到 schema 评审、映射例外、SLA 报告、访问复核和删除证明。
