# `managing-metadata` 独立 GREEN／边界评测

## 评测结论与方法

**GREEN：正向场景可形成有运行证据的最小目录、字段级血缘及变更影响门；负向场景能正确退出。未发现 P0、P1、P2 缺口。**

已完整读取 `skills/managing-metadata/SKILL.md`、`skills/managing-metadata/references/playbook.md` 和 `evals/skill-suite/managing-metadata-baseline.md`。以下独立应用同一六周场景，先写出应有的项目决策与可验收制品，再与未加载技能的 RED 回答逐项对照。场景中没有生产库、代码仓或报表样本可查；表名、版本和数值均仅是待项目确认的演练示例，不表示已经验证企业事实。

判级：P0 为错误主责、把未经证实的血缘或越权内容当成已验证事实；P1 为缺少关键控制，导致审计追溯或变更影响不可安全执行；P2 为仍须项目自行发明的重要制品结构或验收方法。项目现场需填写的源名、SLA 和阈值不自动算技能缺口。

## 测试 A：三份经营报表、两项指标的六周目录与血缘

### 1. 主责、消费需求和范围

`managing-metadata` 主导资产发现、术语/指标目录、跨系统字段级血缘、实现与运行证据、影响分析和目录运营。`establishing-data-governance` 任命业务 owner 并裁决冲突口径；`delivering-data-warehousing-and-bi` 对“净收入”“活跃客户”的业务计算及报表数值负责；`integrating-data` 提供源到目标的映射、批次和作业证据；`securing-data` 批准目录可见性。目录只记录获批口径及版本，不在扫描过程中自行宣布一个全企业唯一公式。

第 1 周冻结三份报表、两项指标及相关 CRM、ERP、订单、退款、批任务、SQL 和 BI 对象作为第一期分母。访谈财务/销售/运营使用者、报表开发、工程、审计和安全，交付“用户任务—验收查询”清单：

| 消费任务 | 验收时应现场回答的问题 | 所需粒度和证据 |
|---|---|---|
| 查找/解释 | 三份报表各使用哪个指标定义及适用范围？差异来自定义、过滤、时间窗还是源状态？ | 报表、指标版本、业务定义、批准人、语义层配置和争议单 |
| 逆向追溯 | 任取一份报表中一项关键数值，能否查到源字段、转换、实际代码和成功作业实例？ | 字段级逐边链路、部署/运行版本、批次/时间、控制总额与证据位置 |
| 正向影响 | 若退款金额字段或客户身份规则改变，哪些指标、报表、接口和 owner 可能受影响？ | 按版本/生效期遍历的上下游图、未知边和人工复核记录 |
| 审计/运行 | 某报表发布日期对应的是哪套实际运行逻辑？目录记录何时更新、何人验证？ | 运行实例、数据水位、采集批次、差异日志、访问审计与批准记录 |

交付需求表为每项查询记录样本、期限、查询角色、允许访问范围、验收人及失败时的降级说明。第一期不做全公司普查；扩展条件是样本查询被通过后，按关键消费者/资产价值接入更多域。

### 2. 三类元数据与架构判定

本场景建议**混合架构**：中央维护稳定资产 ID、术语/指标、owner、关系图、权限索引和新鲜度；数据库、代码仓、调度和 BI 保留详细 schema、提交、作业实例与配置原件。三份报表跨多源且要跨系统查询，纯源内分布难以直接完成影响分析；把所有日志与代码全文搬进单一目录则会增加同步、权限和运行负担。第 2 周验证各源 API/连接器、历史保存、版本标识和跨源查询能力后由元数据产品 owner 批准选型；若单源无法可靠提供运行证据，则该边标未知并附人工验证任务，不因选了混合架构就假定已联通。

最小元模型含 `asset_id`、`field_id`、`metric_id`、`job_id`、`report_id`、源内 ID/别名、版本/有效期、owner、分类、业务定义、schema、映射、作业实例、证据 URI、观察时刻、状态、上游/下游关系及已知缺口。三类验收分开：业务定义和权威由业务 owner 签署；技术 schema、SQL 和 BI 语义与实际部署版本一致；运行状态、实例、输入/输出水位、失败/成功及处理版本可查询。重命名或迁移通过稳定 ID 与别名历史连接，不把同名字段直接视为同一资产。

### 3. 扫描、策展和冲突闭环

为 CRM/ERP/订单/退款库、调度、代码仓及 BI 分别列出采集接口、资产粒度、源版本、扫描周期、访问限制、负责人与失败回退。技术和运行事实先由扫描/API 进入暂存，校验 ID、类型、版本与权限，再生成候选差异；动态 SQL、UDF、手工 Excel 或无法解析的逻辑进入有期限的人工验证队列。策展人可以提出业务定义，业务 owner 才能批准；工程 owner 验证实现逻辑，不能用设计文档覆盖生产事实。人工覆盖记录理由、证据、批准、复审日期和失效条件。

两项指标若出现冲突，目录同时展示“定义 A 适用报表/期间”和“定义 B 适用报表/期间”、争议状态、差异样本及决策单；只有 owner 裁决后发布认证版本，并保留历史解释。扫描失败或版本漂移使条目变旧时，目录显示失效提示与最后可信版本，不静默维持绿色状态。

### 4. 逐边血缘和实际运行证据

对“净收入”的一条**示例候选链**，第 3–4 周应形成下表；字段与转换名称须以现场代码核对后替换：

| 边 | 设计态 | 实现态与运行态所需证据 | 当前交付判定 |
|---|---|---|---|
| `order.amount/discount` → `stg_order.net_amount` | 映射规格说明扣减方式 | 部署 SQL/提交、作业配置、成功实例、输入/输出批次和控制总额 | 证据齐备并由工程 owner 核验后才标“已验证” |
| `refund.refund_amount` → `mart_revenue.net_revenue` | 设计可能规定退款扣减 | 实际连接键、过滤/冲销规则、代码版本、运行实例及样本复算 | 若动态 SQL 解析不到关键变换，明确“未知/待复核” |
| `mart_revenue.net_revenue` → BI 语义指标 → 报表字段 | 指标说明和报表设计 | 当前部署语义配置/报表版本、查询或刷新日志、对应发布时点 | 配置与作业实例一致后再标实现/运行证据 |

“活跃客户”另抽一条 CRM 身份/活动事件 → 转换 → BI 指标的逆向链，专门验证身份合并规则、活动窗口及时间点。每条边保存上下游稳定 ID/版本、转换、证据位置、解析/人工方法、观察/有效时间、验证人、可信度和缺口。设计映射、当前部署实现与某次报表发布所用运行实例分列；若设计写“下单客户”、部署代码算“登录客户”，显示差异并开调查单，不能合成一条无差异的绿色血缘。

第 5 周对报表“两项数值逆查到源”和源字段“正查到消费者”双向抽样。能追到源字段但缺运行实例的链路只能表述为“实现态已知，具体发布日期的运行事实待证”；不能作为完整审计追溯通过。

### 5. 真实变更影响演练与发布门

选一项已存在的退款字段/规则变更申请；以其稳定字段 ID 和拟生效版本为起点，沿实现态依赖边遍历作业、指标、BI 语义、三份报表及接口/消费者，再用生效时间过滤历史版本。记录遍历规则、发现清单、明确不受影响的证据、未知或低置信链路、与代码/报表 owner 逐项核对的漏报，以及业务 owner 的签收。若一个手工补录步骤尚未解析，标“可能受影响，需人工核对”，不能判“无影响”。

变更门要求提交影响清单、关联代码/指标版本、消费者通知、复算/回归结果、回退方案和 owner 确认。关键消费者漏报、关键链路只有设计图、口径无业务 owner 或敏感元数据越权，均是第 6 周 No-Go。

### 6. 质量、新鲜度、权限和采纳

验收报表按冻结样本记录分子/分母、基线、目标、采样和 owner：范围内资产/字段/关键边覆盖率；有定义、owner、分类、来源和版本的必填完整率；有当前实现及运行证据的关键边比率；设计/实现差异关闭率；源变更至目录可见的延迟和过期条目数；抽样与源一致率；搜索成功、影响分析实际使用、活跃消费者、贡献者及反馈关闭。阈值由用户和 owner 在第 1–2 周批准，扫描失败、差异超限或新鲜度超期形成有责任人与 SLA 的工单，复测后关闭。

搜索结果按角色裁剪：普通使用者可看获准的术语、owner 和分类；敏感字段存在性、字段名、SQL 常量、源路径、细粒度血缘、作业日志和客户信息由安全/隐私 owner 明确审批可见范围、遮蔽方式与访问日志。审计角色按批准范围提取证据，不默认拥有全目录原文权限。

第 6 周让业务与审计按前述四个查询现场验收，并培训业务贡献者提出定义/反馈、工程 owner 解释部署差异、运营人员处理扫描失败。移交采集调度、漂移告警、策展队列、反馈 SLA、月度影响演练和使用指标，避免目录在验收后停止更新。

### 7. 六周门禁及与 RED 基线比较

| 周次 | 阶段门与证据 | RED 基线相对缺口及本次补足 |
|---|---|---|
| 1 | 三报表/两指标范围、四类消费查询、源/消费者、分母和业务 owner 签收 | RED 有范围和访谈，但缺正式查询/粒度/证据强度/访问验收 |
| 2 | 三类元数据最小元模型、稳定 ID、混合架构/同步/权限设计获批 | RED 只说“目录”，未比较集中、分布、混合或定义跨源 ID |
| 3–4 | 扫描批次、策展/争议队列、逐边设计/实现/运行证据和差异日志 | RED 有 SQL 阅读与字段图，但缺采集机制、运行实例及每边证据契约 |
| 5 | 双向追溯与真实变更演练，未知边/漏报复核、owner 确认 | RED 有演练意向，但缺遍历规则、版本过滤和未知边阻断 |
| 6 | 权限抽查、覆盖/可信/新鲜度/使用指标、查询演示和运营接管 | RED 有展示/签收，但缺敏感元数据裁剪、持续同步及采纳闭环 |

本次新增能力集中在“目录作为持续运行的数据产品”：业务、技术、运行三类证据分验；集中/分布/混合架构的可解释选择；采集与人工策展分权；逐边血缘的当前代码与运行实例；真实变更演练中的不确定性和漏报；目录自身的质量、安全与使用。RED 原回答已有范围控制、指标口径、样本复算及六周计划，不把这些原有能力计为本技能带来的改进。

## 测试 B：单模型两个字段命名

请求只在一个数据模型中给两个字段命名，没有跨系统资产登记、共享指标口径、血缘或变更影响需求。**`managing-metadata` 不主导，也不启动目录/连接器/采集项目。** 由 `modeling-data` 的命名约定和局部数据字典处理；若日后需要跨系统复用、统一目录或影响追踪，再触发本技能。技能正文“适用边界”明确给出这一路由，负向测试通过。

## 缺口及评测限制

| 级别 | 数量 | 依据 |
|---|---:|---|
| P0 | 0 | 主责和负向边界正确；明确区分设计、部署和运行事实，未知边及敏感内容不会被假装为已验证或默认公开。 |
| P1 | 0 | 目录架构、三类元数据、扫描/策展、逐边证据、影响演练、权限和运营接管均有决策、制品和 No-Go。 |
| P2 | 0 | 现场连接器能力、基线数值、SLA、阈值和实际证据 URI 必须由项目测得并获 owner 批准；技能已提供字段与验收结构。 |

这是静态技能在给定项目情境中的独立应用测试，不能证明真实源连接器、SQL 解析器或元数据平台已运行，也不能证明实际报表数字正确。GREEN 仅证明技能足以引导项目作出可检验的决策、保存证据并正确处理边界。
