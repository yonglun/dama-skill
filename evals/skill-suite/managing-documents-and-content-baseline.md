# 集团合同与客户往来内容治理及实施方案（RED 基线）

## 1. 目标、紧急动作与边界

目标不是建立一个更大的共享盘，而是让集团能够回答：哪些内容存在、谁负责、哪一份是正式记录、为何能访问、何时应保留或处置、收到争议或调查通知后如何立即冻结，以及如何以可重复、可审计的方式检索和移交证据。

由于已收到潜在诉讼通知，项目第一动作应是由法务/合规确认通知适用范围并启动临时保全：暂停可能相关内容的自动删除、邮箱清理、版本淘汰、纸档销毁和迁移去重；保存当时的系统、人员、日期、主题和地点信息；向潜在保管人发出经批准的保全通知并记录确认。先保全、后判定，不能等待完整分类或平台上线。法务决定保全义务、范围、期限和解除；项目团队只执行经授权的技术与运营控制。

本方案是企业内容与记录管理的治理及实施框架，不提供法律意见，不替代适用法律、监管要求、合同义务、隐私要求或律师指示。不是一次性文档编辑、全量扫描或简单搬家，也不承诺仅靠技术自动准确判定法律记录、特权材料或诉讼相关性。

### 纳入范围

- SharePoint 站点与库、部门/个人网盘、邮件及附件、CRM 附件、协作空间、导出文件、备份中的可处置副本，以及纸质合同和客户往来档案。
- 合同草案、审批材料、已签版本、补充协议、变更单、履约通知、客户函件、关键邮件、会议纪要及证明交易或决定的相关记录。
- 内容盘点、分类、受控词表、内容模型、元数据、生命周期、访问与安全、检索、保留、法律保全、处置、e-discovery 接口、迁移、连续性、审计和运营治理。

### 首期明确不做

- 未经业务和法务确认即删除“重复件”、自动认定唯一正式版本，或把全部历史内容一次性迁入新平台。
- 将个人工作便利副本全部升级为正式记录，或把“已备份”等同于“已归档、已保全或可检索”。
- 在内容系统内重做 CRM 交易功能、合同生命周期管理全部能力或法律案件管理；只定义必要接口和责任边界。
- 用搜索命中率代替记录完整性，用扫描图片数量代替纸档治理，用供应商功能清单代替端到端演练。

## 2. 治理原则与目标状态

1. **业务事实决定记录，位置不决定记录**：邮件、CRM 附件或纸张都可能是正式记录；进入 SharePoint 也不会自动成为正式记录。
2. **一项业务事实一个权威记录集合**：合同可由主协议、附件、签署证据和批准记录组成；指定系统、内容 ID 和关系，其他副本可受控引用或按规则处置。
3. **元数据优先、文件夹辅助**：分类、检索、权限、保留和迁移由稳定元数据驱动，不把深层文件夹路径当作唯一语义。
4. **保全覆盖常规生命周期**：有效法律保全阻止销毁和可能破坏证据的变更，但不自动扩大日常访问权限。
5. **最小权限与职责分离**：内容所有者决定业务用途，记录管理制定生命周期规则，法务决定保全，技术执行控制，独立人员验证处置。
6. **证据优于声明**：每次捕获、审批、版本发布、权限变更、保全、导出和处置均应有不可随内容任意修改的日志。
7. **风险分批治理**：先覆盖已保全事项和高价值合同/客户往来，再扩展到低风险历史内容。

目标状态包括：集团内容目录；批准的文件计划和受控词表；统一内容 ID；受控正式库；来源到权威记录的链接；可搜索权限裁剪索引；保留与保全规则引擎；纸电对应台账；经验证的导出、恢复和处置流程；持续运营的责任人、指标和审计。

## 3. 全量盘点与风险基线

先建立“库级盘点”，再对高风险库进行“项目级/文件级剖析”。盘点不应只扫描扩展名，至少记录：系统/站点/邮箱/共享盘/纸库位置，业务用途与流程，业务及技术负责人，用户与权限组，内容类型、数量、容量、时间跨度、格式、语言、版本能力、现有元数据、保留/删除设置、备份、加密、审计能力、外部共享、驻留地、接口、搜索可用性、失效链接和可疑孤儿区。

对邮件应覆盖共享邮箱、离职人员邮箱、PST/本地归档、附件和邮件正文的关系；对 CRM 应区分附件、对象字段、活动历史和外链；对纸档记录箱/卷宗/页级范围、库位、借阅状态、扫描件和原件关系；对 SharePoint 与网盘识别继承权限中断、匿名/外部链接、同步到终端的副本及历史版本。

以内容指纹、业务键、标题、大小、日期和相似度识别完全重复、近重复与版本族，但自动结果只形成候选。仍需结合签署状态、审批链、来源、时间和业务上下文判定。建立风险热力图：诉讼相关性、合同价值、客户影响、个人/敏感信息、访问暴露、无主内容、不可检索、格式不可读、期限冲突、纸档脆弱性和迁移难度。

盘点交付物为：内容源登记册、数据流/副本图、风险与决策台账、潜在保管人清单、保全覆盖矩阵、现有规则冲突清单和首批治理范围。任何扫描工具的只读权限、日志和数据落点必须先获批准，避免盘点本身扩大泄露面。

## 4. 正式记录、版本与副本判定

为每种业务事件制定“记录判定卡”，不得让员工凭文件名猜测。判定卡至少包括：触发事件、必须捕获的组成部分、权威系统、记录所有者、声明时点、业务键、保留类别、敏感级别、审批人、允许格式及关联记录。

| 状态 | 判定与例子 | 控制 |
| --- | --- | --- |
| 正式记录 | 证明承诺、权利义务、批准、决定、交易或监管活动；如双方签署合同、批准链、正式客户通知 | 声明后赋唯一 ID、类别与期限；内容受版本/修改限制；所有权明确 |
| 工作稿/协作件 | 尚在编辑、评论或谈判，仍具业务价值 | 限定工作区、版本和最长工作期；定稿时捕获必要上下文；若被保全则不得清理 |
| 参考/便利副本 | 权威记录的可替换副本，没有新增证据价值 | 显示权威记录链接和副本状态；期限较短；权限不得高于源记录 |
| 重复候选 | 指纹相同或内容相似，但权威性尚未确认 | 隔离为候选，不自动删除；由规则和授权人确认后处置 |
| 短暂内容 | 无持续业务、法律或审计价值的系统通知、临时传输件 | 预先批准的短期规则；受保全或事件调查时暂停删除 |

版本规则区分修订、变体和新记录：编辑同一草案形成小/大版本；已签合同后的补充协议、解除通知和实质变更是关联的新记录；不同客户、法人、语言或签署方版本不得覆盖。正式发布版须记录发布状态、版本号、签署/生效日、审批证据、哈希/完整性信息及被替代关系，界面应明确标出“当前正式版”而不隐藏历史正式版。

## 5. 内容分类、受控词表与内容模型

建立面向业务活动的分层文件计划，而不是按组织架构永久分类。建议顶层为客户关系、合同与商业承诺、交付与履约、争议与索赔、公司治理等；下层按业务活动和记录系列细分。组织变化时业务活动更稳定，也更适合映射保留规则。

受控词表包括：内容类型、记录类别、合同类型、客户/交易对方、法人、业务线、地区、产品/服务、项目/案件、生命周期状态、敏感级别、保留触发事件、处置状态和保全状态。每个术语需有唯一代码、首选名、同义词、定义、上下级/相关关系、所有者、状态、生效日、停用/替换关系和版本。自由标签可辅助发现，但不得驱动保留、权限或处置等强控制。

内容模型采用“共同字段 + 类型字段 + 关系”：共同字段至少包括内容 ID、标题、内容类型、记录类别、业务所有者、保管人、来源系统、原始路径/消息 ID、创建/接收/声明日期、业务键、客户/交易对方、法人、状态、版本、语言、格式、敏感级别、访问组、保留规则/触发日/到期日、保全标志、处置状态、完整性哈希和迁移批次。合同增加合同号、类型、签署方、签署/生效/到期日、自动续期、币种/价值、适用实体及关联补充协议；客户往来增加渠道、收发方向、参与人、主题、关联客户/合同/案件和是否构成正式通知。

字段应定义必填性、数据类型、允许值、来源、默认/继承、验证、可编辑角色、索引用途和质量规则。个人信息、特权/敏感法律材料不应进入对所有用户可见的标签；敏感元数据本身也须权限控制。建立电子记录、纸质原件、扫描影像和保管箱之间的双向关系，不宣称普通扫描件自动等同原件。

## 6. 生命周期：捕获、审批、发布与处置

捕获入口覆盖：受控库上传/模板生成、邮件一键声明或基于规则的建议捕获、CRM 业务事件触发、API 批量接收和纸档登记扫描。捕获时验证最少元数据、病毒/恶意内容、格式可读性、重复候选、权限、来源标识和链路；失败进入隔离队列，不静默丢弃。

关键合同与正式客户通知流程为：起草/接收 → 协作与法律/业务评审 → 授权审批 → 签署或正式发送 → 质量检查 → 声明记录 → 发布/关联业务对象 → 受控修订、续签或终止 → 到期评估 → 处置。审批代理、越级、拒绝、撤回和紧急流程要留理由与身份；数字签名有效性、签署权限和原件要求由有权职能确定。

发布后一般用户不得覆盖正式内容，只能添加关联记录或启动更正流程。更正保留原记录、原因、授权和前后关联。系统自动保存并不等于正式捕获：业务流程必须定义何时形成记录、由谁确认以及捕获失败如何补救。

处置必须由到期计算、保全检查、业务/法务/记录管理审批（按风险设级）、抽样复核和技术执行组成。处置清单包含对象、规则、触发事件、到期计算、所有副本/版本/导出/纸档范围、审批、执行结果、异常及证明；销毁方法匹配介质与敏感级别。无法证明触发日期或副本范围时不得自动销毁，应进入例外队列。

## 7. 访问、安全与隐私

权限采用身份组和角色，不按个人长期授权。默认拒绝，按业务需要、法人/客户隔离、敏感级别和职责配置；外部共享限定对象、期限、下载/再共享能力和审批。记录所有者不能单独授予自己高权并批准其使用；管理员、审计员、保全管理员和处置执行者职责分离。

实施强认证、条件访问、传输/静态加密、受管设备与下载策略、密钥管理、恶意文件检测、DLP/异常访问告警、服务账号治理和定期权限复核。紧急访问限时、需理由并事后复核。离职、调岗、客户/项目结束和外部合作终止应触发撤权及内容所有权转移。

保全副本、搜索索引、缩略图、OCR 文本、导出包、日志、缓存、同步终端和测试环境均属于安全范围。非生产不得默认使用真实敏感内容。隐私请求、数据最小化或删除请求与法定/合同保留及法律保全冲突时，交由隐私与法务职能裁决并记录依据，技术团队不得自行取舍。

## 8. 检索、发现与用户体验

提供按权限裁剪的统一检索，支持关键词、短语、OCR、邮件字段、元数据筛选、业务键、版本族和关联内容浏览；结果明确显示当前正式版、历史正式版、工作稿或便利副本。搜索不得通过标题、摘要、高亮片段、术语建议或数量泄露用户无权知道的内容。

为高价值查询建立同义词、旧客户名/合同号映射、拼写与多语言规则，但词表变更需测试精确率与召回率。无法 OCR 的手写件、加密/损坏文件、嵌入对象、压缩包和特殊格式进入例外队列。用户可反馈“找不到、误分类、权限错误、错误正式版”，由内容管家闭环，而非私下再建共享盘。

检索验收采用已标注测试集：正式合同定位成功率、权限负向测试、查询 p95、索引新鲜度、OCR 质量和零结果率。日常业务搜索与法务 e-discovery 搜索使用不同授权和证据标准，不应混为同一功能。

## 9. 保留、法律保全与可辩护处置

建立经记录管理、业务、法务、隐私/合规批准的保留清单。每条规则记录辖区/法人、记录类别、触发事件、期限、计算方法、例外、适用系统和权威依据；有冲突时由有权职能决定适用规则，系统采用批准后的规则，不由开发人员选择“最长”或“最短”。规则变化应版本化、评估存量影响并可追溯。

法律保全流程为：接收通知 → 法务开立事项并定义主题、日期、人员、系统、关键词/业务键和保全范围 → 识别保管人及数据源 → 暂停相关处置和易失数据丢失 → 发出通知并跟踪确认/追问 → 验证技术保全与缺口 → 定期复审人员、范围和新系统 → 经法务批准解除 → 重新计算而非立即删除。保全应覆盖邮件正文/附件、云版本、聊天或协作内容（若适用）、CRM 对象、纸档、终端/离线文件和离职账户。

避免过度保全：以事项为单位保存范围、理由和复审日；保全状态可叠加，解除一个事项不得释放仍被其他事项、调查、审计或保留规则约束的内容。迁移、格式转换、去重和压缩可能改变元数据或可发现性，涉及保全内容时须经批准、保留原始物和映射并验证完整性。

可辩护处置要求已批准规则、稳定执行、无选择性规避、保全检查有效、授权分离、异常受控、销毁覆盖已知副本并保留处置证明。备份中的到期内容按批准的备份生命周期失效；不得为日常检索恢复，但若受保全或依法要求则按法务指示隔离和保存。无法技术删除的介质要记录风险、补偿控制和最终退出日期。

## 10. e-discovery 与调查接口

内容平台向案件/调查团队提供受控接口，而非让其直接取得全局管理员权限。接口能力包括：按事项冻结、保管人和源清单、搜索条件版本、命中统计、抽样、重复/近重复族、线程关系、权限及保全状态、原生文件和可读呈现、附件关系、完整元数据、哈希、时区、导出清单、错误/遗漏报告和审计日志。

收集与导出保留证据链：请求人、授权、执行人、时间、工具/版本、来源、范围、过滤、对象数与容量、哈希、传递人、存储位置及每次访问。特权审查、相关性判断、披露格式、遮盖/脱敏和对外生产由律师或获授权团队决定；平台只保证可重复收集、完整性和可说明限制。定期用已知样本演练“识别—保全—收集—导出—校验—交接”。

## 11. 业务连续性、恢复与纸档保障

按业务影响为捕获、读取、审批、签署、检索和保全分别确定 RTO/RPO 与最低服务。高可用不能替代备份，备份不能替代法律保全。备份须覆盖内容、版本、元数据、权限、工作流、词表、保留/保全状态、审计日志和加密密钥，并在隔离环境执行恢复演练。

定义平台不可用时的受控离线模板、临时编号、审批证据和事后补录/对账；避免员工转入无人管理的私人邮箱或网盘。灾后恢复验证业务键、版本关系、权限、搜索索引、保全标志和处置计时，不只验证文件能打开。纸档需要防火防水、环境控制、条码/库位、借阅链、异地关键副本和灾损处置；纸档外包商纳入连续性、访问和销毁验证。

## 12. 迁移与退役

迁移以记录类别/业务批次分波进行：发现与冻结范围 → 清理候选和规则确认 → 源到目标字段/词表映射 → 试迁 → 数量、哈希、元数据、权限、版本、关系与搜索对账 → 业务/记录管理/法务抽样验收 → 增量同步和切换 → 只读观察期 → 源退役。原路径、源 ID、消息 ID、创建/修改/接收时间、保管人、版本和审计上下文应尽量保真，任何变换记录在迁移清单。

对不支持格式、密码文件、损坏件、孤儿内容、未知所有者、期限冲突和受保全内容设隔离队列与人工决定。迁移期间禁止用“最新修改时间”重置保留触发。只有当目标完整、权限正确、保全与处置可运行、恢复已验证且源端仍有批准的回退窗口后，才能停写和退役；源销毁需另行批准并留下证据。

## 13. 角色与责任

| 角色 | 主要责任与决策权 |
| --- | --- |
| 高管赞助人/内容治理委员会 | 批准范围、资源、集团政策、重大例外和跨单位争议；接受剩余业务风险 |
| 业务记录所有者 | 定义记录组成、权威来源、访问需要和业务触发；批准分类与业务验收 |
| 记录管理负责人 | 维护文件计划、判定卡、保留清单、处置流程和证据；可暂停不合规处置 |
| 法务/e-discovery 负责人 | 判断保全和案件范围、通知保管人、批准变更/解除及对外生产；不把法律判断委托给系统 |
| 隐私、合规与信息安全 | 确认敏感分类、访问/共享/跨境/隐私控制及冲突升级；开展二线监督 |
| 内容管家/部门协调员 | 维护词表和元数据质量，处理捕获、检索、孤儿与重复候选，培训用户 |
| 平台/集成/搜索团队 | 实现捕获、版本、权限、索引、保留、保全、日志、接口、恢复和监控 |
| 业务系统所有者（CRM/邮件等） | 保证来源事件、业务键、附件关系和接口，配合冻结、迁移和退役 |
| 审计/风险 | 独立抽查控制设计、执行证据、例外和指标，不代替一线审批 |
| 用户/保管人 | 按规则捕获、保护并移交内容，响应保全通知；不得自行清理潜在相关材料 |

每项关键活动必须指定主责、批准人、替补、服务队列和时限，尤其是保全开立/解除、离职保管人、权限紧急撤销、搜索失败、迁移异常、处置执行、恢复演练和供应商升级。

## 14. 分阶段实施与阶段门

| 阶段 | 周期与活动 | 退出证据与门槛 |
| --- | --- | --- |
| G0 紧急保全 | 0–48 小时：法务定范围，暂停相关删除，锁定保管人与源 | 事项 ID、批准范围、通知/确认、系统冻结证据、已知缺口和升级负责人；未验证不得开始去重/迁移 |
| G1 发现与授权 | 第 1–3 周：盘点、风险分层、治理章程、角色和目标范围 | 关键源 100% 有所有者或升级项；保全覆盖矩阵、现状基线、批准的首批范围与 RACI |
| G2 分类与控制设计 | 第 4–6 周：文件计划、词表、内容模型、记录判定、保留映射、权限模型 | 首批记录类别端到端规则获业务、记录管理、法务/合规、安全批准；冲突有决定人和期限 |
| G3 原型与试点 | 第 7–10 周：配置捕获/审批/发布、检索、保全、审计，试点一类合同和客户往来 | 正负权限、版本、正式记录、搜索、冻结/解除模拟、处置模拟、导出和恢复测试均有原始证据 |
| G4 迁移与运营就绪 | 第 11–16 周：分批迁移、纸档登记、培训、支持、连续性与运行演练 | 数量/哈希/元数据/权限/搜索对账达批准阈值；保全内容零误删；运行团队可独立处置代表性事件 |
| G5 推广与退役 | 按风险滚动：扩大类别/地区，观察后退役来源，持续审计 | 业务和控制职能签收；无阻断缺陷；源端有批准退役/销毁记录；遗留风险有所有者与到期日 |

阶段门结论只允许通过、有条件通过或不通过；有条件通过必须列补偿控制、风险接受人和到期日。任何保全缺口、未授权暴露、正式版不可判定、不可恢复、迁移对账失败或处置无法阻断均为 No-Go。

## 15. 运营指标与审计证据

| 维度 | 指标示例 |
| --- | --- |
| 盘点覆盖 | 已登记源/站点/邮箱/纸库占比；无主库数量；高风险源完成细化盘点比例 |
| 捕获与正式记录 | 应捕获业务事件中按时声明比例；缺失组成件；捕获失败/隔离积压；正式版误判率 |
| 元数据与分类 | 必填完整率、受控值合规率、错误类别率、词表变更处理时间、未知期限对象数 |
| 访问与安全 | 过度授权、外链、孤儿权限、逾期访问复核、异常下载、离职撤权时长及负向测试通过率 |
| 搜索 | 已标注样本的精确率/召回率、正式记录首屏命中率、零结果率、索引延迟、p95 响应、权限泄露为零 |
| 保留与保全 | 规则覆盖率、通知确认率、系统冻结验证率、保全缺口/逾期复审、误删事件、解除后重算正确率 |
| 处置 | 到期积压、按期批准/执行率、异常率、全部副本覆盖率、处置证明完整率；不以删除数量作为成功目标 |
| 迁移与连续性 | 数量/哈希/元数据/权限对账差异、不可读率、RTO/RPO 实测、恢复后搜索与保全校验通过率 |
| 运营采用 | 培训/测验、私建库趋势、用户反馈关闭时长、例外数量/龄期、重复候选处理准确率 |

审计事件至少覆盖登录与失败、查看/下载（按风险）、创建/修改/删除、版本/状态、元数据、权限/外链、管理员操作、搜索与导出、保全、保留规则、处置、恢复和迁移。日志需集中、时间同步、防篡改、权限分离并按批准期限保留；敏感搜索词和案件信息也需受限。每月由运营评审积压和异常，每季度由治理委员会评审指标/例外，每年至少按风险进行独立控制测试、保全演练、恢复演练和保留清单复审。

## 16. 方案边界与验收结论

内容治理不能替代合同谈判、签署授权、客户主数据治理、案件策略、隐私法律分析、网络安全事件响应或业务系统数据质量，但必须与这些流程建立触发和证据接口。工具可推荐分类、重复和相关内容，最终高风险判定仍需具名责任人。供应商认证、不可变存储或 AI 搜索不自动证明合规、真实性、完整性或可采性。

验收报告必须列：适用范围和排除项、各阶段门结果、规则/配置版本、保全事项与覆盖证明、抽样方法和实测指标、迁移/恢复/e-discovery 演练、未关闭缺陷、例外及到期日、源退役状态、常态负责人和下次复审日期。项目结束标准是控制已运行且有人持续负责，不是政策发布或文件搬完。

## 17. 容易遗漏的事项

1. 邮件正文可能是记录，附件单独入库会丢失发送者、收件人、时间和业务语境。
2. 共享链接、同步终端、导出压缩包、打印件和聊天转存会形成受控库之外的副本。
3. 已签合同的签署证书、信封审计轨迹、附件顺序和签署权限证据可能与 PDF 同等关键。
4. 同一内容受多个保全事项约束，解除一个事项不能触发立即删除。
5. 离职、并购、法人更名和邮箱别名会破坏保管人与客户检索，需要身份历史映射。
6. 自动续期、终止、结案、客户关系结束等保留触发事件常不在内容平台，接口失败会导致期限不启动。
7. OCR 会误读手写、印章、表格和低清扫描；原件位置、扫描质量和例外必须可查。
8. 时区、邮件接收时间、签署日、生效日和系统修改日不可混用，迁移也不得全部改为迁移日期。
9. 搜索索引、缩略图、缓存和 AI 向量表示可能泄露已撤权或已处置内容，需同步清除和验证。
10. 加密、密码保护、专有老格式、嵌入对象和损坏文件会造成“已迁移但不可读”。
11. 去重可能删除带有独立批注、路径语境、权限、保管链或时间证据的近重复件。
12. 备份恢复会把已到期内容或旧权限带回生产；恢复后须重放保全、处置和权限变化。
13. 纸档借出、异地仓储和第三方销毁证书常与电子台账脱节，应纳入统一审计链。
14. 法务特权、商业秘密和个人信息标签本身可能敏感，不应让全员通过搜索筛选看到。
15. 季节性批量签约、诉讼高峰、平台许可与 OCR/索引成本会影响容量和服务目标。
16. “无命中”不代表内容不存在；必须同时报告未索引源、失败格式、日期缺口和搜索限制。
