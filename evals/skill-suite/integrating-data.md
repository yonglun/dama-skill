# `integrating-data` 独立 GREEN／边界评估

## 总结论

**GREEN：无 P0、无 P1、无 P2，无阻断缺口。**

测试 A 的核心是跨 CRM、计费与湖仓的数据移动、契约、状态、恢复和发布，
应由 `integrating-data` 主导。
技能正文和手册能直接生成模式决策、契约与映射、状态与重放、三层对账、
schema 演进、血缘、共享协议、SLO 和阶段门，达到八周项目所需的执行深度。

测试 B 只要求湖仓数据库的备份恢复、容量、可用性和 DBA 值班，
应由 `operating-data-storage` 主导；本技能仅在管道恢复顺序或水位重建时协同。

## 评估依据与判级

已完整读取并交叉检查：

- `skills/integrating-data/SKILL.md`；
- `skills/integrating-data/references/playbook.md`。

判级口径：

- P0：错误主责、无证据上线、不可恢复或错误发布，阻断 GREEN；
- P1：关键控制缺失，高概率导致方案不可实施或不可验收；
- P2：不阻断交付，但需项目自行补足的模板或表达缺口。

## 测试 A：CRM／计费八周进入湖仓

### 1. 主责与协同边界

`integrating-data` 应主导端到端数据流。
`modeling-data` 裁决客户、联系人、计费账户、发票的粒度、键和业务语义；
若要跨源身份解析或黄金客户，由 `managing-reference-and-master-data` 主导该部分；
`improving-data-quality` 批准质量阈值，`managing-metadata` 发布血缘，
`securing-data` 审批联系人和发票共享，`operating-data-storage` 负责目标实例运行。

本技能没有越界替业务 owner 裁决语义，仍负责把获批语义落实为契约、映射、
状态、对账、重放和发布，主责清楚。

### 2. 模式选择的代表性执行证据

| 数据流 | 建议模式 | 关键理由／限制 |
|---|---|---|
| CRM 初始客户／联系人 | API 全量快照至不可变原始层 | 建审计和重放基线；处理分页、限流、快照漂移 |
| CRM 日常增量 | 优先 CDC；否则稳定游标增量 API／微批 | 记录 token／水位；超 CDC 保留期重建快照 |
| 关键客户 CRM 变化 | CDC／事件；能力不足则短周期微批 | 只为有业务时限的数据承担低延迟成本 |
| 计费账户／发票 | 带 manifest、校验和、控制总额的夜批 | 源只有夜批，不伪装成实时；支持整批重放 |
| 湖仓发布 | 暂存验证后切换分区／版本指针 | 消费者不读取半批；失败保留上一合格版本 |

“每日 7 点”必须拆为源到达、处理完成和合格发布三个时间点。
CRM 与计费分别暴露水位和新鲜度。
计费无日内能力时，关键客户近实时默认只覆盖 CRM 变化；
若业务要求发票近实时，则降目标、改源能力或 No-Go，不能把批源包装成实时。

手册提供时限、耦合、事务、顺序、源负载、重放、成本和运维等选型维度，
也要求模式／理由／回退登记，故模式选择可执行，**通过**。

### 3. 契约、映射与语义冲突

至少建立 CRM API／CDC、计费夜批、湖仓发布数据产品三类版本化契约。
契约覆盖粒度、键、操作／删除、schema、类型／精度、枚举、时区、空值、
API 分页／限流、文件清单／控制总额、水位、到达窗口、质量、保留、错误和弃用。

字段映射表覆盖业务定义、源字段、类型、转换、优先级、代码、空值、时间、
质量、分类、owner、版本和生效日期，可处理状态码、币种、金额精度和时区冲突。

键冲突应按以下方式处理：

- 保留带命名空间的 `crm_customer_id`、`billing_account_id` 等源键；
- 湖仓内部键与跨源 crosswalk 分离，不把一个源键冒充企业客户键；
- 客户、联系人、账户和发票分别声明粒度、唯一性及关系；
- 权威字段、代码优先级和例外由数据 owner／建模或主数据责任人批准；
- 未裁决冲突隔离或保留源事实并列，不静默覆盖。

正文明确将实体粒度、键和业务结构冲突交给 `modeling-data`，
将身份解析和黄金记录交给主数据技能，本技能只实现获批语义，**通过**。

### 4. 状态、幂等、失败与受控重放

最小运行状态应包含：

- CRM 快照 `run_id`、快照时点、页游标、请求范围；
- CDC 分区、起止 token、事件 ID、源提交／落地时点；
- 计费 `batch_id`、业务日期、manifest、校验和、控制总额；
- 实际使用的 schema、映射、代码和作业版本；
- 暂存、隔离、合格、已发布、回退状态及消费者版本。

幂等键可用事件 ID、`源命名空间 + 源键 + 源版本`，
或稳定行键加批次版本；merge／版本化写入、发布切换和通知也要去重。

瞬时网络／限流错误做有界退避；坏 schema、未知代码、缺键、金额非法等
确定性错误进入隔离／死信，不无限重试。
重放记录发起人、理由、范围、原始输入和代码／schema／映射版本，
先影子验证，再三层对账，最后原子替换并抑制重复副作用。

断点续传、重复事件／文件、部分页失败、CDC 乱序／缺口／超保留期、
源晚到、删除、更正、补数和回退均在手册的验证范围内，**通过**。

### 5. 三层对账与发布门

| 层级 | CRM／计费代表性检查 | 基准与阻断 |
|---|---|---|
| 记录级 | 键、字段哈希、引用、删除／冲销、发票金额 | 原始源；缺键、重复、非法引用按阈值阻断 |
| 分组级 | 日期、状态、地区、关键客户、币种、账户的行数与金额 | 源业务分组；差异分类、有 owner、超容差阻断 |
| 总量级 | 起止水位、事件／文件数、总行数、金额控制总额 | 源 owner 的清单／控制；不一致阻断 |

技能明确禁止只对比相邻层，防止共同复制错误后的假通过。
对账和质量门通过后才原子发布；失败保留上一合格版本并标记陈旧，**通过**。

### 6. Schema 演进与血缘

契约需规定兼容级别、版本、通知、弃用和消费者迁移。
新增可空字段、类型扩大或枚举扩展先做影子和消费者契约测试；
字段删除、改名、精度或语义变化走新版本并行。
未知或不兼容 schema 隔离；手册将“破坏性 schema 未兼容”列为 No-Go。

血缘链为：
`源契约/版本 → 原始批次/事件 → 作业/代码 → 映射/规则 → 目标字段/发布版本 → 消费者`。
每条记录可反查 `run_id`、`batch_id` 或 `event_id`，
既支持结果逆查，也支持源字段变更的消费者影响分析，**通过**。

### 7. 共享协议与 SLO

共享协议覆盖允许／禁止用途、对象／字段／粒度、权威源、刷新／质量、
分类／访问／地域、保留／删除、再共享／导出、变更／弃用、差错通知、
升级、暂停／终止和退出处置；生产者、集成服务、消费者责任分别签署。

可执行 SLO 按对象定义测量点、窗口、分母、基线、目标、数据源、owner 和升级：

- 计费约定到达后至 07:00 合格发布的成功率；
- CRM 源提交至合格发布的新鲜度分位数；
- 关键客户事件至发布的 P95／P99 延迟及积压上限；
- 三层对账通过率、未解释差异、重复／缺口、死信老化；
- 最近合格版本可用率、消费者读取成功率和恢复时限；
- 处理量、单位成本、人工干预和接口／规则复杂度。

监控可区分源到达、传输、转换、目标和消费问题；
源晚到仍触发陈旧标记、升级和通知，而不是伪装成管道成功，**通过**。

### 8. 八周阶段门的充分性

代表性门禁为：范围／SLO → 源发现和语义裁决 → 模式／契约／映射 →
薄切片接入／状态／血缘 → 三层对账／原子发布 → 故障／重放／schema 兼容 →
试运行／共享协议／运行接管 → 消费者切换。

语义未决、控制总额不符、重跑重复、无合格版本降级、
破坏性 schema 未兼容或运行无人接管均为 No-Go。
因此技能不只列关注点，还要求签署制品、测试证据和运行接管，**通过**。

### 测试 A 结论

八项受测能力均有明确决策、制品、owner、异常路径和验收证据，
测试 A 判定为 **GREEN**。

## 测试 B：仅湖仓数据库运行

备份恢复、容量、可用性和 DBA 值班属于持久平台与实例运行，
正确主责是 `operating-data-storage`：负责备份策略、恢复演练、容量预测、
HA／DR、监控、事件响应、变更、值班与接管。

只有出现跨系统复制、恢复后的水位重建、管道重放或上下游恢复顺序时，
`integrating-data` 才作为协同技能提供依赖和校验，不应扩展出集成平台建设。

正文明确写出“数据库容量、备份恢复和实例运行由 `operating-data-storage` 主导”，
手册再次要求双方共同确定窗口和恢复顺序，路由一致，测试 B **GREEN**。

## 缺口及严重级别

| 级别 | 发现 | 判定 |
|---|---|---|
| P0 | 无 | 主责、恢复、发布硬门和边界均正确。 |
| P1 | 无 | 八项能力均有流程、模板、证据和 No-Go 条件。 |
| P2 | 无 | 待填项目参数不是技能缺陷；现有模板足以裁剪执行。 |

## 最终判定

**GREEN（无 P0、P1、P2；无阻断缺口）。**

测试 A 可形成混合 API／CDC／夜批的可运行集成方案，
且不会虚构计费近实时能力；测试 B 能正确退让给存储运行技能。
