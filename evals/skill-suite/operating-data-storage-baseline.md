# 新分析数据库六周生产就绪方案（RED 基线）

## 1. 任务定位、成功定义与约束

当前已有逻辑数据模型和平台选型，但这两项只证明了“要存什么”和“准备用什么”，并不构成生产就绪。六周目标是把首期分析数据库建设为一个可部署、可恢复、可观测、可值守、可审计的生产服务，并完成业务、技术、安全和运行团队共同签署的上线决定。

生产就绪的最低定义是：已确定首期负载与数据边界；开发、测试、预生产和生产环境具备必要隔离；物理设计和容量经代表性数据验证；所有变更可重复部署并可回退；可用性、RTO、RPO 和服务时段已由业务批准；备份能够实际恢复；保留与销毁可执行且留有证据；性能达到约定指标；监控、告警、事件分级、值班和供应商升级链路能工作；运行团队已经完成接管。任何关键门槛未通过，项目必须延期、缩小上线范围或在有明确补偿控制和到期日的情况下由有权人书面接受剩余风险，不能仅以日期压力放行。

### 本期范围

- 首批已批准的分析主题、事实/维度数据及其必要的暂存、审计、元数据和作业状态数据。
- 一套生产数据库及配套的开发、测试、预生产环境，涵盖账户/项目、网络、身份、密钥、计算、存储、参数、配额和日志边界。
- 从批准源到数据库、再到首批消费接口的端到端运行链路，包括批量装载、重跑、数据质量阻断和查询服务。
- 物理模型、分区/聚簇/索引、压缩、统计信息、工作负载隔离及数据生命周期配置。
- 配置和模式变更发布、备份恢复、高可用/灾备、性能与容量、监控告警、事件处理、值班、供应商支持和运行移交。
- 对首批数据的分类、访问、加密、审计、保留、归档、法律保全和可验证删除控制。

### 六周内明确不承诺

- 不把所有企业数据域、全部历史数据、所有报表或临时分析迁入首发范围。
- 不进行平台重新选型，也不在本期建立企业级主数据、全域目录或全面数据治理组织；只实现该数据库上线必需的最小治理控制。
- 不承诺未经工作负载基线验证的无限并发、实时服务、跨地域零数据丢失或“永不宕机”。
- 不重构所有上游源系统，也不为未知消费者优化；已发现的上游问题进入责任明确的后续清单。
- 不以备份存在代替业务连续性，不以厂商 SLA 代替端到端服务目标，不以一次性能测试代替持续容量管理。

## 2. 启动时必须确认的输入与假设

第 1 周的首要工作不是建表，而是消除会使后续指标失真的未知项。至少确认：业务服务时段和关键月结/季末窗口；首期用户、查询工具、预计并发与查询类型；初始数据量、日增量、保留期和三至十二个月增长；装载批次、刷新截止时间和允许重跑窗口；敏感数据类别、驻留地点和删除义务；上游可用窗口及下游依赖；平台各层 SLA、配额、限制与支持等级；允许的停机窗口；预算或成本上限；现有企业 IAM、密钥、日志、工单、监控和应急机制。

如果缺少实际负载，使用经过记录的保守假设构造首期模型，例如“初始体量、峰值日增量、典型/重型查询、并发用户、月末放大倍数”，并在预生产以合成数据和脱敏样本校准。所有假设必须有负责人、验证日期和超出假设时的扩容或降级动作。禁止把未经确认的数字写成业务承诺。

## 3. 六周计划与阶段门

| 阶段 | 周次与核心活动 | 必须交付的证据 | 阶段门与决定者 |
| --- | --- | --- | --- |
| G0 启动与风险定标 | 第 1 周前半：冻结首期数据和消费者边界；收集负载、增长、合规、服务时段与依赖；任命服务负责人和运行负责人 | 经批准的范围、依赖图、假设/决策/风险台账、初版 RACI、关键业务日期和禁止变更窗口 | **进入设计**：业务服务负责人确认用途和重要性；安全/隐私确认分类；平台负责人确认资源与支持可用 |
| G1 服务与恢复目标 | 第 1 周后半：完成容量模型、环境拓扑、HA/DR 方案、备份保留方案、RTO/RPO、SLO、事件级别和成本估算 | 服务级别草案、故障模式分析、容量与成本模型、恢复策略、数据生命周期矩阵、适用平台限制清单 | **设计批准**：业务负责人接受 RTO/RPO 和降级；安全/合规批准控制；运行负责人确认可运营；未批准则不得采购或按错误目标实施 |
| G2 平台基础与发布通道 | 第 2 周：用 IaC/受控脚本建立开发、测试、预生产；配置网络、IAM、密钥、审计、监控骨架、配置基线和发布流水线 | 代码评审记录、环境差异清单、权限负向测试、审计日志样本、从空环境重复部署记录、秘密扫描结果 | **平台就绪**：平台/安全负责人签署隔离和最小权限；关键资源不得只靠控制台手工创建且无记录 |
| G3 数据与变更就绪 | 第 3 周：把逻辑模型转为物理模型；完成分区/索引/统计、数据装载、幂等重跑、模式版本和向前/回退迁移；建立质量门禁 | 物理设计评审、源到目标映射、数据对账、模式迁移测试、失败重跑证明、回退演练、血缘与批次追踪样本 | **候选版本**：数据所有者批准口径和对账；工程负责人证明变更与回退；阻断质量缺陷为零或有书面例外 |
| G4 非功能与恢复验证 | 第 4 周：用代表性数据和并发做基线/峰值/耐久/故障测试；执行备份恢复、时间点恢复、节点或区域故障演练；测量监控覆盖与成本 | 原始测试结果、查询计划、资源曲线、恢复时间线、校验和/行数/业务对账、告警到工单证据、缺陷及复测记录 | **预生产退出**：达到经批准的性能、RTO/RPO、数据完整性与告警阈值；只创建了备份但未恢复验证视为失败 |
| G5 运行接管与上线准备 | 第 5 周：演练发布、回退、数据延迟、容量告警、访问撤销、安全事件与供应商升级；完成 runbook、值班表、培训、UAT 和变更冻结 | 演练记录及时间戳、值班人员确认、知识测验/跟班记录、访问复核、未决问题、变更单、上线/回退清单和沟通模板 | **Go/No-Go**：服务负责人、数据所有者、工程、运行、安全共同签字；运行团队可独立处理代表性事件才可接管 |
| G6 生产发布与稳定化 | 第 6 周：按窗口发布；分阶段开放消费者；加强监控与每日复盘；完成最终资产登记、交接和遗留风险接受 | 发布日志、烟雾测试、首批数据对账、SLO 仪表盘、事件记录、业务签收、CMDB/目录/工单队列、交接确认 | **转入常态运行**：连续达到约定稳定期（建议至少 5 个业务日/一个关键批次周期），无未受控 P1/P2；服务所有者接受剩余风险 |

阶段门是停止点而不是例会汇报。每个门必须记录结论、证据链接、批准人、未决条件和到期日。若六周内不能验证跨地域恢复等高成本能力，应明确降低首发服务等级或缩小数据范围，而不是在文件中假定其已具备。

## 4. 角色、职责与决策权

| 角色 | 核心职责 | 决策权/签署点 |
| --- | --- | --- |
| 业务服务负责人/赞助人 | 明确业务影响、服务时段、关键日期、可接受降级与预算；协调消费者 | 批准范围、SLO、RTO/RPO、上线与剩余业务风险；跨团队争议终裁 |
| 数据所有者/数据产品负责人 | 确认用途、口径、质量阈值、保留和消费者；组织业务验收 | 批准数据进入生产、质量例外及数据生命周期要求 |
| 数据库/平台工程负责人 | 环境、物理设计、性能、容量、HA、备份、自动化、升级与故障处理 | 批准技术设计；对不可恢复或不安全的发布有暂停权 |
| 数据工程负责人 | 装载、转换、幂等、批次追踪、对账、质量与血缘 | 签署端到端数据链路、重跑和模式兼容性 |
| SRE/基础设施与网络 | 网络、身份集成、可观测性、资源配额、可靠性测试 | 签署平台可用性、告警路由和基础设施变更 |
| 安全、隐私、合规/记录管理 | 分类、最小权限、加密、审计、驻留、保留、法律保全和销毁 | 对受限数据处理与高风险例外有批准或否决权；法规结论由有权职能作出 |
| 变更经理/发布经理 | 变更日历、审批、发布编排、回退触发和沟通 | 确认发布授权、冻结冲突和回退启动流程 |
| 运行负责人/值班团队 | 监控、事件、请求、备份检查、容量、补丁、服务报告和持续改进 | G5 正式接受或拒绝接管；按 runbook 启动应急处置 |
| 业务消费者代表 | 验证查询、数据新鲜度、已知限制和降级体验 | UAT 签收；不能代替数据所有者批准风险 |
| 平台厂商/托管服务支持 | 提供产品限制、升级通知、严重事件升级与故障分析 | 不承担企业内部数据口径、业务连续性或风险接受责任 |

每项日常任务还应有主责和替补：用户/服务账号创建与撤销、证书/密钥轮换、每日备份检查、恢复演练、失败装载、长查询、空间告警、性能退化、补丁升级、审计导出、法律保全、删除证明和供应商工单。只有团队名称而无具名值班人、队列和替补，不视为已分配责任。

## 6. 服务指标与初始门槛

最终数值必须由业务影响分析、平台能力和实际压测共同确定。以下是首轮讨论与验证框架，而不是在缺乏基线时凭空承诺的 SLA。

| 维度 | 指标与建议定义 | 上线前证明方式 |
| --- | --- | --- |
| 可用性 | 在约定服务窗口内，数据库可连接且认证查询成功的分钟占比；区分计划内维护是否计入 | 合成查询持续检测；明确排除规则和数据来源；不能只引用厂商控制面的可用率 |
| 数据新鲜度 | 从源数据业务时间到认证数据可查询的延迟；例如日批须在业务批准的截止时间前完成 | 至少连续 5 个业务日或一个完整关键周期记录到达、处理、发布时戳 |
| 数据完整性 | 关键表行数、金额/数量控制总额、主键唯一、必填完整和重复率 | 每批自动对账；阻断阈值、例外人和失败后的旧版本可用策略明确 |
| 查询性能 | 按查询等级记录端到端 p50/p95/p99、超时率、扫描量、队列等待和并发 | 预生产按预计峰值并发及增长情景压测；不能只测单用户暖缓存查询 |
| 装载性能 | 每批数据量、吞吐、完成时间、重跑时间和对在线查询影响 | 峰值日增量和补数/重跑并发场景通过；落在维护/刷新窗口内 |
| 恢复能力 | RTO 从事件宣布到最低业务服务恢复；RPO 为可接受的最大数据丢失点 | 计时恢复演练；验证应用连接、权限、作业、数据对账和消费者查询，而非只看数据库实例启动 |
| 备份健康 | 计划成功率、备份年龄、校验状态、恢复成功率和恢复演练间隔 | 上线前至少一次完整恢复和一次时间点/增量恢复（平台支持时）；失败告警进入工单 |
| 变更质量 | 部署成功率、变更失败率、回退率、紧急变更率和平均恢复时间 | 预生产部署/回退记录；生产变更全部关联版本、审批、测试和责任人 |
| 运营响应 | P1/P2 确认、通知、缓解和恢复时间；告警误报/漏报；值班覆盖 | 告警注入及事件桌面演练；轮值表、升级树和替补有效 |
| 容量与成本 | 存储/计算/并发使用率、增长偏差、单位 TB/查询/批次成本、预算预测 | 仪表盘和阈值测试；越过阈值能形成扩容或优化工单，且提前量足够 |

严重级别可先约定为：P1 为数据泄露、不可恢复风险、关键数据库全不可用或错误数据已影响重大决策；P2 为错过关键刷新、核心查询不可用、质量阻断或容量迫近硬限制；P3 为有绕行的局部退化；P4 为一般请求。每级必须定义确认、通知、缓解、更新频率、业务沟通和复盘要求。服务目标应同时说明测量点、窗口、分母、数据源、豁免和责任人，否则无法执行。

## 7. 关键技术与运营控制

### 容量、性能与工作负载

容量模型至少纳入主数据、历史数据、索引/物化结果、时间旅行、临时空间、ETL 中间结果、副本、备份、审计日志和增长裕度，不能只用逻辑表大小。分别估算正常日、月末/季末、集中补数和恢复期间的计算、I/O、网络和并发。为装载、BI、数据科学和管理任务设置工作负载隔离、优先级或资源保护，防止一个失控查询拖垮刷新作业。保存高价值查询的执行计划和基线，明确统计信息、碎片/聚簇、分区、小文件、缓存和资源队列的维护频率。

### 环境、配置和变更发布

生产数据不得复制到非生产，除非有批准的脱敏、最小化和访问控制。环境应使用同一自动化定义但采用明确参数差异；生产变更经代码评审、自动测试、预生产验证和审批。对加列、改类型、删除/重命名列、重分区、回填、索引构建等分别定义在线性、锁、存储放大和回退方式。破坏性变更采用扩展—迁移—收缩：先新增兼容结构，迁移和双读/验证，消费者切换后再在独立变更中删除旧结构。重大版本升级应记录兼容矩阵、驱动/BI 客户端测试和供应商支持窗口。

### 可用性、灾备和恢复

根据业务影响选择同故障域副本、跨可用区或跨地域方案，不默认“云服务即高可用”。识别共享故障点：身份、DNS、密钥、网络、调度、对象存储、连接池、元数据目录和 BI 工具。HA 解决局部故障，备份解决误删/损坏，DR 解决站点级中断，三者不能互相替代。运行手册要给出故障判断、切换权限、数据一致性检查、DNS/连接更新、回切、沟通和证据保留。

### 备份、保留与可验证处置

先按数据类别、业务和法律要求建立保留矩阵，再把规则配置到主库、历史/时间旅行、暂存、导出、备份、副本和日志；不能只删主表。备份与生产权限、账户或故障域适度隔离，密钥和恢复凭据同样纳入恢复测试。恢复验收包括结构、权限、行数/校验和、控制总额、最新可用点、应用查询和下游重连。销毁需处理级联副本、缓存、导出和过期备份，并保留不可抵赖的删除证据；法律保全必须能暂停自动删除且有授权和解除流程。

### 监控、告警与运行移交

监控覆盖平台健康、连接、错误、锁/阻塞、查询延迟、并发/队列、CPU/内存/I/O、存储及增长、复制滞后、备份年龄、装载延迟、质量、成本、权限异常和审计失效。每个可操作告警对应阈值依据、负责人、runbook、升级和抑制规则；仅有仪表盘没有通知不算监控。上线前完成“项目团队不直接操作，由未来值班人员处置”的影子值班。移交后服务负责人每周查看稳定期指标、每月评审 SLO/容量/成本/变更/事件、每季度或按风险频率演练恢复和复核访问。

## 8. Go/No-Go 清单与上线后护栏

上线会议必须逐项回答并附证据：首批范围和消费者是否冻结；业务是否批准服务时段、SLO、RTO/RPO 和降级方式；所有生产资源是否受版本和配置管理；生产权限是否完成复核；数据能否从源到查询端对账；候选版本是否完成发布和回退；备份是否实际恢复；峰值/耐久/故障测试是否通过；告警是否到达当班人员；runbook 和联系树是否可用；厂商支持是否开通；是否避开关键业务与平台维护窗口；回退触发阈值和最后决策时间是否明确；未关闭问题是否都有业务影响、补偿控制、责任人、到期日和批准人。

发布采用小步开放：先运行内部验证和只读烟雾测试，再开放受控用户组，确认首批装载和查询指标后逐步扩展。稳定期内冻结非必要变更，提高备份检查、容量检查和服务报告频率。触发回退的条件应事先量化，例如数据对账超过阻断阈值、核心查询持续超时、恢复点不可验证、权限越权或无法在批准时间内缓解的 P1/P2。回退后保留证据并由变更经理协调重新发布，不能在现场无限修补。

## 9. 主要风险与应对

| 风险 | 早期信号 | 控制/缓解 | 升级或停止条件 |
| --- | --- | --- | --- |
| 六周期限驱动“先上再补运营” | 恢复、值班、容量任务持续后移 | 将恢复、性能、告警、移交设为硬门；按风险削减数据/消费者范围 | G4 或 G5 关键证据缺失则 No-Go，不以承诺后补替代 |
| 负载未知导致规格错误 | 数据增长、重查询或并发无所有者 | 第 1 周建模并记录假设；第 4 周代表性压测；设置扩容前置阈值 | 峰值测试超门槛且无可验证优化/扩容计划则暂停 |
| 逻辑模型无法直接高效落地 | 数据倾斜、全表扫描、批次超窗 | 物理设计评审、样本分布分析、查询计划基线、分区/索引验证 | 核心刷新或查询不达目标则调整设计或缩小首发范围 |
| 平台托管能力被误当成端到端连续性 | 只引用厂商 SLA，无依赖和恢复演练 | 建立依赖图、故障模式和端到端恢复演练 | 任一关键身份/网络/密钥/调度依赖无法恢复则不得宣称达到 RTO |
| 备份可见但不可恢复 | 备份作业成功却未测试密钥、权限或完整性 | 隔离恢复、PITR、数据对账、恢复凭据测试 | 无成功恢复证据为上线阻断项 |
| 变更破坏消费者或长时间锁表 | 无兼容策略、无回退脚本 | 版本化契约、扩展—迁移—收缩、预生产回放、变更窗口 | 破坏性 DDL 无经测试回退或前滚策略则拒绝发布 |
| 保留与删除只作用于主库 | 副本、备份、导出和暂存未盘点 | 生命周期矩阵、法律保全、级联删除和证据 | 受监管数据的期限/处置未获有权职能确认则不载入生产 |
| 告警过多或无人接收 | 测试告警未确认、个人联系方式失效 | 值班队列、分级、去重、演练、替补和厂商升级 | P1 测试告警未在目标时间确认则运行接管失败 |
| 运行知识留在项目人员手中 | runbook 未实操、值班人员无生产视图 | 影子值班、反向讲解、独立演练、交接签字 | 运行团队不能独立完成代表性处置则 G5 不通过 |
| 成本或配额在上线后失控 | 无预算告警、自动伸缩无上限、配额接近硬限制 | 成本/配额仪表盘、预算阈值、资源护栏和审批 | 预计首月超预算/配额且无批准方案则缩小范围 |
| 安全或权限缺口 | 共用账号、长期高权、审计未开 | 最小权限、短期特权、密钥轮换、负向测试、日志集中留存 | 受限数据存在未授权访问或不可审计路径则 No-Go |

## 10. 容易遗漏的事项

1. **恢复的是服务，不只是数据库。** 身份、密钥、网络、调度、连接字符串、语义层和消费者验证必须进入恢复范围。
2. **备份容量和费用。** 时间旅行、快照、跨区副本、导出、临时表和恢复副本会显著放大实际存储与网络成本。
3. **加密密钥与证书到期。** 数据恢复可能因旧密钥、过期证书或无人有权访问保险库而失败。
4. **时区、夏令时和业务日历。** 批次边界、保留计算、月末窗口和恢复点若使用不一致时区，会造成缺数或重复。
5. **迟到、更正和删除数据。** 不仅要处理新增；还要定义反向冲销、源端更正、迟到维度、删除请求和历史重算。
6. **模式漂移与消费者兼容。** 上游新增/改型、BI 驱动版本、视图列顺序和字段重命名可能在数据库健康时仍使服务不可用。
7. **维护操作的资源竞争。** 备份、压缩、统计、索引/聚簇、真空、重加密、复制和大回填会与日常查询抢占资源。
8. **坏数据的灾难恢复。** 高可用副本会快速复制逻辑损坏或误删；必须保留独立恢复点并定义发现延迟假设。
9. **紧急访问和人员替补。** 夜间是否能取得生产权限、谁批准、如何审计、主要联系人休假时由谁接替，经常到事故时才暴露。
10. **供应商支持的真实可用性。** 支持等级、服务区域、开单权限、严重级别定义、响应时间、日志上传限制和升级联系人需提前验证。
11. **审计和监控自身的保留与失效。** 日志未集中、时钟不同步、监控权限变更或告警通道故障会使事故既不可见又不可追溯。
12. **数据导出和个人工作区。** 数据离开数据库后可能绕过保留、删除和访问复核；首期应限制并记录导出，明确个人沙箱边界。
13. **已知限制的消费者沟通。** 数据截止时间、匹配缺口、非支持查询、降级方式和问题渠道应在认证数据集和培训材料中可见。
14. **退役和回收。** 测试账户、临时恢复环境、旧模式、旧备份、临时特权和并行链路须有回收日期、责任人和验证证据。
15. **成功后的持续所有权。** 项目结束不代表服务无人负责；补丁、容量、成本、恢复演练、访问复核、SLO 和供应商合同都要进入年度运行日历。

## 11. 六周结束时的验收结论格式

最终生产就绪报告不应只给“通过/不通过”，而应列出：每个阶段门结果及证据；服务指标的目标值、实测值和测量窗口；恢复与故障演练时间线；生产配置版本；未关闭缺陷与风险；补偿控制和到期日；首发用户/数据/时间范围；稳定期安排；常态服务负责人和值班队列；下一次容量评审、访问复核、恢复演练和版本升级日期。

结论只能是三类之一：**Go**（全部硬门通过）；**Conditional Go**（仅非阻断风险，且由相应风险所有者书面接受，补偿控制和到期日明确）；**No-Go**（任何数据泄露、不可恢复、RTO/RPO 未验证、核心性能不达标、发布不可回退、值班未接管或合规结论缺失）。这使六周成为受控的首发窗口，而不是以项目日期替代生产责任。
