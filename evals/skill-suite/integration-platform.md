# Task 19 / Scenario A：十二周零售云湖仓端到端 GREEN 评测

## 测试输入、加载路径与路由

原始问题见 `evals/skill-suite/scenarios.md` 的 Scenario A：零售企业十二周建立首个云湖仓，汇总 CRM、POS、电商订单，日更销售及客户指标；云厂商已定，正式治理组织、目录、质量规则尚缺。基线是 `evals/skill-suite/baseline-platform.md`。本次先只读 `skills/managing-data-projects/SKILL.md`，再按其要求读路由表、项目生命周期、交付模板及来源映射；根据场景选域后，才读下列子技能的 `SKILL.md` 和各自 `references/playbook.md`。未读取未路由的子技能。

| 加载技能 | 类型与路由理由 | 在本方案中的明确边界 |
|---|---|---|
| `delivering-data-warehousing-and-bi` | 主域：最终结果是每日销售/客户指标和可用的分析产品 | 决策—指标契约、事实粒度、历史政策、认证语义、业务验收与 BI 服务 |
| `integrating-data` | 主域工作包：三个源进入湖仓，须有契约、水位、重跑、对账 | 源端接口与跨系统数据流，不裁决指标口径 |
| `designing-data-architecture` | 支撑：已有云厂商，但还须确定现状、过渡、目标和能力适配 | 湖仓及系统责任、分层与过渡蓝图，不替代管道实现 |
| `establishing-data-governance` | 基础：无正式治理，跨 CRM/POS/电商的定义和例外必须有人裁决 | 授权、所有权、临时决策与持续接管，不代替执行团队 |
| `managing-metadata` | 基础：无企业目录，首版仍需指标、字段、实际运行血缘可追 | 三源和首版认证资产的最小元数据产品，不建设全企业目录 |
| `improving-data-quality` | 基础：无统一规则，发布前须定义用途适用性、基线和闭环 | 业务规则与根因，接入/仓库团队实现校验和对账 |
| `securing-data` | 基础：CRM 客户信息、源副本和 BI 导出存在访问风险 | 分类、最小权限、独立导出权、负向测试和证据 |
| `handling-data-ethically` | 基础检查：多源客户拼接和经营分析可能越过原收集预期 | 决定允许用途、个人影响和停止条件；法务/隐私另判法律义务 |
| `operating-data-storage` | 支撑：首个生产湖仓需容量、恢复、监控和接班 | 持久化服务与运行就绪，不替代数据集成或 BI 服务 |
| `leading-data-change` | 支撑：经理、分析师、数据 owner 须实际使用新口径和治理流程 | 试用、实操、反馈、采纳和持续强化 |

依赖顺序：业务决策/用途 → 授权与所有权 → 源画像/质量基线/分类 → 架构与指标/接口契约 → 管道和模型 → 元数据、质量、安全及伦理验证 → 业务 UAT/恢复演练 → 逐批上线与接管。`modeling-data` 在这次只需由 BI 工作包完成首版事实/维度模型；如多个项目开始复用企业级概念/逻辑模型、实体键或模型评审标准，再单独调用。`managing-reference-and-master-data` 在首版不负责客户黄金记录；疑似跨源客户只标记和隔离，若重复身份影响客户 KPI 且需要持续合并/拆分，另立 MDM 工作包。`organizing-data-management`、`assessing-data-management-maturity`、`delivering-data-science` 和文档内容管理当前都不是关键路径。上述裁剪有触发条件，详见方案末尾。

来源映射：入口第 1 章；本次领域对应 DMBOK 第 2、3、4、6、7、8、11、12、13、17 章。方案中的十二周安排、阈值候选和表格是项目化设计，不宣称为 DMBOK 原文或官方表单。

## 完整项目回答

### 1. 业务结果、范围与必须确认的假设

首版服务零售经营负责人、区域经理与财务/经营分析师的每日晨会和渠道经营复盘。到第十二周，获授权用户应能在已选云环境中，于约定时点看到上一营业日的销售与客户指标，并从任一认证指标追到口径版本、源批次、转换、质量状态和责任人。价值以“完成经营分析任务的时间、跨部门数字争议次数、人工报表返工量”相对第 1–2 周基线的变化衡量；不能用建成湖仓或报表数量代替业务结果。

首版范围限定三源：CRM 客户必要属性、POS 销售交易、电商订单/退款。交付两个认证主题：每日销售、每日客户购买；保留获批准的最低交易/订单行粒度及事件时间、源键、加载时间、批次，构建一致的日历、渠道、门店/区域与商品维度。客户跨源关联仅在证据充分时给确定映射；疑似与未匹配独立标记，客户指标必须显示覆盖率/适用限制。首期 BI 提供获批准的认证数据集及少量回答晨会问题的报表，禁止将原始联系方式直接暴露给普通分析用户。

未决项在第 1 周由具名角色关闭：营业日及统一时区、销售与财务口径是否相同、退款/取消/税费/折扣归属日期、历史重述或锁账政策、源系统可用接口与补数范围、云地域及客户数据保留/允许用途、早晨业务可用时间、查询负载/预算、现有财务日结或源控制总额。若某项关键定义未获业务 owner 签署，相关指标不进入认证发布；可缩小指标或数据域而非让开发人员代判。

### 2. 最小工件与决策权

| 决策/工件 | 单一最终负责者（A） | 执行者（R） | 关键会签/否决与时限 |
|---|---|---|---|
| 项目范围、价值与上线 | 零售经营赞助人 | 数据产品负责人 | 财务、源 owner、技术/安全参与；跨部门未决在 2 个工作日内上收赞助人 |
| 销售/客户指标契约、历史重述 | 经营指标业务 owner；财务口径由财务 owner 独立负责 | 分析工程师、业务管家 | 冲突以各自明确命名的指标保留；未经授权不称为统一指标 |
| 各源字段权威、质量阈值与例外 | CRM/POS/电商各自数据 owner | 各源系统 owner、数据质量负责人 | 影响跨源认证结果由数据产品负责人协调；高损害例外有期限和补偿 |
| 架构和技术发布 | 数据架构负责人 | 平台/集成/BI 工程负责人 | 安全及运营可因硬门缺证据阻断发布 |
| 客户数据用途、字段分类和访问 | 业务用途负责人/相应数据 owner | 安全与隐私负责人实施/核查 | 隐私/法务判适用义务并可否决；安全负责人可阻断高风险访问 |
| 日常服务与事故 | 运营负责人 | 值班平台/数据工程 | 业务 owner 决定使用前一合格版本、附限制显示或暂停指标 |

第 1 周以项目授权书建立仅覆盖三源和首版指标的临时治理：每周决策/问题会、版本化术语与规则登记、批准/例外/到期/复核记录。正式企业治理组织建立后，由赞助人批准移交范围；不能用“委员会负责”替代单一 A。每项质量、口径、访问或架构例外记录范围、影响、补偿、批准人、到期日与撤销条件。

### 3. 指标、架构与数据契约

| 经营决定 | 首版指标候选 | 必须冻结的口径 | 首版验收任务 |
|---|---|---|---|
| 判断昨日销售与渠道异常 | 销售额、订单/交易数、退款额 | POS 与电商是否重复、取消/退款/税费/折扣、交易日/入账日、货币、渠道归属 | 从三天含退款样本的 BI 数值逆查到源控制总额；财务/经营 owner 签署差异解释 |
| 比较地区/门店/商品 | 同一销售指标按一致维度切分 | 历史门店/地区重组如何呈现、商品层级生效时间 | 抽样相同交易在明细与汇总一致；历史视图规则获批 |
| 看新客/回访与购买 | 活跃客户、新客、客户购买额 | 客户身份覆盖/确定性映射、匿名交易、跨源疑似匹配处理 | 两类客户样本追溯 CRM 与订单；疑似未自动合并，指标显示覆盖率 |

指标契约至少含 ID、业务目的/用途、owner、版本/生效、事实粒度、公式和过滤、时间/币种/退款/历史规则、来源权威、质量与对账门、已知局限、刷新、访问与导出边界。它连接事实/维度模型、SQL/语义配置、报表和 UAT 用例。对同名“收入”不做默认合并：财务确认已结口径前，可只发布明确标名的“交易销售额”。

现状视图列三源的系统责任、表/文件/API、权威字段、复制与依赖、数据量/峰值/历史、地域、质量和运行窗口。目标薄切片：三源受控接入 → 原始且带源/批次留痕 → 标准化与质量隔离 → 必要交易历史及一致维度 → 认证销售/客户语义 → BI。过渡态保留现有日结/报表并行比对；通过业务签收后再切换消费，旧报表的退役由 owner 批准。已选云厂商登记为约束：架构负责人在第 2 周对地域、加密、批量窗口、容量、RTO/RPO、成本、可移植性做适配矩阵；有不适配则记录补偿、缩域或升级决定，不把厂商图当需求。

三个源各有版本化数据契约：对象/粒度/键，schema、枚举与空值，事件/更新时间和时区，删除/更正/退款，源批次或水位，交付窗口，控制清单，分类/保留，兼容变更通知，重送与联系人。日更目标下先用可审计的批量或源支持的增量方式；若源无可靠增量，评估快照比对的窗口/成本后由赞助人与运营批准。源记录的 `source_id`、`batch_id`、`run_id`、代码和映射版本进入运行元数据。幂等写入、坏数据隔离、受控重放、源端控制总额与记录/分组/总量三级对账通过后，才原子切换认证版本；失败保留上一合格版本并显著标记其陈旧时间。

最小元数据产品覆盖三源、关键字段、作业、质量规则、两项认证主题、指标和报表：业务定义/owner、分类/用途、技术 schema、实际部署版本、运行批次、来源与消费者。关键血缘边记录字段/版本、转换、代码/作业运行证据、观察时间、验证人和未知段。验收用“从两项 BI 数值反查源批次”与“改动一个源字段正查受影响报表”各一次；只有设计图的边标为设计态，不冒充生产血缘。目录工具可用简单受控登记册起步，达到真实查询和影响分析即可。

### 4. 十二周活动、依赖与阶段门

| 周次/阶段 | Plan / Control / Develop / Operate 的关键活动 | 出口证据与判定人 | 停止、缩域或回退条件 |
|---|---|---|---|
| 1：对齐 | 冻结经营决定、用户、用途与数据范围；任命赞助/三源/指标/运营 owner；记录未决 | G1：章程、允许/禁止用途、首版指标清单和初始风险，经营赞助人批准 | 关键用途、数据 owner 或地域未决时，受限数据不得进入建设样本 |
| 2：评估 | 源画像、质量/日结基线、元数据源、敏感字段/副本、服务窗口/成本；批准临时治理与术语争议流程 | G2：三源能力/控制清单、基线样本、分类和架构适配矩阵；源 owner/安全/架构签署 | 抽取权限、源控制或适用性缺失则缩小源字段或延期对应指标 |
| 3–4：设计 | 指标契约、事实粒度/一致维度/历史政策；数据契约、目标/过渡视图、质量规则、访问矩阵、SLO/RTO/RPO、容量估算 | G3：业务口径、契约、规则/阈值、技术和控制设计均有批准版本；数据/架构/安全/运营会签 | 指标未裁决、恢复目标无责任或敏感权限不清则不进入认证开发 |
| 5–7：构建薄切片 | 建受控环境、流水线、隔离与重放、分层对账；实现首个完整 POS→销售→BI 纵切片，再加电商与 CRM；采集实际血缘 | G4：版本化部署、真实样本的源到报表追溯、故障/重跑不重计、权限拒绝测试 | 关键对账失配、重跑重复、权限泄露时保留旧版本并修复 |
| 8–9：验证 | 初装及多个日更周期、迟到退款/删除/变更测试；财务/经营样本签收；容量/峰值、隔离恢复、UAT 和试用 | G5：对账/质量、BI 五项真实任务、负向访问、恢复和源字段变更影响演练；业务/安全/运营批准 | 硬门未过则仅内部沙箱或缩小指标/用户群，不能贴认证标签 |
| 10：灰度 | 与原报表并行，按用户群放行，标示最新合格版本与差异；训练分析师、经理、管家与值班 | G6：发布/回退演练、用户实操、支持链、例外、运营接管签字；赞助人决定 Go/Conditional Go/Hold | 认证数值或权限回归失败即回退到前一版本/原报表并通知消费者 |
| 11–12：稳定与移交 | 连续观察日更与使用；关闭阻断问题，分析根因；签服务和治理接管，形成后续 90 天路线 | G7：约定观察窗口内运行趋势、事故/例外台账、采纳任务证据、成本与价值复盘；赞助人验收 | 达不到 SLO、无人值班或重大用途漂移，则延长灰度/缩域并明确 owner 与日期 |

周次是依赖安排，不是自动放行日期。任何 Conditional Go 都写明已知风险、责任人、补偿控制、到期日和撤销触发器。对法律/监管/跨境/保留的结论只由适用地区的隐私、法务或合规责任人核对当前权威依据后决定，项目计划不得自行推断。

### 5. 质量、安全、伦理与运行验收

第 2 周先画像，按源、日、渠道、客户可识别状态分别冻结分母、样本、基线和质量规则版本。首版候选硬门：源清单和批次覆盖 100%；关键交易 ID/金额/日期/币种可解析且与源日结的记录数和金额对账；金额差异容差暂拟 0.5%，但须根据真实基线、财务用途和风险由指标 owner 在 G3 批准，不能在发现差异后移动阈值。客户身份匹配报告确定/疑似/未匹配三态及各自分母；疑似不自动合并，客户指标覆盖率低于业务批准下限时只发布销售指标。规则失败阻断认证、隔离记录并指派源/转换根因 owner；非阻断例外有可见限制和到期复核。连续的新增缺陷率与消费报表差异均进入运营记分卡，源头预防事项不可用下游补值代替。

安全方面，客户姓名、联系信息、持久标识及可重识别组合先按受限候选分类，待数据 owner/隐私确认。生产、非生产、原始、认证和 BI 层按身份/动作/期限分离；查询与批量导出单独授权，服务身份不共用人员账号，密钥与日志职责分离。非生产优先合成数据；确需生产子集时，在进入非生产前完成获批、持久脱敏和组合重识别测试。最低负向验收：普通 BI 用户无法读取原始联系方式或导出限制字段，撤权即失效，恢复副本仍继承访问/审计，日志中断触发告警；记录策略版本、主体、预期/实际、证据和独立复核。

伦理用途声明限定为内部汇总经营分析。比较聚合/代理键等少数据方案；识别客户、员工及门店代表的潜在不利影响，检查小样本分群、误关联和误导性图表是否可能把个人/门店错误标为异常。营销定向、个体价格/待遇、风险评分、对外共享和跨境传输均需新用途评估及相应批准。BI 展示时效、覆盖、退款和未结限制；有关个体的重大行动不得只凭本版指标自动执行。受影响者的更正/投诉渠道由客服与数据 owner 指定；出现用途外导出、严重误关联或无法解释的分群伤害时暂停相应消费，保全证据并复核。

运营目标由业务在 G3 批准：每日指定晨会时点前发布 T+1 最近合格版本；各源单独显示 `as_of` 和批次，不用一个“已更新”掩盖某源迟到。监控源到达/水位、批次、拒收与对账、认证版本年龄、BI 查询 p95、容量/成本、权限与审计、用户任务完成。平台负责人交付可重建配置、备份/恢复计划、保留/处置范围；未来值班人员在隔离环境从非当前备份恢复，实测从事件宣告到最低服务恢复的 RTO、可接受的 RPO、结构/权限和业务总额。RTO/RPO 数值先依据晨会业务影响在 G3 冻结，恢复演练实测未达目标即 No-Go。容量计算包括主数据、日志/暂存、时间旅行/副本、备份、恢复空间和增长，并设置扩容提前阈值。云厂商 SLA 不能替代数据产品的端到端日更、查询、恢复和支持目标。

故障分级：敏感数据暴露、错误认证指标影响经营决定或不可恢复的数据丢失为 P1，值班立即止用/隔离并联络安全、数据 owner、赞助人；错过发布窗口、关键源迟到或质量阻断为 P2，在承诺通知时限内发布原因、最近合格版本和预计恢复时间。P1/P2 的分钟级通知及恢复时限要由运营与业务在 G3 签署，随后做告警到工单、联系人确认、回退/恢复演练。变更单包含源/口径/规则/代码版本、影响消费者、测试、回滚和通知；运行期继续每周服务复盘、每月访问和用途复核，重大拓扑/密钥/备份变更触发恢复复测。

### 7. 采纳与明确裁剪

第 1–2 周按经营高管、区域经理、财务/经营分析师、源系统 owner、数据管家和值班人员画出真实任务与当前报表返工；第 5–9 周请每群体代表参与原型和样本解释。培训须让用户亲自说明指标口径、刷新与限制，完成一个追溯/质疑/纠错任务；签到不算能力。灰度期按有真实使用机会的用户分母统计任务完成、连续使用、绕过认证数据集、争议和返工；访谈低采用的原因，修入口/定义/权限或流程。赞助人及中层经理在日常晨会使用认证版本，并解释例外；第十二周将采纳、问题和培训纳入常态产品运营。
