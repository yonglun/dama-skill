# RED 基线：客户数据质量反弹

## 测试条件

- 在 `improving-data-quality` 技能创建前独立作答；未读取或使用该技能，也未修改任何技能。
- 场景：三个月前对 CRM 客户记录做一次性去重和地址清洗；现在重复客户、无效新地址、缺省国家码再次上升，报表与寄送受影响。源头和下游都有异常，多团队互相推责；业务要求八周内让质量持续改善。
- 下面的“实际回答”先写出，随后才按 DMBOK 第 13 章要求自评；自评中的补救项没有回填到实际回答。

## 实际回答（未使用专属技能）

这次不再做一次性全量清洗。我会把八周目标定为：新增客户记录的重复、无效地址和缺省国家码持续下降；经营报表和寄送清单能够使用一份有明确质量状态的客户数据。先挑 CRM 新增客户和最近两个月的寄送对象，避免在八周内扩展到全部历史记录。

第 1 周，CRM、计费、报表和寄送团队各指定一名负责人。取近期新增和更新的客户样本，统计重复率、地址校验失败率、国家码缺失率，并把问题按来源系统、录入渠道和发生日期拆开。抽样追查十到二十条典型记录，确认是表单约束、批量导入、接口映射还是下游转换造成的异常。业务负责人确认三个指标的目标值和每周报表口径。

第 2–3 周，在 CRM 表单和导入接口加入必填、格式、国家码标准值和疑似重复提示；在下游落地前设置校验和异常队列。对于合法但不满足自动校验的地址，安排人工核实。对现存高影响记录按寄送时间和客户活跃度排序修复，保存修改前后的值和操作人。对不能确认的客户，不自动合并。

第 4–6 周，把每周质量报告送到各团队例会，按渠道、系统、规则显示新增异常、未解决积压和复发情况。问题单记录发现位置、样本、负责人、截止时间和修复结果；对跨团队争议，由 CRM 产品负责人召集业务和技术负责人决定修在源头还是接口，并跟踪部署后的异常变化。用真实寄送失败和报表差异样本验证修复效果。

第 7–8 周，抽查新增记录和已修复记录，验证三项指标是否连续四周改善。验收交付包括规则清单、基线与趋势图、问题台账、源头校验及下游异常队列的运行记录、寄送失败与报表差异的复测结果。若指标反弹，保留每周例会和异常队列，继续由 CRM 产品负责人协调处理。

## 回答后自评：DMBOK 第 13 章维度遗漏

| 维度 | 实际回答覆盖 | 具体缺口 |
| --- | --- | --- |
| Fit for purpose | 部分 | 只把报表和寄送列为用途，没逐项写出使用方所需的准确性、时效性、容错限度与验收门槛，也没有判断同一字段对不同用途的适用性。 |
| 关键数据元素 | 部分 | 聚焦客户、地址、国家码，但没有正式指定关键数据元素清单、字段定义、系统边界、负责人和优先级。 |
| 维度与规则 | 部分 | 有重复、有效性、完整性及校验项，但没有逐条规定适用粒度、分母、排除条件、阈值、误报复核和维度间关系。 |
| 画像与基线 | 部分 | 有样本统计、基线和趋势；未定义全量画像、分层抽样、基线时点、观察窗口、数据量及置信边界。 |
| 业务影响与优先级 | 部分 | 用寄送时间和客户活跃度排序修复，但没有量化退件、报表误差、人工返工的成本及风险，也没有按影响与修复成本建优先级。 |
| 根因 | 部分 | 提出典型记录排查，但没有把每个问题与可验证的根因假设、证据、责任边界、控制缺陷和复发实验相连。 |
| 预防、侦测、纠正 | 基本覆盖 | 三类措施都有，但没有定义各控制点的覆盖范围、失败时退路、运行责任与控制有效性验证。 |
| 问题流程 | 部分 | 有问题单、负责人和期限；没有严重度、升级门槛、关闭证据、重复问题合并规则或跨系统争议仲裁时限。 |
| 规则版本 | 遗漏 | “规则清单”只是静态交付；没有版本号、生效日期、变更审批、回测、发布和回退流程。 |
| 趋势 | 部分 | 有连续四周改善和周报，但没有分清存量与新增、输入与输出、量与率，也没有明确阈值触发升级。 |
| 成本与收益 | 遗漏 | 未建立实施成本、运行成本、返工节省、寄送成功率、报表可信度的基线和收益追踪。 |
| 例外与风险接受 | 部分 | 有人工核实与“不自动合并”，但没有例外登记、审批权、有效期、补偿控制、风险接受与复核。 |

基线主要失败模式：方案意识到一次性清洗会反弹，也设计了源头和下游控制，但仍把质量规则当作静态清单，把八周验收压缩为三项指标的改善；未形成可审计的规则变更、例外、业务适用性和收益闭环。多团队互相推责时，`CRM 产品负责人协调`也不足以界定每项关键数据元素及每个控制点的业务与技术责任。

## 负向场景

若核心诉求是长期统一 CRM、计费和客服中的客户身份，定义权威客户标识、黄金记录及合并/拆分权，主路由应为 `managing-reference-and-master-data`。数据质量可以为匹配误差、字段完整性和发布后漂移提供监测，但不能代替 MDM 的实体解析、权威来源与主数据治理决策。
