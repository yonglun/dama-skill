# DAMA 数据项目技能体系设计

## 1. 目标

把附件《DAMA-DMBOK Data Management Body of Knowledge, 2nd Edition, Revised Edition》转化为一套可在真实数据项目中按需调用的 Codex Skills。

技能体系必须帮助代理完成项目判断与交付，而不只是复述术语。它应能：

- 从业务目标、项目阶段、数据风险和预期交付物判断应使用哪些数据管理知识域；
- 把 DMBOK 的目标、原则、活动、角色、输入、交付物、技术、工具和指标转成项目工作流；
- 在数据平台、治理、质量、主数据、数仓 BI、数据科学等项目中补齐经常被遗漏的治理、安全、元数据、质量和变更管理；
- 根据组织成熟度裁剪，而不是要求所有知识域一次性全面落地；
- 保留来源映射和适用边界，不复制原书，也不把框架当成强制标准。

默认输出语言为中文，关键 DAMA 术语首次出现时保留英文。

## 2. 设计选择

采用类似 Superpowers 的“一个路由入口 + 多个可独立触发的子技能”结构。

不采用单体 SKILL，因为它会在每次调用时加载大量无关知识，且难以验证不同项目情境下的行为。不采用只有参考文件的单技能结构，因为参考文件无法被独立发现或触发。

## 3. 总体架构

```text

├── managing-data-projects/                 # 总入口：诊断、路由、组合、阶段门
│   ├── SKILL.md
│   └── references/
│       ├── project-lifecycle.md            # 战略到运营的端到端生命周期
│       ├── routing-table.md                # 场景 × 阶段 × 知识域路由
│       ├── deliverable-templates.md        # 通用项目交付模板
│       └── source-map.md                   # DMBOK 章节与技能映射
├── handling-data-ethically/
├── establishing-data-governance/
├── designing-data-architecture/
├── modeling-data/
├── operating-data-storage/
├── securing-data/
├── integrating-data/
├── managing-documents-and-content/
├── managing-reference-and-master-data/
├── delivering-data-warehousing-and-bi/
├── managing-metadata/
├── improving-data-quality/
├── delivering-data-science/
├── assessing-data-management-maturity/
├── organizing-data-management/
└── leading-data-change/
```

每个子技能包含一个精简 `SKILL.md`。需要较多领域细节的技能使用 `references/playbook.md`，按以下统一模型组织：

1. 业务驱动与目标；
2. 原则与关键概念；
3. Plan / Control / Develop / Operate 活动；
4. 输入、供应者、参与者、消费者；
5. 交付物与验收证据；
6. 工具与技术的选择标准；
7. 指标、风险和实施注意事项；
8. 与其他知识域的依赖关系。

## 4. 核心运行模型

入口技能先建立最小项目画像：

- 业务结果与价值假设；
- 项目类型和当前阶段；
- 数据范围、关键数据对象和消费者；
- 法规、伦理、安全和隐私约束；
- 当前能力、组织职责与变更阻力；
- 已有交付物、缺口和决策期限。

然后执行四步：

1. **诊断**：识别主要知识域、基础知识域和治理知识域。
2. **裁剪**：依据风险、价值、成熟度和依赖关系确定最小可行范围。
3. **编排**：把活动映射到 Plan / Control / Develop / Operate，并设置阶段门。
4. **交付**：生成具备责任人、输入、输出、验收标准、指标和风险的项目工件。

入口技能不会代替领域技能回答详细问题。它负责选择技能、说明顺序、合并跨域交付物并发现遗漏。

## 5. DMBOK 框架映射

技能体系保留附件中的三个关键视角：

- **DAMA Wheel**：数据治理位于中心，11 个核心知识域共同构成数据管理能力；
- **Environmental Factors Hexagon**：目标与原则由人员、流程和技术共同实现，并落到角色、活动、工具、技术和交付物；
- **Evolved Framework**：治理是监督层，架构/建模/平台等构成生命周期层，数据质量、元数据以及安全/隐私/风险构成贯穿全程的基础层。

因此任何建设型项目都至少检查：治理责任、数据质量、元数据、安全与隐私。检查不等于全部实施；是否纳入范围由风险和价值决定，并记录裁剪理由。

## 6. 子技能责任边界

| 子技能 | 主要用途 | 代表性交付物 |
|---|---|---|
| handling-data-ethically | 伦理风险、隐私原则、负责任使用 | 伦理影响评估、允许/禁止用途、升级机制 |
| establishing-data-governance | 决策权、政策、标准、治理运营 | 治理章程、决策权矩阵、议题流程、业务术语表 |
| designing-data-architecture | 当前/目标架构与迁移路线 | 架构原则、现状/目标蓝图、过渡架构、路线图 |
| modeling-data | 概念/逻辑/物理模型及模型治理 | 数据模型、命名标准、模型评审记录 |
| operating-data-storage | 数据库与存储运营可靠性 | 容量/备份/恢复方案、运行手册、SLA/SLO |
| securing-data | 分类、访问、保护与审计 | 分类分级、访问模型、控制矩阵、安全测试证据 |
| integrating-data | 批流集成、交换和互操作 | 接口契约、映射、血缘、对账与监控规则 |
| managing-documents-and-content | 非结构化内容生命周期 | 分类体系、保留处置规则、内容治理流程 |
| managing-reference-and-master-data | 主数据和参考数据一致性 | 黄金记录规则、匹配合并、层级、分发与变更流程 |
| delivering-data-warehousing-and-bi | 数仓、语义层、BI 产品 | 需求矩阵、维度模型、语义定义、发布路线图 |
| managing-metadata | 业务/技术/运营元数据 | 元数据策略、目录模型、血缘、影响分析、覆盖指标 |
| improving-data-quality | 质量定义、评估、整改和监控 | 质量规则、基线、问题台账、根因、控制图/记分卡 |
| delivering-data-science | 分析与数据科学全生命周期 | 假设、数据选择、实验、模型风险、部署监控 |
| assessing-data-management-maturity | 现状评估与能力改进 | 评估范围、证据评分、目标能力、优先改进计划 |
| organizing-data-management | 组织模式、角色和职责 | 组织模型、RACI、岗位职责、委员会与互动机制 |
| leading-data-change | 采纳、沟通与持续变革 | 利益相关者图、变更计划、沟通/培训、采纳指标 |

## 7. 交付物契约

除纯问答外，技能输出的项目建议必须包含：

1. 业务结果与范围；
2. 假设、约束和未决问题；
3. 相关知识域及选择理由；
4. 活动与依赖顺序；
5. 角色与决策权；
6. 交付物及可验证验收标准；
7. 指标、风险、控制和升级条件；
8. 裁剪掉的内容及理由；
9. 下一阶段门与所需证据。

通用模板放在入口技能的参考资料中；领域特有模板放在对应子技能的 `playbook.md`。

## 8. 错误处理与边界

- 缺少业务目标或范围时，先请求最小必要信息，不直接生成完整方案。
- 法律、监管或行业标准随时间和地区变化；技能只给控制框架，具体要求必须核对适用的权威来源。
- DMBOK 不背书具体厂商。技能提供能力与选择标准，不默认指定产品。
- 不把成熟度评分当作精确科学；所有评分必须关联可复核证据。
- 不因“建设优先”跳过伦理、安全、隐私、质量和元数据检查。
- 不把检查结果自动扩张为实施授权；重大范围变化需用户确认。
- 不长篇复制受版权保护的原文；采用归纳、重组和项目化模板，并保留章节级来源映射。

## 9. 验证策略

### 9.1 RED：无技能基线

使用独立代理执行至少三类场景，并记录其遗漏：

1. 新建湖仓/数据平台：观察是否遗漏治理、血缘、质量、安全、运营和变更；
2. 客户主数据质量整改：观察是否只做清洗而遗漏所有权、匹配规则、参考数据、根因和持续控制；
3. 风险评分模型上线：观察是否遗漏伦理、用途限制、元数据、模型监控和组织采纳。

### 9.2 GREEN：逐技能验证

每个技能创建后立即完成：

- `quick_validate.py` 结构验证；
- 触发与反触发测试；
- 一个应用场景测试，确认能产出该领域的活动、角色、交付物、验收标准和指标；
- 引用路径和渐进披露检查。

### 9.3 集成验证

由入口技能重新执行三个基线场景，验证：

- 路由到正确的主技能和基础技能；
- 依赖顺序合理；
- 输出包含交付物契约的九项内容；
- 能说明哪些能力暂不实施以及原因；
- 不出现 DMBOK 未支持的强制要求或厂商偏好。

### 9.4 完成标准

- 17 个技能目录均通过结构验证；
- 所有子技能至少通过一次独立行为测试；
- 三个端到端场景相较基线明显减少关键遗漏；
- 入口及子技能的描述可以被正确发现且不会相互误触发；
- `source-map.md` 覆盖附件第 1–17 章；
- 不存在脚手架占位符、断链或未说明的跨技能依赖。

## 10. 环境与发布

成果保存在当前仓库的 `skills/` 目录，便于审阅和后续安装。当前目录没有 Git 元数据，因此设计和实现阶段无法执行提交或推送；除非用户另行提供 Git 仓库，该限制不阻止生成与验证技能文件。
